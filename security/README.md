# Security inventory: principals, protected assets and credential requirements

Plan leaf **S-01.1**, "Inventory principals and protected assets", as of 2026-11-07
(baseline commit `b358a68`). This record is the input that S-01.2 (role-scoped
identities and secret delivery) and S-01.3.x (management API admission and
container-socket isolation) implement and test against.

- **Acceptance of this leaf:** each privileged operation has a named principal, and no
  agent-managed token is described as Owner authority.
- **Inherited parent obligation (S-01, not tested here):** an agent cannot invoke
  privileged conversation creation or reach Owner or admin tokens, even if it controls
  its own workspace.
- **Machine-readable form:** [`inventory.json`](inventory.json). Every table below is
  rendered from it, and [`tools/check_security_inventory.py`](../tools/check_security_inventory.py)
  checks it (`task security:check`; see [What the checker enforces](#what-the-checker-enforces)).
- **S-01.4 (2026-11-07)** adds the deny-by-default network matrix,
  [`policy/network-matrix.json`](../policy/network-matrix.json), keyed by the trust domains
  below, and [decision 0013](../decisions/0013-owner-ui-session-access-and-management-key-custody.md)
  (Proposed): the Owner UI's access to engineering sessions and the dispatcher's sole custody
  of the management key. It splits `cred-owner-ui-access` into two planned credentials, adds
  the Owner host and the Integration API as assets, turns the container network deviations
  and the host-loopback exposure into limits and records a plan-silence finding.
- **S-02.1 (2026-11-08)** adds the versioned containment cases and their
  expected-denial matrix: see [Containment cases](#containment-cases-s-021).
- **This is an inventory, not a control.** It creates and changes no identity, account,
  key, token, service, firewall rule or permission. Nothing here makes the strong tier
  operational: that still waits for S-02.x (decision 0003, C6).

## How to read it

Every entry carries one status from a closed set:

| Status | Meaning | Must carry |
|---|---|---|
| `observed` | Exists today and is shown by committed evidence. | at least one evidence link: a committed evidence record, or the decision or profile that records the observation |
| `planned` | Defined by accepted authority (the blueprint, the plan, a decision or the execution-profile contract) but not built or not enforced yet. | at least one source link |
| `unknown` | Not established from the accepted records or the committed evidence. | a finding |
| `conflict` | Two accepted records disagree. | a finding of kind `conflict` |

Planned and observed are kept apart at two levels:

- **Principals** carry `identity.planned` (what the authority assigns) and
  `identity.observed` (what exists today, with evidence, or `none`). A principal can be
  `planned` while part of its identity is already observed: the engineering agent's
  container identity was observed for a no-LLM fixture conversation, but no agent
  workload has run.
- **Operations** carry the accountable `principal` the authority names, and, separately,
  who performs the operation today (`observed_performer`). An operation is `observed`
  only where the binding to its principal is itself shown by evidence; where the
  principal is planned and an interim performer acts today, the operation stays
  `planned`. Example: the authority gives conversation creation to the trusted
  dispatcher (`planned`), while today the Owner's account performs it through the
  operator login during inspection runs.

No conflict between accepted records was found. No credential or secret value was
encountered in the records read for this inventory; credentials are described by
custody only, and locations are described generically.

## Summary

- **Trust domains (9).** Owner; trusted management; privileged effect; Git hosting
  (trusted computing base); execution-guest control (contained); untrusted engineering;
  review; untrusted CI; CI runner host (contained).
- **Principals (18).** Seven are observed today: the Owner, the Owner's Windows
  account, the host-side bootstrap agent sessions, the Gitea site administrator (its
  account, administered during bootstrap through Gitea's CLI by the Owner's account),
  and in the guest root, the service user `openhands` and the operator login `agent`.
  One, the release job environment, is unknown. The other ten are planned.
- **Credentials (27), assets (41), findings (21:** 6 unknown, 2 open risks, 13 limits).
- **Privileged operations (37), each with exactly one principal.** 6 Owner-only,
  all assigned to `owner`. 14 observed, 22 planned, 1 unknown. By principal:
  `management-dispatcher` 9 (the Agent Server management API and the CI dispatch; planned, no
  dispatcher yet); `owner` 6; `owner-os-account` 5 (guest lifecycle, exec, exchange,
  session-key export, provisioning fetch); `guest-root` 3; `privileged-executor` 2;
  `gitea-site-admin` 2 (Gitea administration and the CI lane's administration);
  `guest-service-openhands` 1 (the guest's Docker API); and one each for
  `engineering-agent`, `reviewer-agent`, `ci-job`, `ci-runner-service`,
  `release-job-environment` (unknown), `authorization-verifier`, `authorization-recorder`
  (the protection check), `integration-service` and `inference-broker`.
- **No agent principal holds, manages or may read an Owner, admin, executor or
  management credential, and no Owner-only operation uses such a credential.** The
  engineering and reviewer agents and CI jobs hold only `scoped` credentials (their
  Gitea bot or job tokens, and each conversation's own inner-server keys).
- **The material limit** is [`fd-bootstrap-shared-identity`](#findings): the host-side
  bootstrap agents run as the Owner's Windows account, so every credential in that
  account's custody is reachable by them. They are recorded as an agent principal that
  shares the Owner's OS identity and is **not independently isolated** (decision 0004,
  Owner clarification 5). UAC consent gates their elevation but is not a security
  boundary. The checker requires every privileged credential they can reach this way to
  carry a finding that names them.

Two Agent Servers appear in the records and belong to different domains. The **outer**
Agent Server runs in the guest as the service user `openhands`, holds the guest's Docker
authority and serves the management API (`td-guest-control`; decision 0003, F-04.1c
amendment: "the guest's own service principal"). Each conversation runs its own
**inner** Agent Server inside its container (`td-untrusted-engineering`; blueprint
`#containment-architecture`, "Per-conversation Agent Server").

### Open risks and limits against the assets they affect

The containment deviations recorded at F-04.2 are narrowed by S-01.3.1 (the container
guard and icc off close every path from a container to the guest itself and to another
container), by S-01.3.2 (no engine socket, engine API, management route, host service or
management, Owner, admin or bot credential is reachable from a job) and by S-01.4 (the
egress guard refuses every new connection out of the guest from a container; decision 0013
scopes the host network plane). What remains:

- **`host-gateway`, the default bridge and request caps that override the server's**
  affect `conversation-container`, `guest-sshd` and `guest-conversation-listeners`
  (`fd-container-network-deviations`, a limit since S-01.4, re-tested by S-02.1;
  E-01.2.2, S-02.2, S-03.1).
- **Conversation containers run as the service user's uid** and their keys are visible
  through `docker inspect` (`fd-container-shares-service-uid`, open risk; S-02.1: a job writes
  only its own three binds, its own conversation store included; E-01.2.2: a job-written
  `running` record made the pinned server resume the conversation in its own process at its
  start, compensated by the root quiesce step before every server start,
  `fd-outer-server-local-recovery`); their image ships engine clients and setuid-root helpers,
  inert in a job (`fd-job-image-engine-clients`, re-run by S-02.1).
- **QMP and the SSH forward** are open to every local process on the host
  (`fd-host-loopback-exposure`): a limit under the same-account scope of decision 0013,
  point 6. Every harness host listener binds 127.0.0.1 only (`guest.py host-census`).
- **While a forward session is held, the guest's own processes** reach the inference
  endpoint and through it the broker's inference listener (`fd-guest-inference-reach`, a limit;
  S-03.2): the container guard filters docker0 only, so the attempt token is the only admission
  control there (`nm-guest-inference`, case `egr-inference-guest-login`, both planned).
- **Between the protection check and Gitea's own merge-time evaluation** a repository or site
  administrator can change a rule of `repo-gitea-authorization` on `gitea-server`; the recorder's
  second read after the merge discloses a change that is not reverted within the window
  (`fd-protection-check-toctou`, a limit; Owner decision OA-16).

## Findings

- **`fd-bootstrap-shared-identity`** (limit): Host-side bootstrap agents share the Owner's Windows account. The host-side agent sessions run as the Owner's account and are not independently isolated security principals. Every credential and store in that account's custody (the public-repository push credential, the provider login, the guest SSH keys, the exported session keys, QMP, the guest-state root, the integration store) is reachable by them. Their elevation is gated by the Owner's interactive UAC consent, which is not an OS security boundary. This is the accepted bootstrap limit; the guest boundary is the boundary against untrusted agents, and the genuine OS boundary for privileged effects is the executor's separate identity (G-04.2.1). No credential is designated to an agent principal here; the reachability is disclosed, not prevented. Since F-06.1 this includes the host-loopback Gitea: any process of the Owner's account, host agents included, can read Gitea's app.ini secrets (SECRET_KEY, INTERNAL_TOKEN, JWT_SECRET) and its SQLite database under the managed data root. The INTERNAL_TOKEN reaches Gitea's private API, and write access to the database can change any account, its administrator flag or its password hash, so such a process can forge or take over Gitea sessions and identities, the site administrator's and the Owner account's included. The two temporary passwords in Credential Manager, and after task gitea:finalize-credentials the two harness-held final passwords, are readable the same way. The final passwords exist only as Gitea's password hashes. Directory placement is not a security boundary (decision 0009, point 11). Since S-01.2.2 it also includes the four bot tokens in Credential Manager ("AIEH Gitea bot <role>"; five since the protection auditor's was provisioned on 2026-11-12, cred-gitea-protection-audit, OA-16), which CredReadW returns to any process of the account without a prompt, and Gitea's CLI, which mints a token for any account, the site administrator's and the Owner account's included, without a password. None of this is reachable from the execution guest (profiles P3-P5, F-03.3.1). Carried to: G-04.2.1.
- **`fd-owner-authorization-record`** (limit): Owner authorization is a recorded decision, not an authenticated one. Narrowed at P-04.2, not closed. An Owner authorization is now a recorded decision: the authorization recorder (decision 0012, accepted 2026-11-12) records the Owner's statement in the shared Owner decision record (kind authorize-operation), binds it to the exact head and manifest digest of the proposal, writes a write-ahead receipt to the integration store and merges as aieh-owner with the decision's trailers; merged_by aieh-owner means merged under Owner authority by the recorder, never by the Owner. What remains: in the bootstrap channel the statement is the Owner's verbatim reply in the main-session conversation, transcribed by the Overseer, which proves a declared decision bound to an exact revision, not an authenticated Owner (the target channel is an authenticated Owner host session); aieh-owner cannot read the branch protection rule in Gitea 28.3.0 (repository or site administrators only), so the recorder merges only when the protection check (op-protection-verify; Owner decision OA-16), reading as a read:repository auditor, answers verified (the auditor provisioned and the check qualified live on 2026-11-12, OA-16 Acts A to D; its time-of-check limit is fd-protection-check-toctou); processes of the Owner's account can reach the credential (decision 0010); one Owner authorization has been recorded and merged, on the S-01.2.2 fixture (OA-14, 2026-11-12), but the authorization repository (G-03.1) and the record verifier (G-04.3) do not exist yet. During bootstrap the Owner's other decisions still reach the repository as records the Overseer writes (decisions/, evidence/bootstrap-log.md). Carried to: G-03.1, G-04.x.
- **`fd-protection-check-toctou`** (limit): The protection check and Gitea's merge-time enforcement are not one transaction. Owner decision OA-16 (2026-11-11). The authorization recorder merges only when the protection check (op-protection-verify) answers verified as its last read before the merge; Gitea 28.3.0 then evaluates the rule row as it is at the merge itself, twice (CheckPullMergeable in the merge handler, and the pre-receive hook of the merge push), and no API spans a read and a merge. What Gitea enforces at merge time: the merge allowlist, the required approvals from the approvals allowlist, rejected reviews, official review requests, code-owner reviews, an outdated branch, status checks, protected files, signed commits, the head_commit_id the recorder sends (409 when the head moved) and the bypass allowlist, which lets a listed account force-merge past every gate; it does not compare the rule with any declaration, so a changed rule is enforced as changed. What remains: a repository or site administrator (inside the trusted computing base, decision 0010) can change a rule between the check and the merge, about one request round-trip on host loopback; the check runs again after the read-back and the receipt records both digests, so a change that is not reverted within the window is disclosed (PROTECTION_CHANGED_AFTER_MERGE), not prevented. Gitea 28.3.0 audits branch protection changes made through its web pages only, not through its API, and exposes the audit log through web pages only (protection-check recommendation, finding F-B), so the audit log is corroboration for web-made changes, never the control. Team membership is not readable with read:repository (it needs the organization scope), so who belongs to the Owners team, whose members administer the repository, is not compared; each collaborator's permission is read as Gitea computes it, team membership included. Carried to: G-03.1.
- **`fd-guest-login-name-and-key`** (limit): The operator login `agent` reads the management key; no agent workload has that login. Custody as of S-01.3.1. No dispatcher exists. During bootstrap the dispatcher's role is performed by the Owner's account through tools/guest.py, over the instance's host-loopback SSH forward with the per-instance key, as the operator login agent, which reads the session key from its root:agent 0440 file inside the guest (never on a command line). No agent workload ever has that login: an engineering agent runs in a conversation container as 999:989 in its own namespaces, holds no SSH key, cannot reach the guest's sshd (the container guard refuses it at every guest address), cannot reach the management listener, and its readable process environments hold only its own conversation keys (the outer key's fingerprint was absent from both containers, S-01.3.1). The name still collides with the engineering-agent role, and anyone given the login would hold the full management key. Moving the key to a separate guest identity (a dispatch group that agent is not in) is proposed to the Overseer, not done; whether the login keeps the key once a dispatcher exists is decided with the dispatcher (E-01.2.x). S-01.3.2: no job holds the login, its SSH key or the management key: the outer key's fingerprints are absent from every readable file and process environment of two conversation containers, and sshd, the management listener and the instance's host forwards refuse from them. Custody beyond bootstrap stays with E-01.2.2. S-01.4 (ruling R9): the session-key file stays where it is; the finding is carried to E-01.2.2 and E-01.3.1. E-01.3.3 (2026-11-11, the Overseer's ruling F-2 on the architecture consultation): the bootstrap reading of decision 0013 point 1 applies as written. The dispatcher principal is the Owner's account acting through the dispatch module (integrations/dispatch/guest_transport.py) over tools/guest.py's GuestApi as agent; the key file stays root:agent 0440 (R9) and is read in the guest only, never on a command line or in the host process; the cut-over is the code path (op-as-* on Work only through the dispatch module); no seed, profile or guest-login change. The host copy of the key stays the leak scan's needle, disclosed under decision 0013 point 6. The separation of an operator login from the dispatcher's guest login is deferred to the first leaf that changes the seed for the Owner UI forward (OA-07, U-03.1), and the dispatcher's own host identity is a plan silence routed to the Owner (no leaf; carried_to names plan leaves only). Built offline; not yet verified live: the custody probe is prepared and unrun. Carried to: E-01.3.3, U-03.1.
- **`fd-session-key-not-fine-grained`** (open-risk): One session key grants the whole management API. The outer Agent Server accepts one X-Session-API-Key for every key-gated route; there is no per-route or per-role scope, and the only rotation is recreate and provision. S-01.3.1 enumerated the routes (193; the key admits 166 HTTP routes directly and mints the workspace and app-backend sessions) and marks in the route inventory which ones the trusted dispatcher may call: that allowlist is the dispatcher's policy, not a server control. What the server and the guest enforce is admission by key and by network: the listener is on the guest's loopback only, the unit drops non-loopback packets, and the container guard refuses every new connection from a container bridge to the guest. S-01.4 narrows its reach without changing the mechanism: by decision 0013 no browser, UI process, Integration process or agent ever holds the key; the Owner UI reaches a session only with that conversation's runtime credential. Carried to: E-01.2.2, E-01.3.1.

## What the checker enforces

`python -I -B tools/check_security_inventory.py` (`task security:check`) exits 0 only
when:

1. every privileged operation names exactly one principal (`principal` is one id, never
   a list) and that principal exists;
2. no credential of authority `owner`, `admin`, `executor` or `management` is held,
   managed or readable by an agent-controlled principal; an `owner` credential is held
   by a principal with Owner authority; and no Owner-only operation uses a credential
   that an agent principal holds, manages or may read;
3. an Owner-only operation's principal holds Owner authority; an agent principal is
   never assigned an Owner-only operation or a privileged credential; and only the
   Owner and the Owner's own account (never an agent-controlled principal) are
   described as holding Owner authority;
4. an agent principal that shares the OS identity of an Owner-authority principal is
   marked `independently_isolated: false` and carries a finding, and every privileged
   credential it can reach that way carries a finding that names it;
5. every referenced id exists: trust domains, principals, credentials, assets,
   findings, and plan leaves in `carried_to`;
6. every entry's status is one of the four, with its required evidence, sources or
   finding; every link resolves to a file in the repository, and every blueprint anchor
   and plan id to an element of it;
7. no machine path (drive letter, UNC path, user-profile variable) appears anywhere;
8. this README names every operation and finding id.

`--list` also prints each privileged operation with its principal and status. The
negative cases (an unnamed principal, an agent-held Owner token, a dangling reference,
and the rules above) are in
[`tools/tests/test_check_security_inventory.py`](../tools/tests/test_check_security_inventory.py).

## Containment cases (S-02.1)

[`containment-cases.json`](containment-cases.json) is the versioned expected-denial matrix
of the job environment (plan leaf S-02.1). Each case names its category, the principal it
runs as, the exact non-destructive attempt, the outcome classes it expects, the
enforcement location that must produce that outcome (with references to profiles P-ids,
network-matrix edges and inventory assets, credentials or findings) and the permitted
operation that pairs with it as its positive control.

- `tools/guest.py containment-probe` (`task guest:containment-probe`) runs every case in a
  disposable provisioned guest. It reuses `admission-probe` and `job-access-probe`
  unchanged for the cases they already cover and runs the rest inside two further
  disposable conversation containers with generated canary workspaces. Per case it
  records the attempt, the principal, each observation, its classification, the control's
  result, the verdict and the runtime-configuration snapshot the case depends on.
- **Verdicts.** PASS: the expected outcome was observed and the positive control passed
  in the same run. FAIL: an attempt succeeded (a stop condition), a hardening control is
  missing or loosened, an observation is missing or unexpected, or a compensating case did
  not pass. UNKNOWN: the positive control did not pass, so the denial proves nothing. A
  denial is never PASS without a working control, and a missing control is never skipped.
- `--sensitivity` also runs the mutations below: each points a denial case at an
  operation the job may perform, and each must be classified a success (FAIL).
- [`tools/check_containment_cases.py`](../tools/check_containment_cases.py) (`task
  security:containment-check`) checks the catalogue: every category covered, every
  enforcement reference resolvable, every probe paired with an existing permitted control,
  every attempt non-destructive, no machine path, and the block below equal to its
  `--render` output.
