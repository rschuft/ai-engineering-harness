## Threat model

**Assets (what the lanes protect), by inventory id.**
1. Owner authority and credentials: `cred-gitea-owner-account`, `cred-gitea-admin`, `cred-uac-consent`, `cred-owner-github`, `cred-owner-provider-login`, the Owner's credential store and home (`host-credential-stores`, `host-owner-windows`).
2. Management: `cred-agent-server-session-key`, `cred-guest-ssh-key`, the dispatcher's standing bot tokens (`cred-gitea-bot-*`), `cred-llm-provider-key` and the inference broker's control listener, QMP, the integration store.
3. Privileged effect: `cred-executor-identity`, `cred-executor-target-secrets`, `store-effects`, the release-signing identity (unknown, 0007 point 3).
4. The git hosting trusted computing base: Gitea's HTTP listener and process, `app.ini` secrets (`SECRET_KEY` encrypts Actions secrets; the general token signing secret signs the runtime JWT), the SQLite state, protected branches and their rules, bot and runner identities, the Actions token ceilings, Actions secrets and variables (`gitea-server`, `repo-gitea-authorization`, `repo-gitea-policy`).
5. The integrity of the integration branch and of **CI evidence**: the run record (run id, job id, SHA, workflow and ref, runner identity, conclusion, log) and the status the merge gate consumes. This is the asset a hostile job most wants: a forged "passed".
6. The CI lane's own keys: the **registration token (standing in Gitea's database until reset)** and the runner's persistent token: whoever holds either can register or operate a runner that receives the validation jobs and reports whatever it likes.
7. The execution guest and its attempts (`td-guest-control`, `td-untrusted-engineering`, `td-review`): the CI lane must add no path into them.

**Adversary.** Untrusted proposal code: anything an agent (planner, builder, reviewer: `td-untrusted-engineering`, `td-review`) or any future pull-request author produces, at an exact revision: repository content, tests, build and dependency manifests with install hooks, `.gitea/workflows/*`, submodule and symlink tricks, and PR metadata that a workflow might interpolate. Its capabilities inside the validation lane: arbitrary code execution as the job user; reading the job's environment and filesystem; any network call the job's network allows; use of whatever tokens the runner put in the environment (the job token and, as expected, the runtime JWT); writing to the workspace and to anything mounted; exhausting CPU, memory, pids and disk; attempting a container escape (the residual the VM boundary contains); poisoning anything shared across jobs (caches, images, volumes) to influence later jobs; and influencing what the trusted lane reads (test output, report files).

**In scope** (decision 0010 point 1): agents and CI acting through their normal interfaces, and operators taking shortcuts. **Out of scope** (unchanged): a malicious process already running with the Owner's account privileges, an administrator, operating-system compromise; same-account host edges are disclosed, not prevented (0013 point 6).

**Attack paths considered, and the control that answers each** (the number recurs in sections 2 to 7).
- T1 Exfiltrate a credential from the job: none is present but the two tokens Gitea mints for the task (6.1 to 6.4, 5); both are bound to a repository that holds nothing the attacker wants, carry no permission there (5), and are unusable from the job (4).
- T2 Use the job token against Gitea (write a ref, post a status, read another repository, upload an artifact): the job has **no network path to Gitea** (4); the token's effective permission on the governance repository is **none on every unit** by configuration (5); other private repositories are unreachable by configuration (no `AllowedCrossRepoIDs`, no `CollaborativeOwnerIDs`); public repositories stay readable by Gitea's construction (residual 1).
- T3 Forge the required status for the proposal's SHA: statuses need write on Code, which no job token has (G7, 5); only the trusted lane's reporter identity posts the context the gate requires, and only after reading the run record it dispatched (8.1); a context string, scoped prefix included, is never evidence (8.2).
- T4 Make the job trivially "pass" by editing the workflow: the workflow that runs is the governance repository's, dispatched by the trusted lane from its protected default branch; proposal repositories have Actions disabled, so a proposal's own workflow files never execute anywhere (7).
- T5 Run on the runner host rather than in a container (`runs-on: host`): no `host` or `lxc` label exists (2.3).
- T6 Reach the engine: `docker_host: "-"`, no engine TCP endpoint, the container guard (2.3, P6).
- T7 Mount a host path or escalate the container (`volumes`, `--privileged`, capabilities, host namespaces): `valid_volumes: []`, `privileged: false`, `--cap-drop ALL`, `no-new-privileges`, a non-root user, pids/memory/cpu limits in `container.options` (2.3).
- T8 Fetch code or data from outside (`uses:`, package indexes, `git clone` of a URL): the job has no egress (egress guard, SLIRP `restrict=on`) and no resolver; the workflow uses no `uses:` (7.3).
- T9 Poison later jobs: `cache.enabled: false` (the runtime JWT's cache-write scope has nowhere to go); images are pre-loaded by digest and never pulled; per-job networks and `--rm` containers; the exchange mount is read-only; the CI guest is recreated at every policy or pin revision and after any failed containment probe (2.4).
- T10 Escape the container and subvert the runner: contained by the CI guest (a VM boundary, the blueprint's own requirement for privileged nested infrastructure): the guest holds no credential but the runner token, reaches the host only through the single guest-loopback forward to Gitea's runner RPC (3), and never the execution guest or the Owner host; a compromised runner can at most lie about its own tasks, which section 8's verifier bounds and section 11 discloses.
- T11 Impersonate the validation lane with the registration or runner token: the registration token is **reset immediately after each registration** so the value delivered to the guest is dead before any job runs (6.3); the runner token is root-owned in the CI guest; ephemeral registration where the guest is per-validation; the runner is deleted at destroy; the verifier checks the job's `runner_id` against the registered runner (6.5, 8.2).
- T12 Deny service (fork bombs, disk fill, endless jobs): per-container limits, `runner.timeout`, Gitea's `ZOMBIE_TASK_TIMEOUT` (10 m), `ENDLESS_TASK_TIMEOUT` (3 h) and `ABANDONED_JOB_TIMEOUT` (24 h), the scratch disk ceiling, `capacity: 1`.
- T13 Skip CI by commit message (`[skip ci]`): irrelevant to a dispatched workflow (the skip strings apply to push and pull-request events); the gate requires the context on the exact SHA, so a missing status blocks (Q-03.2).
- T14 Attack the trusted promotion lane from CI: no Actions job on the validation runner is ever a promotion step; the executor is reachable from no CI domain (matrix `nm-ci-privileged-effect`, `nm-runner-privileged-effect`, deny) (8).

## Considered options

**A. Where the runner and its jobs run.**
1. **The runner on the Owner host (beside Gitea), jobs in the execution guest's Moby over `DOCKER_HOST=ssh://`.** Rejected. The runner process parses and evaluates workflow files and runs act's expression engine; even with trusted workflows it is CI-lane code on the trusted host with the Owner's account reach; the guest's Moby would have to be reachable from the host as a Docker API (the `agent` login in the docker group, or a forwarded root socket), reopening P6 and S-01.3.x; and the inventory's `ci-runner-host` is "not the trusted management host" (matrix `nm-management-runner`).
2. **The runner inside the existing execution guest, jobs in its Moby.** Rejected. It mixes two untrusted domains behind one engine (shared images, volumes, daemon state; the Agent Server's session key is readable by the guest login), adds a service to a qualified guest (decision 0006: not without a defect), and still needs the same guest-to-host path as option 3, so it saves only a VM.
3. **A dedicated disposable CI guest of the strong tier** (the same provider, image, seed pattern, guards and lifecycle as the execution guest; act_runner and the pinned job image in place of the Agent Server), jobs as disposable containers in its own Moby. **Chosen.** It is the shape the blueprint, the inventory (`td-ci-runner-host`) and the matrix already plan; the VM boundary is what the blueprint requires behind privileged nested infrastructure; the CI lane adds no path into the execution guest. Cost: a second QEMU instance with its own, smaller ceilings (the profile's own caveat about two full instances), a runner provisioning step in the 0006 pattern, and a profile variant to qualify (Q-02.2.1, Q-02.2.2).
4. **No Gitea Actions: the dispatcher runs validation as a job in the execution guest's qualified container environment and posts the result.** Not chosen: the blueprint adopts Gitea Actions as the independent CI (SEC-04), the plan's Q-02 and Q-03 and the lineage model (`ciRunRef: gitea:actions/run/<id>`) rest on its run records, and a validation driven by the same Agent Server as the agent's own attempts is not a separate compute domain. **Recorded fallback** if act_runner cannot be pinned or constrained as section 2 requires.
5. A runner on another machine or on the LAN. Out of scope: Gitea is loopback-only and no record opens it.

**B. How the runner reaches Gitea (the item 0013 left open).**
1. `guestfwd` to 13300. Rejected: one chardev stream for the life of QEMU (F-03.3.2); a long-poll plus RPC and log streams cannot share it; a broker-before-guest ordering.
2. SLIRP `restrict=off` (the guest reaches the host alias `10.0.2.2`). Rejected: `restrict=on` is the qualified enforcement point; off, every host loopback service is reachable from the guest (0015 option 5; 0013 point 6 on firewall rules).
3. **An OpenSSH remote port forward held by the dispatcher over the existing loopback `hostfwd`, bound to the CI guest's own loopback: `ssh -N -R 127.0.0.1:13300:127.0.0.1:<target>`** (0015's mechanism, with the bind on `127.0.0.1` instead of docker0 so that only guest-level processes, never containers, can reach it). **Chosen.** Per-connection channels; created after boot and re-established at will; torn down with the session; `launch.argv` unchanged; `ROOT_URL = http://127.0.0.1:13300/` is literally correct inside the CI guest, so the runner registers with `--instance http://127.0.0.1:13300`, and the same URL inside a job container is the container's own loopback: dead by construction.
4. **Option 3 with a host-side loopback filtering proxy as the forward's target**, admitting only the runner RPC (section 3.5) and refusing every other path: the two artifact route families (which accept the runtime JWT and, for v3, the job token), the REST API, git smart HTTP and the web. **Recommended, Overseer's decision**: it is owned code of the 0015 "minimal broker" class (standard library plus the pinned `urllib3`), one more host listener (an Owner act under the 0015 precedent), and it reduces what a fully compromised CI guest can reach from Gitea's whole HTTP surface to five RPC methods and a ping. Without it, section 11 discloses the wider residual.

**C. How the validation job gets the repository content, and whether it reaches Gitea.**
1. **A mediated, read-only, task-token-authenticated git path from the job to Gitea** (a filtering proxy admitting `info/refs` and `git-upload-pack` of the task's repository, forwarded to docker0, one container-guard allow). Rejected for now: it is a refinement of 0013 point 7 (untrusted code would have a network path to Gitea), it would need a Code-read ceiling on the governance repository (section 5 sets none), it exposes Gitea's smart-HTTP handler, which spawns `git upload-pack`, to hostile clients, and it needs more owned code than option 2. **Recorded alternative**, also the only way to admit job-uploaded artifacts (G8).
2. **The trusted side stages the exact revision as a verified git bundle into the CI guest's exchange before it dispatches the run; the job clones from a read-only mount.** **Chosen.** It keeps 0013 point 7 intact (the job has no network path to Gitea at all), reuses observed mechanisms (`exchange push` over SFTP, the repository module's bundle writer and verifier, the read-only verifier token), and pins what the job validates to a SHA the dispatcher chose, independent of what Gitea serves at run time. Cost: the dispatcher stages before it dispatches; a job never fetches anything.
3. `pull_request_target` on the proposal repository with no secrets and no network. Rejected: the blueprint names the pattern as the one not to use for trusted contexts, and it would require Actions on the proposal repository (option D1's problem).

**D. Who defines and triggers the validation workflow.**
1. **Event-triggered runs of the proposal revision's own workflows** (`push` to `work/*`, `pull_request`). Rejected: the attacker defines the workflow; at Gitea's defaults a same-repository run (which every dispatcher-pushed proposal is) carries a **write** token on all units and every secret and variable (G4, G5); a ceiling and an empty secret set can neutralize the token, but the definition stays the attacker's, so no check it produces is evidence, every hostile workflow would execute on the runner (capacity, noise), and the context strings it emits are indistinguishable from legitimate ones (G7).
2. **The trusted lane dispatches a governance workflow**: the dispatcher triggers `workflow_dispatch` of the validation workflow held in a protected governance repository (blueprint `repo-gitea-policy`), **always with `ref` the governance repository's protected default branch**, with inputs `repository`, `sha`, `bundle_sha256`, and `return_run_details=true` so the run id is returned; **Actions stays disabled on every repository that receives proposals**, so proposal workflow files never run. **Chosen.** The run's definition is trusted, the token is bound to the governance repository under an all-none ceiling (G4, section 5), no secret exists to deliver (6.1), fork-versus-same-repository semantics stop mattering, and the required context on the proposal SHA is posted only by the trusted lane (section 8). The fallback if dispatch proves unusable at the pin is **a trusted push by the dispatcher to the governance repository** (a `dispatch/<sha>` branch whose commit carries the tracked workflow file and a `request.json`), which runs the same trusted definition.
3. **Required scoped workflows (G10)** as the central check. Not chosen for the validation lane: a scoped run executes in the consuming repository's context, so it requires Actions **enabled** on every proposal repository (admitting option D1's hostile runs), ties the token ceiling and the secret set to each consuming owner and repository, and its scoped-run marker is not exposed by the API, so a verifier could not distinguish it from a repository-local workflow that imitates the prefix. **Recorded, verified alternative for Q-03.1** (section 8.6).

**E. How the result reaches the merge gate.**
1. The Actions pseudo-user's own commit status. Insufficient alone: under option D2 it lands on the governance repository's commit, not the proposal SHA, and under G7 a context is forgeable by any holder of write on Code.
2. **The trusted lane's reporter identity posts the required context on the proposal SHA after reading the run record it dispatched** (run id from the dispatch response, event, path and ref, head SHA, trigger actor, job conclusion, runner id), and the verifier of SEC-02 re-reads the same record before any promotion. **Chosen.** "A status label alone does not prove trustworthy execution; verify exact run origin and commit."

## Decision

### 1. Two lanes, two compute domains
1. **The validation lane** executes untrusted proposal content at an exact revision. Its compute domain is the CI guest (`td-ci-runner-host`, contained) and the disposable job containers inside it (`td-untrusted-ci`, untrusted). It holds **no Owner, administrator, management, executor, release or signing credential and no Actions secret or variable**; its only credentials are the runner's persistent token (on the guest, never in a job) and the two tokens Gitea mints per task (in the job, inert and permissionless: section 5). Its only network path off the guest is the runner's `ci-control` forward (section 3). It produces evidence (the run record, the runner-streamed log, the job's conclusion) and nothing else: it merges nothing, promotes nothing, signs nothing, deploys nothing, and never posts the status the gate requires.
2. **The promotion lane** is trusted: the protected merge, the independent verification of the merged revision and its evidence, and the privileged effects that build, sign, activate or publish (section 8). It runs on the trusted side (`td-owner`, `td-management`, `td-privileged-effect`) under Owner authorization recorded as the blueprint and decisions 0007 and 0008 prescribe. **No step of it is a Gitea Actions job on the validation runner, and no Actions context of any kind ever holds a promotion credential.** Whether a release step is realized as an executor operation kind or as a separately registered trusted runner is Q-02.4's proposed decision, within 0007 point 3's invariants.
3. The two lanes share exactly one object: the exact revision (the SHA, and the bundle digest that carried it). The promotion lane consumes the validation lane's evidence by reading Gitea's run record; it never consumes a file the job wrote.

### 2. The CI runner host is a dedicated, disposable guest of the strong tier
1. **Placement.** The runner (act_runner, to be pinned at Q-02.2.1 as a new component resolution under decisions 0001 section 1 and 0005: the Linux amd64 release binary with its published checksum, and one job image pinned by digest and image id) runs inside a **CI guest**: an instance of a CI variant of `profiles/strong-windows-qemu-whpx` (same provider, accelerator, image, seed pattern, guards, lifecycle verbs and P1 to P12 contract), whose provisioning installs Moby, the runner and the job image by the 0006 pattern (host download of pinned artifacts, SFTP over the management channel, a seeded one-shot root step with copy-then-verify-then-install) and **does not install the Agent Server**. It runs **never on the Owner host and never inside the execution guest**.
2. **Ceilings.** The CI variant declares its own, smaller ceilings (Q-02.2.1 proposes them; a first proposal: 4 vCPU, 6 GiB, 20 GiB root, 40 GiB scratch) so that a CI guest beside the execution guest stays within the host's recorded headroom; the Owner confirms the footprint (section 10, C-3).
3. **The runner's configuration is declared in the profile variant and enforced by the checker** (Consequences): one label only, `aieh-validation:docker://<pinned image>`; no `host` or `lxc` label; `runner.envs` empty and no `env_file`; `runner.capacity: 1`; a declared `runner.timeout`; `cache.enabled: false`; `container.privileged: false`; `container.docker_host: "-"`; `container.valid_volumes: []`; `container.network` empty (one network per job, behind the guards, which already match `br-+`) and never `host`; `container.enable_ipv6: false`; `container.force_pull: false` and `force_rebuild: false` (images are loaded by digest at provisioning and never pulled); `container.options` exactly the declared list: the read-only exchange mount, `--cap-drop ALL`, `--security-opt no-new-privileges`, a non-root `--user`, `--pids-limit`, `--memory`, `--cpus`, `--ulimit core=0`, and nothing else. The runner runs as a dedicated guest service user (in the docker group, which makes it root-equivalent inside the CI guest and is why the guest, not the user, is the boundary); the `agent` login stays out of the docker group (P6).
4. **Lifetime.** Job containers are disposable (`--rm`, one network each). The CI guest is **recreated** at every policy or pin revision, after any job whose containment probes fail, when the runner is deleted, and at least at each unit boundary; between those it may be reused for successive jobs (`shared` mode) with a non-ephemeral runner that is deleted at destroy. The stricter alternative, **one guest per validation with an ephemeral runner** (G2: the runner record and its token die with the single task), is recorded with its cost (create, provision, register and destroy per run) for the Owner's choice (section 10, C-3).
5. **Guest-local secrets (P5).** The CI guest holds, labelled, its SSH host keys and the runner's persistent token (root-owned, outside every mount). The registration token passes through it once, in memory, at `register` (section 6.3). It never holds a bot token, the management key, `OH_SECRET_KEY`, a provider key or any Owner credential; the P5 needles gain the runner token's fingerprint and every S-01.3.2 credential fingerprint.

### 3. The runner's reach to Gitea, decided against 0013 point 7
1. **The runner process, not the job, is the only CI component with a network path to Gitea.** The runner is pinned upstream software operated by the harness in a contained domain; it is not untrusted code in 0013 point 7's sense, and 0013 point 7 stays exactly as written: untrusted code has no network path to Gitea.
2. **The path is a new profiles P7 endpoint class, `ci-control`**: "the CI runner's control channel to Gitea's runner RPC, reachable from the CI guest's own processes only, never from a job container". It is realized as a **dispatcher-held OpenSSH remote port forward inside the qualified management channel**, `ssh -N -R 127.0.0.1:13300:127.0.0.1:<target>` with `ExitOnForwardFailure=yes`, keepalives, the per-instance key and the profile's client options, where `<target>` is Gitea's 13300 or the filtering proxy's port (option B4, the Overseer's decision). The CI guest's sshd drop-in gains `AllowTcpForwarding remote`, `GatewayPorts clientspecified` and `PermitListen 127.0.0.1:13300` (no other bind). Because the bind is the guest's loopback, no container can reach it (a container's `127.0.0.1` is its own, and the container guard refuses every new connection from a bridge to the guest), so the egress guard's allowlist stays empty and no container-guard allow is added. The runner registers with `--instance http://127.0.0.1:13300`.
3. **Every such forward is an Owner act** (`op-guest-boundary-change`; the standing authorization's "no guest network ... or new host port"), requested by Q-02.2.2, the leaf that first needs the runner to receive a job, never by Q-02.1 or Q-02.2.1. The dispatcher records the forward session (pid, bind, target, instance) beside the launch record while it holds it; the forward exists only while a validation session is open; if it drops, the runner's next poll fails closed and the dispatcher re-establishes it idempotently.
4. **Matrix consequences** (Overseer, as matrix owner, at Q-02.2.1): `nm-runner-gitea` becomes an allow, status `decided`, class `ci-control`, credential `cred-runner-token`, owner act; `nm-ci-git-hosting` becomes a deny, status `decided`, by this record and 0013 point 7; new rows: the dispatcher to the CI guest over the management channel (`management`, `exchange`: the bundle staging), the dispatcher-as-reporter to Gitea (covered by the planned dispatcher-as-bot allow), the Gitea-administration command to Gitea (same-account, disclosed), Gitea to the runner stays a deny (the runner polls). `fd-ci-runner-unpinned` keeps its `unknown` kind until Q-02.2.1 pins the runner.
5. **The filtering proxy's allowlist (option B4), if adopted:** exactly `POST /api/actions/ping.v1.PingService/*` and `POST /api/actions/runner.v1.RunnerService/{Register, Declare, FetchTask, UpdateTask, UpdateLog}` (G2: the whole `/api/actions` mount), with `Register` admitted only while the dispatcher's provisioning window for that CI guest is open; **denied**: `/api/actions_pipeline/*` and `/twirp/github.actions.results.api.v1.ArtifactService/*` (G8: job-side artifact routes; the lane admits no artifact upload, and these routes accept the runtime JWT and the job token), `/api/v1/*`, git smart HTTP, the web and everything else. The runner needs nothing but the RPC; act_runner's cache server, which the runtime JWT's cache scope would authorize, is disabled and local to the runner host anyway.

### 4. The validation job reaches nothing; content arrives by staged bundle; evidence leaves through the runner
1. **A job has no network path to Gitea, to the host, to the execution guest, to a resolver or to the internet**: the egress guard (empty allowlist), the container guard, `icc` off and SLIRP `restrict=on`, all already qualified, plus the loopback-bound forward of section 3. `GITHUB_SERVER_URL`, `GITHUB_API_URL` and the runtime URLs inside a job name the container's own loopback.
2. **Content.** Before it dispatches a validation, the dispatcher (`management-dispatcher`; during bootstrap `tools/guest.py` under the Owner's account, 0013 point 1) writes the proposal revision as a git bundle through the repository module, verifies it (decision 0014 rows R5, R6), copies it into the CI guest's exchange (`exchange push`, bounded by the profile's `exchange.push` limits) and records the bundle's sha256. The job's first steps, defined by the governance workflow (section 7): check that the mounted bundle's sha256 equals the `bundle_sha256` input, `git bundle verify`, clone from the bundle, check out `sha`, and assert `git rev-parse HEAD` equals `sha`; only then do the repository's own quality commands run (Q-01.x discovers them). The exchange is mounted read-only; the clone lives in the job's own writable workspace volume, destroyed with the container.
3. **Evidence.** The runner streams the job log and reports the job's conclusion to Gitea's run record over the `ci-control` forward. The job uploads no artifact (G8: both artifact route families need a job-to-Gitea path, which does not exist, and the proxy denies them); a report the job writes is log content, treated as data. Admitting artifacts is option C1, a separate Owner act, deferred to Q-02.4's handoff contract.
4. The S-01.3.2 job-environment constraints transfer to CI jobs verbatim (`provisioning.agent_server.jobs.ci`): no engine socket or TCP endpoint, no management, Owner, admin or bot credential, no privileged mode, capability, device or host namespace, no host-path mount beyond the scoped workspace; the `job-access-probe` pattern (fingerprint scan, socket and address probes, root not obtainable) is re-run from inside a CI job at Q-02.2.2 and Q-02.3.2.

### 5. The job token rule: topology and configuration
1. **The validation lane grants the job token nothing, twice over.** By topology: the job cannot reach Gitea (section 4.1). By configuration: the token's effective permission on the governance repository is **none on every unit**, which is also exactly what a dispatched validation job needs (it clones from the bundle, posts nothing, uploads nothing, caches nothing). The trusted lane relies on nothing a job could do with it.
2. **The configured ceiling** (G4; applied at Q-02.3.1, read back by the live check of section 6.6):
   - the governance owner (an organization, section 7.1): `TokenPermissionMode: restricted`, `MaxTokenPermissions` none on all eight units, `AllowedCrossRepoIDs: []`;
   - the governance repository: `OverrideOwnerConfig: false` (the owner's ceiling governs), and, so that a later override changes nothing, its own `TokenPermissionMode: restricted` and `MaxTokenPermissions` none on all units; `CollaborativeOwnerIDs: []`;
   - every other repository on the instance: `CollaborativeOwnerIDs: []`; every owner: `AllowedCrossRepoIDs: []`;
   - the governance workflow: a top-level `permissions: {}` (the explicit empty mapping: none on every unit, G4) and no job-level `permissions:` block (checker).
   Effective: `min(none, none)` = none on the governance repository; none on every other private repository (restricted-read clamp, then no cross-repository grant); **read on every public repository of the instance**, which no ceiling removes (G4). Therefore **every repository on the host Gitea that the lane must not read is private**; the lane's rule is that no public repository exists on the instance, and the live check lists any that does as a disclosed read exposure (section 11, residual 1).
3. **`cred-ci-job-token`, restated** (inventory row): "Minted by Gitea per task (40 hex characters, salted hash; valid while the task is running or cancelling); delivered to the runner as `GITHUB_TOKEN` and `GITEA_TOKEN` and placed by the runner in the job environment; authenticates as the Actions pseudo-user bound to the task. Effective permission: none on every unit of the governance repository (restricted mode, all-none ceiling at owner and repository, `permissions: {}`); none on every other private repository (no `AllowedCrossRepoIDs`, no `CollaborativeOwnerIDs`); read on every public repository of the instance (irreducible; none exists by policy); accepted as a Bearer fallback by the v3 artifact route for its own task. Issuer `external:gitea-actions`, holder `ci-job`, manager `ci-runner-service`, lifetime one task. Reach from the validation job: none (no network path). Relied on: never." The role row `ci-job` loses `cap-ci-statuses-artifacts` (the job reports nothing; the runner streams logs and the trusted lane posts statuses) and keeps `op-ci-untrusted-job`, `cred-ci-job-token` and the new `cred-ci-runtime-token`; its denials are unchanged.
4. **`cred-ci-runtime-token`** (new inventory credential, authority `scoped`): "A JWT Gitea mints per task (`gitea_runtime_token` in the task context; HS256 with the instance's general token signing secret; scope `Actions.Results:<run>:<job>` plus cache write; valid from issue for 1 h plus `ENDLESS_TASK_TIMEOUT`, 4 h at the default). Accepted by the v3 and v4 artifact routes and by act_runner's own cache server. Whether act_runner places it in the job environment as `ACTIONS_RUNTIME_TOKEN` is an A1 fact to verify at Q-02.2.1; **the lane treats it as present in the job either way**: inert (no network path; the artifact routes are denied by the proxy; the cache server is disabled), never relied on, never recorded." Issuer `external:gitea-actions`, holder `ci-job`, manager `ci-runner-service`, lifetime one task plus the JWT's validity.
5. **Untrusted jobs never get a token that reaches anything**: if a later decision admits a mediated job-to-Gitea path (option C1), the admitted requests are read-only git fetches of the task's own repository under a Code-read ceiling, and the record that admits them refines 0013 point 7 and section 5.2 explicitly; nothing in this record does.
6. The "token maxima" the plan and the inventory presuppose **exist at the pin** (G4) and are set here to none; Q-02.3.1's realization is this section: the restricted mode and all-none ceiling at owner and repository, `permissions: {}`, no cross-repository grants, no public repository, the no-secrets rule and the no-path rule.

### 6. Secrets and credentials kept out of the validation lane
1. **No Actions secret or variable exists** at the governance repository, at its owner, at any other repository or owner of the instance, or instance-wide (G5 delivers every owner and repository secret to every task of a non-fork run and every variable, global ones included, to every task; an empty set is the only rule that keeps them out of jobs; a per-workflow `secrets:` discipline would not). Enforced by the live check of section 6.6.
2. **The runner host holds** only `cred-runner-token` (new inventory credential, authority `scoped`, holder and manager `ci-runner-service`, root-owned on the CI guest, outside every mount) and the guest's host keys. `runner.envs` and `env_file` are empty (checker).
3. **The registration token is a standing management-class secret inside Gitea's database until reset** (G2), and custody is designed around that: `cred-runner-registration` (authority `management`, issuer `gitea-site-admin`, storage "the active row for the governance-repository scope in Gitea's database; never a file, a record, a log or the Owner's credential store", lifetime "from reset to reset"). The procedure, performed by the **host-side Gitea-administration command** (the `gitea_roles.py` class, which holds the site-administrator credential; the dispatcher and the CI guest never do, S-01.2.1 ruling):
   1. **reset** the governance repository's registration token through Gitea's web settings route (`POST /{owner}/{repo}/settings/actions/runners/reset_registration_token`, under a site-administrator web session obtained by the F-06.1 sign-in flow with CSRF), which invalidates every older token for the scope and creates a fresh one;
   2. read the fresh token with the CLI (`gitea actions generate-runner-token --scope <org>/<repo>`, which returns the active token) into memory, never to a log or file;
   3. hand it to the dispatcher in memory for one delivery over the management channel to the CI guest's provisioning step, which runs `act_runner register` (the guest keeps only the runner token in `.runner`);
   4. **reset again** immediately after a successful registration, or after a failed delivery, so that the delivered value is dead before any job runs.
   Net exposure: the value is live between steps 1 and 4 (minutes), seen only by the administration command, the dispatcher's memory and the guest's `register` call, and a compromised CI guest later holds a dead registration token (T11). The registration scope is the governance repository, so even a live token could register a runner for that repository only. **Fallback** if the Overseer declines the web-route automation: the token stays active in Gitea between provisionings, is read by the administration command at each one, and is reset at policy revision or suspected exposure; disclosed as a standing management secret (section 11, residual 2).
4. **The dispatcher's standing bot tokens** never enter the CI guest or a job (0013 point 7; `fd-guest-login-name-and-key` pattern): the dispatcher stages and dispatches from the host.
5. **Revocation** (0007 point 5 rows): `cred-runner-token`: triggers suspected exposure, policy revision, Owner direction, and always at CI-guest destroy; revoker `gitea-site-admin` (delete the runner record through the administration command, `DELETE /repos/{owner}/{repo}/actions/runners/{id}`, owner-only; Gitea then refuses the token at its next poll; an ephemeral runner is deleted by Gitea when its task ends); receipt in the integration store by fingerprint. `cred-runner-registration`: reset by the administration command after every registration and on any trigger; the reset is the revocation. `cred-ci-job-token` and `cred-ci-runtime-token`: end with their task (Gitea); on suspected exposure the dispatcher cancels the run and recreates the CI guest. `cred-gitea-bot-ci` (section 8): as the other bot tokens, rotated by `gitea_roles.py rotate`.
6. **The live check** (`--gitea` mode) is a **site-administration verification performed by the host-side Gitea-administration command**, not by `check_ci_policy.py`, the dispatcher, the verifier or the guest: G9 shows that listing secrets and variables needs the repository owner or a site administrator and that user-level secrets have no list route at all, so the verifier's read-only grant could never do it and is not widened. Two oracles, both read-only: (a) **Gitea's database**, the authoritative instance-wide check: zero rows in the Actions secret and variable tables (every owner, every repository, the global scope), the governance owner's Actions configuration (restricted mode, all-none ceiling, no `AllowedCrossRepoIDs`), every repository's Actions unit configuration (unit enabled on the governance repository only; token mode and ceiling as declared; no `CollaborativeOwnerIDs`), and no public repository; read through a read-only connection to the SQLite file under the managed root (the lifecycle contract already reads this database for backups), schema names pinned to 28.3.0 and carried by `fd-gitea-version-docs`; (b) **the API as `aieh-site-admin`** (basic authentication, the `fixture` pattern), the cross-check: the repository and organization secret and variable listings (`reqOwner`), every repository's `has_actions`, the registration token's existence per scope (listing it is reading a secret: the check reports presence only, never the value), and the runner list. `[actions] ENABLED` and `DEFAULT_ACTIONS_URL` are read from `app.ini` as `verify` already does.

### 7. Workflow authority: the governance repository and the source of record
1. **The validation workflow's source of record is this repository**, tracked at `policy/ci/workflows/validation.yml` and checked mechanically (Consequences). **Its runtime home is a protected governance repository in Gitea** (blueprint `repo-gitea-policy`; a proposal: organization `aieh-governance`, repository `quality-workflows`, **private**, Actions unit **enabled**, the token configuration of section 5.2, every ref push-protected, `main` Owner-only merge, administrator override blocked): the dispatcher mirrors the tracked file there by the module's push as the bot identity that holds write on that repository, and the trusted lane records the commit and blob sha it dispatched.
2. **Actions is disabled on every repository that receives proposals** (the integration repository, the fixture, any planning repository): a proposal's `.gitea/workflows/*` never runs, and no scoped workflow runs there either (G10). The instance-wide `[actions] ENABLED` becomes true only to serve the governance repository (an Owner confirmation, section 10, C-1).

### 8. The trusted promotion lane

### 11. Threat model: what is prevented, what is disclosed
**Prevented (in scope):** a job reading any credential but its two permissionless task tokens (nothing else present; proved by fingerprint search); a job reaching Gitea, the host, the execution guest, a resolver or the internet (guards, `restrict=on`, loopback-bound forward); a job using either token (no path; an all-none ceiling; artifact routes denied by the proxy; cache disabled); a proposal's workflow executing (Actions disabled where proposals land, scoped workflows included); a job defining what runs (the governance workflow is dispatched from a protected ref); a job forging the gate's status (no path; no write on Code; the reporter alone posts; the verifier re-reads the run record); a job mounting a host path, escalating the container or reaching the engine (`valid_volumes: []`, `privileged: false`, `docker_host: "-"`, `--cap-drop ALL`, `no-new-privileges`, the container guard); cross-job poisoning (`cache.enabled: false`, no pulls, `--rm`, per-job networks, read-only exchange, guest recreation); a stolen registration token registering a rogue runner (reset after every registration); a CI component reaching the executor or the effects store (no path; typed operations only).

**Disclosed residuals:**
1. The job token can read **every public repository of the instance**, whatever the ceiling (G4: the Actions user's individual read is added after clamping). The lane's policy is that no public repository exists on the host Gitea; the live check reports any that does. The token is in any case unusable from the job (no path).
2. The registration token is a standing secret in Gitea's database between the reset steps of section 6.3; with the web-route automation it is live for minutes per provisioning; without it (the fallback) it stands between provisionings and is reset on revision or exposure. Same-account processes can read it through the CLI at any time (0013 point 6).
3. A container escape inside the CI guest reaches the runner, its token and the guest-loopback forward, hence Gitea's runner RPC (with the proxy of option B4) or Gitea's whole HTTP listener, the artifact routes and the REST API included (without it), with the runner's token and any in-flight task tokens; it reaches nothing else (no credential, no path to the Owner host, the execution guest, the executor or the internet). Its reward is a forged conclusion for its own tasks, bounded by the verifier (8.1, 8.3) and by the CI guest's recreation; the exposure of Gitea's surface is the reason the proxy is recommended.
4. The commit-status gate is forgeable by any holder of write on Code (G7); all such holders are trusted-side custodians, and the promotion lane trusts the run record, not the status.
5. Same-account host processes (the bootstrap agent sessions included) can read every dispatcher-held token, the site-administrator credential, the registration token (CLI) and operate the forward (0013 point 6; `fd-bootstrap-shared-identity`): disclosed, not prevented.
6. Job-uploaded artifacts are not available; evidence is the runner-streamed log and the conclusion. Reports as artifacts need option C1 (Q-02.4).
7. A proposal that does not pass through the dispatcher (an external fork PR, should Gitea ever be reachable beyond loopback) gets no staged bundle and no dispatched validation: it fails closed and is out of scope until a record opens Gitea.
8. The runtime JWT's presence in the job environment is assumed, not verified (A1); its validity (up to 4 h) outlives the task, which matters only if a path to the artifact routes is ever admitted.
9. The Gitea facts G1 to G10 are verified at source, not live; the act_runner facts A1 are the Architect's recollection. A failed live verification changes a mechanism, not a lane.

> The detection and correction of the incorrect pinned Gitea assumptions is appropriate. Retain
> source-verified security semantics rather than assumptions.
>
> In particular, do not qualify a live CI runner while its registration token remains reusable and an
