## The corpus and the suite

- [`tests/repository_corpus.py`](../integrations/repository/tests/repository_corpus.py) builds
  the probe's corpus with git (fixed identity and dates; root `a b ü`) and records git's
  answers: `repo one` (loose; spaces and non-ASCII in paths and a directory; `eol=crlf`, binary,
  CRLF-blob and executable files; `export-ignore`; annotated, lightweight, nested, tree and blob
  tags; a merge; remote-tracking, top-level and non-ASCII references; reflogs; `FETCH_HEAD`,
  `ORIG_HEAD`; ambiguous abbreviations; plumbing commits with links, a gitlink and an unsafe
  name; a work tree with every kind of change and a nested repository), `packed copy`
  (`repack -a -d -k`, `pack-refs --all`, no loose object left), `bare.git`, `linked tree`
  (`--relative-paths`), `separate work` and `separate.git` (relative gitfile), `sha256 repo`,
  `long.git` (a 295-character path), `id mismatch`, `corrupt zlib`, `corrupt pack`,
  `conflicted` and `not a repo`. Recording takes about 10 s.
- The tree is committed as `repository-corpus-tree.json.gz` (33,729 bytes; 407 files, 219 as
  text and 188 as base64, git's sample hooks left out; no machine path, checked file by file,
  zlib objects decompressed). A tar was the first form; the publication gate refused it as
  `binary-not-allowlisted`, so the tree is gzipped JSON, which the gate inspects. The
  expectations (`repository-corpus.json`) carry the tree's sha256 (checked).
- The suite extracts the tree once per process (one `mkdtemp`) and only reads it. Recorded half:
  35 tests (`DulwichPresent`, `MissingDulwich`, `Grammar`, `RecordedExpectations`, `Export`,
  `Integrity`, `ConfigPolicy`, `Bundles`, `NoProcess`). Git-oracle half: 8 tests; at test time
  git is asked the commit forms through one `cat-file --batch-check` per repository (restarted
  after a name git dies on) instead of 356 one-shot launches, every live answer must equal the
  recorded `rev-parse --verify` one, and a one-shot `rev-parse --verify` sample (the proof's
  forms and others) equals the batch; bundles the module writes pass `git bundle verify` and
  `list-heads`, and carry git's own bundle's header.
- **Without Dulwich** (`python -I -B -S`, the system interpreter): the suite **fails**,
  15 failures and 74 errors, none skipped, each naming `REPOSITORY_NEEDS_DULWICH: Dulwich is
  not importable by …python.exe (No module named 'dulwich'); run task tools:install … and rerun
  with the interpreter it prints (… tools_install.py --python)`.

## Candidate decision-0014 notes

For the Overseer; nothing here is decided by this leaf beyond the README's local mechanics.

- **N-1 (the date fallback).** When a name holding a numeric `@{N}` does not resolve otherwise,
  git rereads the text after its last `@{` as a date (approxidate), so its answer depends on the
  clock: `main@{0}:README.md`, `main@{1}^{tree}`, `main@{1}x`, `main@{3}~1`, `@{1}^{blob}`,
  `HEAD@{0}:` and `side@{0}~5` as commits, and `@{1}^{blob}`, `main@{1}^{tag}`,
  `HEAD@{0}^{blob}` as names, all resolved by git to commits (recorded in
  `fallback_commits`/`fallback_names`). The module refuses them with `REVISION_INVALID` (the
  `@{<date>}` gap), but at the point git would read the date, after a failed resolution, not
  "before any repository access" as 0014 section 2 says of gaps: the shape is only known then.
- **N-2 (`host` policy, G12).** 0014 section 5 defines `host` as "the configuration git would
  read on that host, located as Dulwich's default backends locate them". On this host the two
  differ under Git Bash's `PATH`: Dulwich locates `C:\Program Files\Git\mingw64\etc\gitconfig`
  (absent) and so reads no system configuration, while git reads
  `C:\Program Files\Git\etc\gitconfig` (`core.autocrlf=true`); under PowerShell both read the
  latter. The module implements the "located as Dulwich locates them" clause and lists what it
  read. F-10.4's snapshots of the Owner's checkout use `host`: a decision is needed before then.
- **N-3 (parity differences 0014 does not list).** Replace references (`refs/replace/`) are not
  applied (git applies them by default). Dulwich 1.2.21 reads no user or system attributes file
  (`core.attributesFile`, `$XDG_CONFIG_HOME/git/attributes`), so `status` under `host` can
  differ where such files convert a path. Reftable repositories are refused (`GIT_FAILED`): the
  module reads references from files, because Dulwich's reference container refuses names git
  reads.
- **N-4 (status needs a process for filters).** A path git would pass through a configured
  filter driver (clean or process, such as Git LFS, which this host's system configuration
  defines) or a `working-tree-encoding` is refused with `FILTER_UNSUPPORTED`: answering as git
  would need a process (or an encoding conversion the module does not run). Not in the G-list.
- **N-5 (0014 section 3, G9).** "Dulwich verifies the object id on read" holds for Dulwich's
  parsing path, not for `object_store.get_raw`, which returned another object's content for the
  id-mismatch fixture. The module verifies every object it reads against its id.
- **N-6 (0014's enumeration).** Forms git resolves that section 2 does not list (describe
  output `<x>-<n>-g<hex>`, `^{object}`, `ORIG_HEAD`/`FETCH_HEAD`/`MERGE_HEAD`,
  `main-worktree/HEAD`, any valid reference name under the git directory, `@@{N}`) are
  implemented as preserved forms. Two refusals are slightly broader than git's behaviour: a
  revision part holding `..` is refused even where `cat-file` would resolve a describe-shaped
  name, and the empty `@{}` is refused as a date form.

## Findings

- **F-1 (introduced-by `3272ba8`; fixed by `3aa5ef3`).** The corpus had non-ASCII file names but
  no non-ASCII directory, which proof clause 5 names. Commit A now holds
  `openspec/changes/ünï çhange/` (with `spécs/s péc.md`); re-recorded.
- **F-2 (introduced-by `622bd75`; fixed by `3aa5ef3`).** A read failing inside a pack raised
  `GIT_FAILED` within the `except` block; the error's context kept Dulwich's buffer into the
  pack, so `close()` could not release it and the pack and index stayed open (a temporary corpus
  then failed to be removed at exit, WinError 32). Errors are now raised after the failing
  call's frames are released, `close()` retries once after a collection, and `Integrity` checks
  that nothing stays open. Two temporary directories left by the runs before the fix remain in
  `%TEMP%` (`aieh-repo-corpus-9o7tj36r`, `aieh-repo-corpus-_ifrtu9s`): removing them was refused
  by this session's permission classifier; they hold only the synthetic corpus.
- **F-3 (exposed-by `cabc027`, the interpreter switch of ruling 2).** `test:budget` from
  PowerShell exceeds the kept wall budgets of planning (15.93 s against 15.73 s) and lineage
  (23.67 s against 23.53 s). The committed walls were measured from Git Bash, where these
  git-heavy suites run about 25% faster (no `cmd\git.exe` launcher), and the tools interpreter
  adds 0.2 to 0.3 s to each; under the plain interpreter they passed by the same margin (15.5,
  23.2 s). From Git Bash: PASS. Not loosened (ruling 4); whether the wall budgets belong to one
  shell is the Overseer's call.
- **F-4 (exposed-by; projection).** Serial `task test` from PowerShell: 159.0 s, above the F-09
  expectation of 150 s; before this leaf the eight existing suites took 150.0 and 149.3 s from
  PowerShell under the plain interpreter (A/B). From Git Bash: 145.0 s. No other suite was
  optimized (ruling 4).
- **F-5 (unrelated-but-detected).** `tools/test_profile.py` labels a git launch whose `-C` path
  holds a space by a fragment of that path (`git b`); the attribution by file is right.
- **F-6 (unrelated-but-detected, upstream).** Dulwich 1.2.21 behaviours the module works around:
  `get_raw` does not verify a loose object's id (N-5); `read_reflog` fails on a line without a
  message (git writes one for `worktree add`); the reference container refuses `refs/<one
  component>`, `ORIG_HEAD` and `FETCH_HEAD`; `create_bundle_from_repo` records an annotated
  tag's peeled commit instead of the tag; `get_win_system_paths` under Git Bash (N-2).
