## 2. Slice 3 part two: discovery and the proposed family pin

`integrations/inference/inference_qualification.py`:

- **`discover`** (`<synthetic key> | ... discover --provider ID --out FILE`): the qualification launcher in its
  discovery mode. It refuses exactly as `broker` does, through the same `launch`, and before the key is read also
  unless `--out` is a new file outside the checkout (`PROPOSAL_OUT_REFUSED`, the harness's one checkout comparison,
  section 6) and each keyed family's upstream is an IPv4 loopback literal (`FAKE_ADDRESS_REFUSED`) on which it binds
  that family's fake upstream itself (`DISCOVERY_PORT_TAKEN`). At the broker's stop it reads that run's audit file (the
  name from the broker's status) and writes the proposal with a `discovery` member: the provider, the keyed families,
  the provider key's fingerprint and, per family, what the fake upstream received (requests per route and answer,
  whether every credential was the synthetic key's fingerprint, and the admitted bodies' key paths). A family keyed to
  another provider id is not bound. A key refused after the bind leaves no audit and no proposal and frees the port; a
  write that fails after the run is `PROPOSAL_WRITE_FAILED`, exit 1, no traceback.
- **`propose-pin`** (`--audit FILE --out FILE [--attempt-id UUID]`) and `propose_pin`: the reader. The proposal
  (`aieh-inference-family-pin-proposal/1`, `status` `proposed`, `applied` false) gives per family the exact routes and
  the exact model names (the secondary model included) of the requests that presented a grant, with their answer
  codes, query parameter names and per-model routes; `declared` and `compared`; requests without a grant apart
  (`unattributed`); the grants (`attempts`). Only strings inside the audit's grammars are carried (no wildcard;
  anything else `READER_DROPPED`); a proposal holding the synthetic key's prefix is not written. It never writes
  `families.json` or `config.yml`: the routes are for the Owner's approval (6b), the model identifiers for the
  engineering manager's `select-models` record (decision 0018 point 3).
- **Flags:** `MODEL_NOT_TOP_LEVEL` (F7), `MODEL_UNRECORDED`, `PATH_UNRECORDED`, `QUERY_NAMES_UNRECORDED`,
  `QUERY_OBSERVED` (the declarations hold `refuse` or `pass` only), `ROUTE_NOT_DECLARABLE`, `UNATTRIBUTED_REQUESTS`,
  `AUDIT_LINES_WITHHELD`, `AUDIT_LINES_UNREADABLE`, `BROKER_UNRECORDED`, `READER_DROPPED`, `NO_GRANT_REQUESTS`, and
  from a discovery run's key paths `MODEL_KEY_ELSEWHERE`, `KEY_PATHS_TRUNCATED`, `KEY_NAMES_UNRECORDED`. `complete` is
  false when a value went unrecorded, unread or withheld, the key paths were truncated or held an unrecorded name, a
  request presented no grant, or no grant's request was seen; `MODEL_KEY_ELSEWHERE` is a suitability flag and does not
  affect it.

## 3. F7, option (b): the admitted bodies' key paths

Only under `discover` (a `FakeUpstream(..., key_paths=True)`; the `fake-upstream` command's records unchanged), each
admitted request records `body_key_paths(body)`: names only, never a value; object keys joined by `.`, arrays as `[]`
(`messages[].content`); a key outside `[A-Za-z0-9_$@-][A-Za-z0-9_$@:-]{0,31}` or holding the token prefix as
`<unrecorded>`, counted. Key names can carry data: under the open maps `metadata`, `properties`, `input_schema`,
`parameters`, `definitions`, `$defs` and any key ending in `_metadata`, and below them, a name is recorded only when it
contains `model`, else as `<map>` (so `metadata.fallback_model` is still seen). Bounds: 256 paths per request and per
route, 32 levels, 32 MiB of body; beyond them `truncated`. `MODEL_KEY_ELSEWHERE` names each path other than the
top-level `model` whose last segment contains `model` (any case), never a value. Not shown, and said so in the
proposal's `not_shown`: a model under a key without `model` in its name; a model elsewhere in a refused request
(refused requests never reach the fake upstream); everything when `propose-pin` reads an audit file alone.

## 4. Slice 4: the real-key containment search

`integrations/inference/inference_real_key_search.py` (`search --owner-act ACT --expect-fingerprint FP --surface
...`): after every argument is checked, the key is read once from the entry `AIEH model provider` through the broker's
own credential factory (`credentials.select_provider`), never standard input, an argument or the environment; refused
by fingerprint (`FINGERPRINT_MISMATCH`, worded for the credential entry's key), an absent or malformed entry
(`KEY_ENTRY_ABSENT`) or a failing provider (`KEY_PROVIDER_FAILED`, its error type only), none repeating what was read.
It is held in memory and searched by `inference_key_search.run` (the same forms, views, surfaces and positive controls
planted by the standard library's encoders; for a key without the synthetic prefix the body is the whole key). The
report (`aieh-inference-real-key-search/1`) adds the entry, the provider's name and the act, is searched for the key
before it is printed and withheld if it holds one. `--owner-act` is a label naming the act: its grammar is checked,
never a record. **Its live use is covered only by the Owner's act A1.** It was tested with fakes only (a fake
credential provider holding a synthetic key, and a key of a provider key's shape made at run time) and has never read
a real entry. `inference_key_search.py` itself stays independent of the broker; its shared mismatch wording ("the piped
key") is unchanged (an existing assertion holds it; the engineering manager accepted that).
