## Lock process

The pinned uv 0.13.7 Windows archive was downloaded from its GitHub release and its sha256
checked against `components.lock.json` `tools` (`0cdc5b38…cec46e021`, equal) before use. In
`composition/lock`, with `UV_NO_CONFIG=1`, `UV_PYTHON_DOWNLOADS=never` and an empty
`UV_CACHE_DIR`:

```
uv pip compile python/tools-requirements.in --python-version 3.12 --universal --no-build --generate-hashes --no-header --no-annotate -o python/tools-requirements.txt
uv pip compile python/dev-requirements.in --python-version 3.12 --universal --no-build --generate-hashes --no-header --no-annotate -o python/dev-requirements.txt
```

- `tools-requirements.in` (new): `dulwich==1.2.21`, `pyyaml==6.0.3`, `urllib3==2.8.0`.
  `dev-requirements.in` gained `dulwich==1.2.21` and `urllib3==2.8.0`.
- Resolved sets: tools 3 pins (dulwich 64 hashes, pyyaml 73, urllib3 2); dev 11 pins. On
  CPython 3.12 Dulwich requires `urllib3>=2.2.2` only (`typing_extensions` only below 3.12), so
  **no transitive dependency beyond urllib3** and no non-wheel dependency.
- The PyYAML block of the tools lock is byte-identical to the F-07.1 one (73 hashes, same
  order). The dev lock differs from the previous one only by the two added blocks.
- A second run of both commands, in the checkout with a fresh empty cache, left both files
  unchanged (`tools-requirements.txt` sha256 `442f4405…de8bd`, `dev-requirements.txt`
  `49bfdffb…8c7fd`).

## The basic tier stays standard-library only and offline

A scratch probe ran each check as `python -I -S -B -X utf8 <probe> <repo> <script> [args]`.
It asserts `-I` and `-S` are in effect and that no `site-packages` directory is on `sys.path`.
An audit hook refuses (raises on) `socket.__new__`, `connect`, `bind`, `getaddrinfo`,
`gethostbyname`, `gethostbyaddr`, `getnameinfo`, `sendto`, `urllib.Request` and
`http.client.connect`, and counts each attempt. After the script it classifies every module in
`sys.modules` as standard library (built in, or a file under the interpreter's stdlib or DLLs
directory), repository, or other. It passes only when the script exits 0, no network attempt
was made and no module is "other".

| Check | Exit | Modules (stdlib / repository / other) | Network attempts | Probe |
|---|---|---|---|---|
| `tools/check_prereqs.py --tier basic` | 0 | 99 / 0 / 0 | 0 | PASS |
| `tools/verify_seed.py` | 0 (PASS, 164) | 97 / 0 / 0 | 0 | PASS |
| `tools/verify_seed.py --baseline seed` | 0 (PASS, 136) | 97 / 0 / 0 | 0 | PASS |
| `tools/publication_gate.py verify` | 0 | 167 / 0 / 0 | 0 | PASS |
| `tools/publication_gate.py pre-commit` (this leaf's 11 staged files) | 0 | 168 / 0 / 0 | 0 | PASS |

The first four ran from Git Bash and again from PowerShell with the same results. The
`pre-commit` row ran from Git Bash. Positive controls: a script that connects to pypi.org was
refused at `socket.getaddrinfo` and the probe FAILED. A script that imports `yaml` got
`ImportError` under `-S` (the system interpreter has PyYAML in its own site-packages, so `-S` is
what keeps it out), and its module loaded by path from outside the stdlib and the repository
was classified "other", so the probe FAILED. The publication gate's hooks and the
`prereqs`, `verify`, `verify:baseline`, `hooks:*` and `scan:history` targets keep the plain
`PYTHON`. A contract test checks this (`RequiredTargets`).

## Findings

- **F-1 (introduced-by `e146063`; not repaired, outside the authorized paths).** The
  docstring of `integrations/paths/tools_install.py` and three rows of
  `integrations/paths/README.md` still describe the tools set as PyYAML only and the dev set as
  pytest, pytest-xdist and PyYAML. The asset-record example there shows only the PyYAML wheel.
  The dispatch allowed `integrations/paths/` only if `tools_install` needed a code change, and
  it did not. Wording only; carried to the Overseer.
- **F-2 (exposed-by; forward obligation for F-10.2).** `test:profile`, `test:budget` and
  `hooks:verify` (whose test 7 reruns the whole tool suite) still run under the plain
  `PYTHON`, by design of this leaf's scope. Today their counters and outcomes equal those under
  the tools interpreter (shown above). Once F-10.2 adds Dulwich-dependent tests, which fail with
  `REPOSITORY_NEEDS_DULWICH` without Dulwich, these targets need the tools interpreter too.
  The per-suite targets (`planning:test` and the others) also use the plain `PYTHON` when run
  alone; `test` passes them the tools interpreter.
- **F-3 (unrelated-but-detected).** `docs/development.md` said `setup` "took about four
  minutes". The paragraph was rewritten in this leaf with the observed 156 s.
