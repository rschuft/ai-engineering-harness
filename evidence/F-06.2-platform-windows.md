## 9. Findings

1. **introduced-by `e17ac2b`, fixed forward in `5e8b031`.** `security/inventory.json`
   `fd-outer-server-local-recovery` said the outer Agent Server creates the stored `working_dir` and
   runs `git init` "before any lease check". At OpenHands v1.60.1 only the module imports and the
   registrations precede the lease claim; the directory and `git init` follow it, and the claim
   succeeds in Docker mode because the start-up cleanup has removed the containers
   ([OA-03](OA-03-openhands-resume-report.md) section 1.5). The suggested remedy "hydrate only after a
   lease check" was replaced by skipping or confining the recovery. Only `detail` changed.
   **Not fixed (outside this leaf's paths):** `security/README.md` repeats the old text verbatim in its
   `fd-outer-server-local-recovery` bullet; it needs the same correction.
2. **introduced-by `8a87d7d`, fixed forward in `05130af`.** The new composition tests built a fresh
   managed root per test, which put the gitea suite at a 3.46 s median against its 3.25 s limit. One
   root per module, reset per test, brought it to 3.08-3.1 s. The suite's wall headroom was already
   small at `6ab2cbc` (3.04 s against the 2.5 s budget's 3.25 s limit): the next gitea test of any cost
   will need a wall re-proposal, which is an Overseer decision.
3. **Scope, for the Overseer.** Plan leaf F-06.6 names "the upgrade, recover and uninstall verbs and
   the aieh-service-transition/1 record" as its artifact. This leaf implemented them to the design, as
   the dispatch directed, with fixture-only tests. What remains for F-06.6 is its proof: the rehearsal
   on a disposable instance (a real upgrade needs a second pinned version), the reboot or sign-out
   behaviour, and the egress-proxy inspection.
4. **Semantics chosen within the design, for review.**
   - `uninstall` on Windows empties `ephemeral/tmp/gitea/` only: the harness registers nothing with
     the system, so nothing else exists to remove, and `up` works again afterwards.
   - The upgrade backups (`gitea.db`, `app.ini`) are in `persistent/gitea/backups/<transition>/`, in the
     same custody as `app.ini` (class E).
   - `retire` is realized for the role credentials only and keeps the bot account. The human
     accounts' `rotate` is `finalize-credentials` (temporary to final); rotating a final human
     password again has no realization yet (it needs a pending-entry design under I3).
   - The product's I7 scan covers what each act shows. The managed-root and checkout scans after a
     credential act remain those of `finalize-credentials`; `identities` and the role acts scan their
     output only.
   - The token-shape check fails closed: a message that happened to hold a 40-hex git object id
     would be withheld as `EXPOSURE_FOUND`.
5. **Observation.** The live instance's records predate F-06.2 (run record `aieh-gitea-run/1`, no
   `platform.asset_key`); both are accepted, and the next `up` writes `aieh-service-run/1`.
6. **unrelated-but-detected.** From PowerShell only, the repository suite's three-run median (7.78 s)
   is above its wall limit (7.67 s); Git Bash, which gates the walls, measures 5.9 s. This leaf does
   not touch that suite; F-10.5 measured the same from PowerShell (Git for Windows' `cmd` launcher).
