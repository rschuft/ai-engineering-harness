## 1. The driver (slice 5)

`tools/guest.py acp-qualification` (`acp_qualification_run`), PREPARED, NOT RUN:

```
<tools python> -I -B integrations/inference/inference_control.py issue \
    --conversation-id a0333c00-0000-4000-8000-0000000ac0d1 --family anthropic-messages --model <M> ... \
  | python -I -B tools/guest.py acp-qualification --profile <dir> --state-dir <dir> --name <name> \
      --attempt-token-stdin --prompt single|delegated --acp-model <M> \
      [--key-search off|synthetic|real] [--provider-key-fingerprint sha256:<hex16>] [--real-key-act <act>] [--out <file>]
```

On one running guest created with `create --provision --inference`, the forward session held, it runs thirteen
steps in this order, each judged PASS, FAIL or UNKNOWN by `ACP_QUALIFICATION_RULE` (fixed in the code before any
run and copied into every record):

| Step | What it does | Built from |
|---|---|---|
| (1) | Preconditions: the forward held; the piped token's grant live, bound to the reserved conversation, of the family `anthropic-messages`, which is ready; the named model in the grant and in the family's allowlist; the key-search mode matching the broker's provider key; no outer conversation and no conversation container | the broker's control listener (`BrokerAccess`), `ForwardControl`, the root facts |
| (2) | The pinned qualification create built and admitted (`acp_qualification.build_create`, which runs `check_create`), sent through the dispatcher's transport (`guest_transport.GuestTransport` over `GuestApi`), then: 2xx, one container of the declared shape (`container_problems`), the outer server listing exactly this conversation, the answer's `acp_server` `claude-code` where it names one | slice 2; E-01.3.3's transport |
| (3) | The sets before the turn: container ids (root facts), outer conversations (`GET /api/conversations/search`), the inner server's conversations with their parents (a script in the container, below) | slice 1's `sets_verdict` input |
| (4) | The fixed prompt, `POST /api/conversations/{id}/events` with `run: true` | `ACP_QUALIFICATION_PROMPTS` |
| (5) | While the turn runs: slice 1's container view (`collect container` sent as the file itself), its new connection view, and the guest-root view | `conversation_containment.py` |
| (6) | The job contract in the qualification conversation (D-6): `JOB_ENV_PROBE` with the token's admitted name, `job_env_verdict` | section 2 |
| (7) | The turn ends `finished` within `acp_prompt_timeout`'s default and a margin (1920 s), polled with `wait_until` | the conversation's state |
| (8) | After the turn: the container view (the adapter no longer required), the connections, the guest-root view and `sets_verdict` (no new container, no new outer conversation, every new inner conversation a child of this one), the container guard's refusal counters before and after (recorded) | slice 1 |
| (9) | The events, every page (`events/search`, at most 50 pages), and `agent_final_response` (its size and sha256 only): the delegation mechanisms (a) to (d) of the slice plan section 2.4 | `acp_delegation` |
| (10) | The broker admitted at least one request of the grant (the base URL honoured, R6) | the grant's counters |
| (11) | The provider key search: inspect's P5 search of the guest and the instance files (`inspect` with the key), and every Agent Server answer and container output of this run, held in memory, with the key search's positive controls | S-03.2 slice 5's `inference_key_search.Search` |
| (12) | The token revoked at attempt end (decision 0015 section 3.3) | the control listener |
| (13) | Teardown: the conversation deleted, its container gone, the outer server empty | the transport, the root facts |

The delegation mechanisms, as the record distinguishes them: (a) the provider's own tools and sub-agents, from the
ACP tool-call events (their count and titles) and the processes under the adapter during and after the turn; (b) an
ACP session fork, which runs inside the adapter process and is not separable from (a) by observation: the record
shows that the driver called no `ask_agent`, `fork` or `children` route, and a call of one fails step (9); (c) the
inner server's children route, from the new inner conversations whose parent is this one (classified, not failed);
(d) OpenHands' `start_child_conversation` tool, which an ACP agent does not receive: an event naming it as a tool
fails step (9).

**STOP conditions** (FAIL; later steps are skipped, while the key search, the revocation and the teardown still run):
a process outside the container's lineage (entered from outside, not a descendant of the inner server once that is
identified, or an escaped child in the guest-root view); an outer-server conversation that was not expected (at
create or after the turn); an `npx` or `npm` process; a credential found in a recorded surface (the attempt token or
the management key echoed in any Agent Server answer, a provider-key shaped value in a process environment, the
provider key found by the search); a connection that reached any destination other than the broker's inference
endpoint.

**Secrets.** The token arrives on standard input only and every API call is sealed with it (`GuestApi`'s sealed
form: the requests and the token in the script's text on ssh's standard input; the token redacted in the guest and
counted); the record carries its fingerprint and the redaction counts, the transport's call list carries each
body's sha256, never a body. The key search's key is held in memory; a record that would hold the key in any form
is not written (`SECRET`). **The driver never reads a real provider key by default:** `--key-search` is `off` by
default (step 11 UNKNOWN); `synthetic` takes S-03.2's synthetic key from the next line of standard input (its shape
and the broker's fingerprint checked); `real` is refused without `--real-key-act` naming the Owner's act, and even
then the key is read through the credential provider (`read_real_provider_key`: the entry the broker reads,
`credentials.select_provider`, checked against the running broker's provider-key fingerprint) only inside step (11),
and not at all when the preconditions failed.

**The inner server's conversations** are read inside the container by `ACP_INNER_CONVERSATIONS`, with the
conversation's own key read there from `/proc/1/environ`, as `job-access-probe`'s route sweep already does (the
exposure class S-01.3.1 recorded); the key never leaves the container, its occurrences in the answers are counted and
removed, and only ids and parent ids are printed.

**Slice 1's connection view** (`conversation_containment.py`): `collect container` now also lists the container's
other TCP sockets (local and remote address and port, the state's kernel name, the owning pids; no inode, no
payload), and `network_verdict(snapshot, endpoint=)` fails on a connection whose peer answered anywhere but the
inference endpoint, loopback or inbound to the inner server (`other_reached`, the stop), records a connect still in
`SYN_SENT` as `attempted`, and fails without a stop on a `CLOSE` or unknown state or an unread table.

## 3. Findings

- **F-6 (detected, not changed; a boundary for the Overseer): the guest-root vantage has no channel.** Slice 1's
  `collect host --pid` must run as the guest's root (the PID namespace link and `/proc/<pid>/exe` of the server
  user's processes need it). On a guest created with `--inference` the driver's channels are the `agent` login
  (`Ssh`, `GuestApi`, `exec`), the bash route inside the container and the root facts reporter, which runs a fixed
  script (docker inspect, listeners, storage, counters; no process inventory); the `--drill` helper is refused with
  `--inference`. The driver therefore takes the vantage as a seam (`host_vantage`); its default
  (`no_host_vantage`) makes steps (5) and (8) UNKNOWN, never PASS, so a live run cannot PASS until a channel is
  decided. Options, not chosen here: (a) a root request unit for the collector in the inference overlay (a seed
  change, under A4); (b) the collector run unprivileged as `agent` with reduced fields (membership by cgroup instead
  of the namespace link, no executable), which changes slice 1's independence argument; (c) the drill helper allowed
  on an inference guest (a test-only path); (d) accept the container view and the root facts' docker inspect alone.
- **F-7 (disclosed): the prompt route.** The prompt goes through the outer server's proxy route `POST
  /api/conversations/{conversation_id}/{tail}`, whose dispatcher value in the pinned route inventory is `validation`
  ("used only by the admission probe in a disposable conversation"). The qualification conversation is disposable,
  but the inventory's text names only the admission probe; the inventory (`profiles/.../agent-server/routes.json`,
  pinned by sha256) was not changed here.
- **F-8 (UNVERIFIED shapes, recorded as `ACP_ASSUMED` in every record):** the message body and `run`, the
  `execution_status` values that end a turn, the events page (`items`, `next_page_id`, `kind`, `ACPToolCallEvent`
  with `title`, a native call's `tool_name`), the inner server's search items (`id`, `parent_conversation_id`) and
  the answer's `agent.acp_server`. They come from the slice plan's source reading and the agent server's routes, not
  from the locked wheels in this dispatch (no network: the wheels were not re-read). A shape that differs gives FAIL
  (a refused route) or UNKNOWN (an unread page, a turn that never ends), except a different tool-call kind, which
  would undercount mechanism (a) without failing: a read-only check of `sdk/event/acp_tool_call.py` and the events
  router in the locked wheels before the run closes it.
- **F-9 (scope of the network view):** the connections are snapshots at two moments (while the turn runs and after
  it); a connection that opened and closed between them is seen only while it lingers in `TIME_WAIT`, and UDP is not
  listed. The container guard's refusal counters before and after the turn are recorded beside them, not judged.
