## 1. The question, as a decision

The recorder merges as `aieh-owner`, a write collaborator. Gitea 28.3.0 serves the branch-protection rules only to a repository administrator or a site administrator (`SOURCE`, section 2.1). OA-15a requires: every security-relevant protection setting verified immediately before the merge, fail closed when unverifiable, no administrator privilege for `aieh-owner`, no administrator credential in the recorder, an existing trusted mechanism or a small bounded adapter, no policy service.

So the decision is **which trusted read-only principal reads the rules, and how its verdict is bound to the merge call.** Four candidate mechanisms were weighed (section 3). One is recommended (section 4).

## 2. What the pinned source establishes (SOURCE unless marked)

### 2.1 Who may read the rules, and how scopes are enforced

1. `routers/api/v1/api.go:1397-1412`: the `/repos/{owner}/{repo}/branch_protections` group (GET list, POST, GET one, PATCH, DELETE, POST `/priority`) is wrapped by `reqToken(), reqAdmin()`. GET included.
2. `api.go:459-466` `reqAdmin()`: passes when `ctx.IsUserRepoAdmin() || ctx.IsUserSiteAdmin()`; the refusal text is "user should be an owner or a collaborator with admin write of a repository". `services/context/api.go:329` `IsUserRepoAdmin` = `ctx.Repo.Permission.IsAdmin()` = `AccessMode >= AccessModeAdmin` (`models/perm/access/repo_permission.go:47`). **A collaborator with `admin` permission on one repository satisfies it; site administration is not needed.**
3. `api.go:334-378` `tokenRequiresScopes`: the required level is taken from the HTTP method: `GET`/`HEAD` need the Read scope of the category; `POST`, `PUT`, `PATCH`, `DELETE` need the Write scope. The whole `/repos` group (`api.go:1311-1628`) sits under `tokenRequiresScopes(Repository)`. Hence **a `read:repository` token can GET the rules of a repository where its account is admin, and is refused (403, "token does not have at least one of required scope(s)") on every write route under `/repos` before any handler runs.** The scope check is skipped only when no `ApiTokenScope` is present, i.e. for password basic authentication.
4. `services/auth/basic.go:74-121` `VerifyAuthToken`: a personal access token sets `ApiTokenScope = token.Scope` **both** as `Authorization: token ...` and when presented as the basic-auth password. So a token cannot escape its scope by being used as a password. (OBSERVED at S-01.2.2 F3: an `all` mint attempted with a token as basic-auth password got 403 by scope.)
5. `api.go:111-145` `sudo()`: impersonation requires `ctx.Doer.IsAdmin` (site administrator), else 403 "Only administrators allowed to sudo."; an impersonation is audited (`audit_model.UserImpersonation`). A repository administrator cannot sudo.
6. `api.go:1173`: `GET /user` is under `tokenRequiresScopes(User)`; a `read:repository` token gets 403 there. `api.go:1142-1148`: `/users/{username}/tokens` needs `reqSelfOrAdmin(), reqBasicOrRevProxyAuth()` (a password); a Bot has none.
7. `api.go:1111-1113`: `GET /token` (`token.GetCurrentToken`) is wrapped by `reqToken()` only, **no scope requirement**; `routers/api/v1/token/token.go:19-52` returns `{id, name, scopes, created_at, last_used_at, user: {id, login}}` (`modules/structs/token.go:10-30`). This is the one scope-free way for a repository-scoped token to learn its own login and scopes.
8. `cmd/admin_user_create.go:114-118,152-154`: a `--user-type Bot` account may not be given a password ("password can only be set for user accounts"); an Individual must have one. (OBSERVED S-01.2.2 section 1: basic auth with any password answers 401 for every bot.) `--restricted` bots see only repositories they are explicitly given (OBSERVED S-01.2.2 section 7 Q2: a public repository answered 404 to all four bots; `repo_permission.go:488` gives a restricted user `AccessModeNone` as the floor).
9. `routers/web/repo/githttp.go:162`: git-over-HTTP checks `CheckRepoScopedToken(ctx, repo, GetScopeLevelFromAccessMode(accessMode))`; a push needs the Write level. (OBSERVED S-01.2.2 F10: the read-scoped verifier got 403 at the git endpoint.)
10. `api.go:1365-1376`: `GET /collaborators` and `GET /collaborators/{u}` need `reqAnyRepoReader()`; `PUT`/`DELETE` need `reqAdmin()`; `routers/api/v1/repo/collaborators.go:248-252` `GetRepoPermissions`: a repository admin may query every collaborator's permission ("repo admins can query all repo permissions, collaborators can query only their own"). `api.go:1377-1382` `GET /teams` needs `reqAnyRepoReader()`. `api.go:1452-1458` deploy keys (`/keys`) need `reqToken(), reqAdmin()`. `api.go:1355-1364` hooks need `reqToken(), reqAdmin()`.
11. `routers/api/v1/repo/branch.go:82` `GetBranch` passes `ctx.Repo.Permission.IsAdmin()` to `convert.ToBranch`; `services/convert/convert.go:106-108` sets `effective_branch_protection_name` only then; `convert.go:116-117` `user_can_push`/`user_can_merge` are computed for the caller only. This is all a non-admin ever sees of a rule (confirms P-04.2 F1).

### 2.2 The rule model and its API view

12. `models/git/protected_branch.go` `ProtectedBranch`: besides what P-04.2 listed, 28.3.0 carries **`EnableBypassAllowlist`, `BypassAllowlistUserIDs`, `BypassAllowlistTeamIDs`** and **`BlockOnCodeownerReviews`**, plus `Priority`. `protected_branch.go:205-224` `CanBypassBranchProtection`: a repository admin bypasses unless `BlockAdminMergeOverride`; **otherwise any user or team on the bypass allowlist bypasses**. `services/pull/check.go:191-205`: a `force_merge` succeeds exactly when `CanBypassBranchProtection` is true; `routers/private/hook_pre_receive.go:293-296`: the pre-receive hook of a merge push skips status checks, reviews and protected files for a bypasser. **The bypass allowlist is therefore a merge-authority setting of the first rank, and no existing harness record names it.**
13. `modules/structs/repo_branch.go` `BranchProtection` (the API view) has 37 JSON fields: `branch_name` (deprecated alias), `rule_name`, `priority`, 32 behavioural settings, `created_at`, `updated_at`. `services/convert/convert.go:144-211` `ToBranchProtection` maps every model field one-to-one; `routers/api/v1/repo/branch.go:607-620` `ListBranchProtections` converts every rule of the repository.
14. `convert.go:145-165`: allowlist *names* are resolved only among the repository's current readers and teams with access (`getWhitelistEntities(readers, ids)`); an id of an account that no longer has access is omitted from the API view while the row still holds it. The merge checks use ids (`services/pull/merge.go:686` `IsUserMergeWhitelisted(ctx, pb, user.ID, p)`). INFERRED consequence: such a stale id cannot be exploited, because the account cannot reach a private repository at all (`repo_permission.go:488`; restricted or not, a private repository gives a non-collaborator `AccessModeNone`), but the API view is not a byte-for-byte image of the row.
15. `modules/structs/repo_branch.go` `EditBranchProtectionOption`: every scalar is a pointer, lists are plain slices: a PATCH changes only the fields it names. INFERRED: a fixture declaration that names every field makes re-applying the fixture a full reset of a drifted rule; today's `gitea_roles.protection_rules()` names 7-13 fields per rule and leaves the rest at Gitea's defaults.
16. Merge-time evaluation: `routers/api/v1/repo/pull.go:962` `CheckPullMergeable` (allowlist, approvals, status checks, outdated, protected files, bypass) then `pull.go:1035` `pull_service.Merge` with `HeadCommitID`; the resulting push re-evaluates the rule in the pre-receive hook (`hook_pre_receive.go:144,275-311`: `IsUserAllowedToMerge`, `CanBypassBranchProtection`, `CheckPullBranchProtections`). Both reads take the rule row *as it is at that moment*. No API exposes a transaction spanning a rule read and a merge.

## 3. The options, weighed

### Option 1 - a host-side adapter reads `protected_branch` from Gitea's SQLite file. **Rejected as the mechanism; kept as the fallback of record.**
- For: no Gitea credential; reads the very row the merge evaluates (section 2.2 item 14 does not arise); the harness already has a read-only open (item 20).
- Against, decisive: (a) *narrowness is not enforced by anything*: a process that opens `gitea.db` reaches every table (password hashes, token hashes, `app.ini`-encrypted secrets); only code discipline keeps it to one SELECT, whereas Gitea's permission model enforces option 2's reach; (b) it couples the recorder to the storage schema of the pin (the `branch_name` column alias, JSON-TEXT id lists, the `version` table) instead of to the API Gitea publishes, against adoption-first ("reconcile the upstream APIs you actually observe", AGENTS.md) and 0011's upgrade verbs; (c) it compares ids, so the declaration would have to resolve usernames to ids itself (another read); (d) in DELETE journal mode a reader's shared lock stalls Gitea's writer for the read's duration (harmless at millisecond scale, but a second coupling); (e) it proves nothing about Gitea's *permission* model, which the API read exercises for free. Which identity reads it: the Owner's account, the same that runs Gitea (F-06.1), so no boundary is crossed or gained.
- Keep it recorded as the alternative if a future pin closes the API read to non-site-admins.

### Option 2 - a dedicated read-only audit identity: a restricted Bot with `admin` collaboration on the admitted repository only, one `read:repository` token, held by a small adapter the recorder calls. **Recommended.**
- Every property OA-15a asks for is enforced by Gitea at the pin (SOURCE, section 2.1): the rules are readable (items 1-2); nothing is writable with the token in either presentation (items 3-4); no sudo (item 5); no interactive sign-in and no password at all (item 8); no push (item 9); nothing instance-wide (restricted; no user, organization or admin scope: items 6, 8). The token is not an administrator credential: it is a read-only token of a non-administrator account, and the account's repository-administrator *permission* is exercisable through it only for reads.
- It is the existing trusted mechanism: S-01.2.2 built exactly this shape for the verifier (`aieh-bot-verifier`, `read:repository`), with provisioning, rotation, retirement, receipts and the I7 no-exposure scan in `gitea_roles.py`. Adding a role is a dictionary entry plus one collaborator permission.
- Self-check is possible without any admin: `GET /token` (item 7) proves login and exact scopes; `GET /repos/{o}/{r}` proves `permissions.admin`.
- Residuals: the read reach of a repository administrator (hooks, deploy keys, collaborators, teams, protections of that repository); the same-account limit (0010); the TOCTOU window (section 6); item 14's filtered view.

### Option 2' - reuse the verifier's identity (`cred-verifier-read`) by raising its collaboration to `admin`. **Rejected for now.**
- It would be the smallest change, and G-04.3 will need the same protection read. But it gives one credential entry two custodians (the recorder's adapter now, the executor-side verifier later), against 0011 I2 and the one-custodian pattern the matrix encodes (`custodian_of` vs `manager`), and it decides the verifier's permission before G-04.3 designs the verifier. The adapter (section 5) is identity-parameterized, so G-04.3 can reuse it with whatever identity it decides.

### Option 3 - Gitea's CLI, `gitea dump`, or another administration path. **Rejected.** Item 17: no CLI read exists; `dump` is a whole-instance backup; `doctor` checks nothing of the kind. The CLI runs as the Owner's account with `INTERNAL_TOKEN` reach (F-06.1 section 9): wider, not narrower.

### Option 4 - something else at source. **Nothing found.** No non-admin view beyond the branch's `protected`/`user_can_*` (item 11); no webhook on protection changes (item 18); the audit log is web-only, admin-only, off by default, and misses API changes (item 19); a server-side git hook would be a policy service in disguise and needs the site administrator's hook permission.

## 4. Recommendation (one option)

**Adopt option 2.** Concretely:

1. A fifth role in `integrations/gitea/gitea_roles.ROLES`, `protection-audit`: Gitea account `aieh-bot-protection-audit` (added to `gitea_host.BOT_ACCOUNTS`, which `gitea_host.verify`'s `accounts_are_the_expected_ones` and the recorder's bot refusal both read), created by the existing path (`admin user create --user-type Bot --restricted`), token scope exactly `read:repository`, fixture collaboration `admin` on `aieh-authz-fixture/authz` only, credential provider entry `AIEH Gitea bot protection-audit`, inventory credential `cred-gitea-protection-audit` (scoped authority), custodian `authorization-recorder`.
2. A small bounded verification adapter, `integrations/gitea/protection_check.py`, with one declaration of the expected protection (total over the closed list of section 5) shared with the fixture, a fixed set of GET calls, and a verdict that is one of `verified`, `drift`, `unverified`. It reads its entry by name into memory for one check and never returns the token.
3. The recorder calls the adapter in-process, in the same `record` command, after its own checks and immediately before the receipt reservation and the merge POST; and once more after the read-back, so the receipt brackets the merge with two protection digests (section 6).
4. The recorder refuses with new stable codes before anything is sent: `PROTECTION_UNVERIFIED`, `PROTECTION_DRIFT`, `PROTECTION_AUDITOR_INVALID`, `PROTECTION_CREDENTIAL_MISSING`; after a merge whose post-read differs: `PROTECTION_CHANGED_AFTER_MERGE` (exit 1, receipt `confirmed`, the difference in the receipt detail: a disclosure, not a refusal).
5. Decision 0012 point 6 is amended as in section 7; the inventory and matrix as in section 8; the live qualification and the Owner acts as in section 9.

Why this and not a composition by the dispatcher: a verdict produced in an earlier command is a bearer artifact any same-account process can forge (0010), and the window between the two commands is seconds to minutes instead of milliseconds. Why not a subprocess: it adds a launch site (`test_launch_census.py`) and gains no boundary under 0010; separation is by credential entry and code path (0013 point 6), which two modules in one process already give.

## 5. "Every security-relevant setting": the closed list

Derived from the 28.3.0 API view (`modules/structs/repo_branch.go`, which `ToBranchProtection` fills one-to-one from the model) and from what `gitea_roles.protection_rules()` declares. The adapter compares **34 fields per rule** (every API field except `branch_name`, `created_at`, `updated_at`), **the exact rule set**, and **six repository-level facts** the rules depend on.

Per rule, grouped by what it governs (API names):
- identity and precedence: `rule_name`, `priority` (the first matching rule by priority is the one the merge evaluates; a stray higher-priority glob would shadow `main` - INFERRED from `Priority` and `GetFirstMatchProtectedBranchRule`; the exact-set check closes it);
- push authority: `enable_push`, `enable_push_whitelist`, `push_whitelist_usernames`, `push_whitelist_teams`, `push_whitelist_deploy_keys`;
- force-push authority: `enable_force_push`, `enable_force_push_allowlist`, `force_push_allowlist_usernames`, `force_push_allowlist_teams`, `force_push_allowlist_deploy_keys`;
- merge authority: `enable_merge_whitelist`, `merge_whitelist_usernames`, `merge_whitelist_teams`, `block_admin_merge_override`;
- bypass authority (new at this pin; absent from every harness record): `enable_bypass_allowlist`, `bypass_allowlist_usernames`, `bypass_allowlist_teams`;
- review gate: `required_approvals`, `enable_approvals_whitelist`, `approvals_whitelist_username` (Gitea's singular), `approvals_whitelist_teams`, `block_on_rejected_reviews`, `block_on_official_review_requests`, `block_on_codeowner_reviews`, `dismiss_stale_approvals`, `ignore_stale_approvals`;
- freshness and checks: `block_on_outdated_branch`, `enable_status_check`, `status_check_contexts`;
- content: `require_signed_commits`, `protected_file_patterns`, `unprotected_file_patterns`.

Rule set: exactly the declared rule names (`main`, `work/*`, `**` for the fixture), none missing, none extra.

Repository level (all readable by the audit identity, items 2, 10): `private` true, `archived` false, `default_branch`; the merge-style settings (`allow_merge_commits`, `allow_rebase`, `allow_rebase_explicit`, `allow_squash_merge`, `allow_fast_forward_only_merge`, `allow_manual_merge`, `autodetect_manual_merge`, `default_merge_style`: G-03.1 wants merge commits only); the collaborator roster with each permission, exact (planner write, builder write, reviewer read, verifier read, `aieh-owner` write, `aieh-bot-protection-audit` admin, nobody else); the teams with access, exact (the organization's `Owners` team only); deploy keys: none. Webhooks are *reported*, not compared (G-03.1 plans one to wake the verifier).

Declaration values for the fixture's `main` rule (total): every field above explicit; `enable_merge_whitelist` true with `merge_whitelist_usernames` `[aieh-owner]`; `block_admin_merge_override` true; `required_approvals` 1; `enable_approvals_whitelist` true with `[aieh-bot-reviewer]`; `block_on_rejected_reviews` true; `block_on_outdated_branch` true (G-03.1 requires it for the authorization branch; the fixture should match; the live proposals branch from `main`'s head, so it costs nothing); every other flag false, every other list empty, both pattern strings empty, `priority` 1. Open to G-03.1, not decided here: `dismiss_stale_approvals` (an approval surviving a new head is a weakness the Owner may want closed; the fixture declares false until G-03.1 says otherwise). `null` and `[]` compare equal for list fields (Go serializes an unset slice as `null`; `getWhitelistEntities` returns `[]`).

Pin sensitivity, by design: an observed rule with a field outside the closed list, or missing one, is `unverified` ("a setting this pin does not know"): an upgrade that adds a protection setting stops merges until the list is revisited. That is the fail-closed behaviour OA-15a asks for, and it is a compatibility clause the Gitea pin now carries (0011 upgrade verb, R-02.3.x).

## 6. Time of check to time of use

The check and the merge cannot share a transaction (item 16). What narrows the window and what remains:
- the adapter's read is the last call before the receipt is reserved and the merge is POSTed, on the recorder's own loopback connection: milliseconds;
- Gitea itself evaluates the rule twice at merge time (handler and pre-receive hook), so the *enforced* rule is the row at the moment of the merge; the harness's check proves what that row was just before;
- after the read-back, the adapter reads the rules again; `receipt.protection = {before: sha256 of the canonical observed rules, after: ..., equal: bool}`. Equal brackets prove the row did not change across the merge except by a change-and-revert inside the window.
- Who can change a rule: a repository administrator of that repository (items 1-2). In the fixture that is the site administrator (organization owner), whose credential is harness-held and readable by any same-account process: inside the trusted computing base of 0010. So the residual is "a same-account or administrator actor changes and reverts a rule within one request round-trip", which 0010 places out of scope, and the bracket discloses even a non-reverted change. State this in 0012 point 13 as detected, not prevented.
- Do not lean on the audit log for the window: at this pin a rule changed through the API is not audited at all (item 19), and the log is web-only. This also narrows G-03.1's proof clause "a protection change observed in the log" to web-made changes; see finding F-B.
