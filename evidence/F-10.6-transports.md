## The transports (`a934980`, `93781f9`)

`integrations/repository/repository_access.py` gains the transports decision 0014 section 8 leaves
to "the leaves that first need them" (its README, [Transports](../integrations/repository/README.md#transports-f-106)):

- `ls_remote(url, credential=None, *, names=None)`: `git ls-remote`, annotated tags peeled under
  `<tag>^{}`; `names` asks the server only for those full names (protocol v2 `ref-prefix`).
- `clone(url, destination, credential=None)`: `git clone --bare` (branches, tags, HEAD,
  `remote.origin.url` without a credential).
- `Repository.push(url, refspec, credential=None)`: `[+]<src>:<dst>`, with git's client-side rules
  applied before anything is sent (non-fast-forward, fetch first, an existing tag, deleting a
  missing reference); returns `RefUpdate(name, old, new)`; nothing local is written.
- `Credential(username, secret, scheme)`: held in memory, sent only as `Authorization: Basic ...`
  or `Authorization: token ...` to the URL's own origin; `repr` hides the secret. A URL with
  credentials, a query, a fragment or a scheme other than `http`/`https` is refused before access.

Over Dulwich 1.2.21's `Urllib3HttpGitClient` with **no git configuration** (`config=None`: no
credential helper, `http.extraHeader`, `insteadOf`, proxy or TLS settings from configuration) and
**no process**: no helper, no ssh, no subprocess (G13 is not a gap for this flow). Two Dulwich
behaviours are handled in the module: the client stores `extra_headers` but never sends them, and
answers 403 as an untyped protocol error, so the module overrides the documented
`_http_request` hook to add its header for the origin only and to keep the HTTP status; and
urllib3's default retries (a refused loopback connection took about 8 s: urllib3 retries a failed
connection three times) are replaced by one attempt per request, as git makes.

**Codes** (recorded in the module README, the record of local codes): `PUSH_REFUSED` (HTTP 401 or
403 on a push; the plan's code), `PUSH_REJECTED` (a rejected update: the server's `ng`, git's
client-side rules, or a source naming no object; the plan's code), and three the leaf needed
beyond the plan's two, for the Overseer to confirm: `REMOTE_REFUSED` (401 or 403 on `ls_remote` or
`clone`), `REMOTE_FAILED` (any other transport failure) and `HOOKS_UNSUPPORTED` (decision 0014
section 6: "every write operation of the module ... refuses a repository that has client hooks
configured ... with a stable code naming the hook").

**Tests.** `integrations/repository/tests/test_repository_transport.py` (22 tests) against
Dulwich's own smart-HTTP application (`dulwich.web.make_wsgi_chain`) under `wsgiref` on
127.0.0.1, in process, behind an authorization layer answering 401 and 403 as Gitea does, with an
in-process `update` hook declining a protected branch; every repository is built with Dulwich's
object API; process creation and Dulwich's user and system configuration are patched to fail.
`OracleTransport` in `test_repository_oracle.py`: `git ls-remote` lists what `ls_remote` lists, and
`git fsck --strict` accepts the module's clone and the served repository after two module pushes.
The live suite `integrations/gitea/tests/test_transport_live.py` (`e2e`, opt-in through
`AIEH_GITEA_TRANSPORT=1`, target `gitea:transport`, documented in `docs/development.md`) never runs
in `task test`; there both its classes skip with their reason.

**R1, the repository wall.** Disk Cleanup (`cleanmgr`) was running when the first budget profile
started; that profile was stopped, and the run waited for Disk Cleanup to exit (it could not be
waited on by handle, so its process was checked every 10 s until it was gone), then a three-run Git
Bash profile at `53584ef` ran with a watch that never saw Disk Cleanup again. `propose` derives
`wall_s` 5.9 s for the repository suite (median 5.893 s; runs 5.893, 5.862, 5.985). Only that wall
changed (4.8 s -> 5.9 s, limit 7.67 s); every other wall is kept and passes. Counters re-proposed in
the same commit (`836368c`). `OracleTransport` stays in `task test`.

**R3, the codes.** `REMOTE_REFUSED`, `REMOTE_FAILED` and `HOOKS_UNSUPPORTED` stay as named.
`HOOKS_UNSUPPORTED` applies to `push`, the module's only write besides `clone` (which creates a new
repository, where no hook can exist): `Push.test_client_hooks_are_refused_before_any_access` (a
`hooks/pre-push` file, then `core.hooksPath` under the `none` and `repository` policies, each
refused before any request reaches the server).

**R4, redirects (a security check).** `Redirects` in `test_repository_transport.py`:

- `test_a_redirect_to_another_origin_carries_no_credential`: a stand-in replaces urllib3's
  connection-pool `urlopen` (no network) while urllib3's real PoolManager redirect logic and the
  module's transport run; for https to http (the downgrade), http to https, another host and
  another port, with `ls_remote` and `push`, Basic and token (16 subtests), the first request
  carries the credential and the redirected one carries **no `Authorization`**;
- `test_a_redirect_within_the_origin_keeps_it`: the control, the header after a same-origin
  redirect;
- `test_a_real_redirect_to_another_port`: end to end, a loopback server answers 302 to the served
  remote on another port; the remote receives the request without the header and refuses it (401,
  `REMOTE_REFUSED`).

All pass: urllib3 2.8.0 drops `Authorization` whenever the scheme, host or port changes
(`HTTPConnectionPool.is_same_host` compares all three), and the module adds it only for the
remote's own origin, so **no module change was needed**. That the tests catch a leak is shown by a
mutation (`mutate_redirect.py`: `is_same_host` patched to answer True): 16 subtests and the
end-to-end test fail, the control passes.

**R5, Dulwich upstream behaviours.** The module README now states that the `_http_request`
override and the retry policy are pin-sensitive, and that `test_repository_transport.py`,
`OracleTransport` and `task gitea:transport` are the check at every Dulwich or urllib3 pin change.
The `extra_headers` behaviour was reproduced locally with Dulwich 1.2.21 and checked for duplicates
upstream; the report below is a draft for the Owner, not filed.

## Upstream report: Dulwich `extra_headers` (draft, not filed: filing is the Owner's act)

**Duplicate check** (2026-11-09; read-only, unauthenticated GitHub search API on `jelmer/dulwich`
issues and pull requests; nothing posted). Queries: `extra_headers`, `extra_headers` in title or
body (issues), `"extra headers"`, `extraHeader`, `custom headers http`, `headers not sent`,
`Urllib3HttpGitClient headers`. No equivalent issue was found. Related, all closed: #1769
"Support http.extraHeader" and #882 "Support for extra header authentication" (both about the
`http.extraHeader` configuration option, implemented by #1774 and #1969); #2201 "drop credentials
when info/refs redirects to a different origin". The constructor argument and its stored attribute
first appear in #1774's diff ("Add support for http.extraHeader configuration"), whose tests cover
the configuration path only.

**Title:** `Urllib3HttpGitClient(extra_headers=...)` stores the headers but never sends them

**Versions:** dulwich 1.2.21 (the `cp312-win_amd64` wheel), urllib3 2.8.0, CPython 3.12.10,
Windows 11. Not tried on other versions or platforms.

**What happens:** `Urllib3HttpGitClient.__init__` accepts `extra_headers: dict[str, str] | None`
and assigns `self._extra_headers = extra_headers or {}`. In the 1.2.21 wheel no other line of the
`dulwich` package (outside its tests) reads `_extra_headers`, and a server receives none of the
headers. Headers from the `http.extraHeader` configuration are applied (through
`default_urllib3_manager`), so the configuration path works; only the constructor argument is
ignored.

**Expected:** the headers given as `extra_headers` are sent with each request (or the argument is
removed or documented as unused).

**Minimal reproduction** (standard library and dulwich only; a local server records the header):

```python
import http.server
import threading

from dulwich.client import Urllib3HttpGitClient

seen = []


class Handler(http.server.BaseHTTPRequestHandler):
    def do_GET(self):
        seen.append(self.headers.get('X-Probe'))
        self.send_response(404)
        self.end_headers()

    def log_message(self, *args):
        pass


server = http.server.HTTPServer(('127.0.0.1', 0), Handler)
threading.Thread(target=server.serve_forever, daemon=True).start()
client = Urllib3HttpGitClient(f'http://127.0.0.1:{server.server_address[1]}/', extra_headers={'X-Probe': 'yes'})
try:
    client.get_refs('/repo.git')
except Exception as exc:
    print('get_refs raised', type(exc).__name__)
server.shutdown()
print('X-Probe received by the server:', seen)
```

Observed output: `get_refs raised NotGitRepository` (the 404), then
`X-Probe received by the server: [None]`. Expected `['yes']`.

**Root cause, as far as shown:** the attribute is assigned and never read in 1.2.21 (a search of
the installed package source); `_http_request` builds the request headers from the pool manager's
headers, the call's headers and the Basic credential only. Whether a later release changed this
was not checked.
