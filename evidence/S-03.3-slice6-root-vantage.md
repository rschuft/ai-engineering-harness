## 1. F-6: the reporter's `containment` section

The reporter is `aieh-provision conversation-facts`, a mode of the root step the user-data template writes
(`profiles/seed/user-data.tmpl`, `/usr/local/sbin/aieh-provision`), started by `aieh-conversation-facts.path` when
`agent` creates `/var/lib/aieh/facts-request/conversation-facts`. Its report (`/run/aieh/conversation-facts.json`,
schema `ai-engineering-harness/profiles/conversation-facts/v1`, unchanged) gains one key, `containment`, computed by
the new `containment_host(inspected)` from the `docker container inspect` objects the reporter already reads:

| Field | Content |
|---|---|
| `format` | `ai-engineering-harness/containment/snapshot/v1` (slice 1's `SNAPSHOT_FORMAT`) |
| `caps` | `{containers: 16, processes: 1024, outside_children: 64}` |
| `skipped` | the containers beyond the 16th, counted, not reported |
| `containers` | per container `Id`: for a running one (`State.Pid` > 0), exactly the snapshot slice 1's `collect host --pid <State.Pid>` prints (`format`, `mode` `host`, `self` (the reporter's own pid), `vanished`, `target_pid`, `target_pidns`, `processes`, `outside_children`, `limits`) plus `truncated` `{processes, outside_children}` (the members and outside children beyond the caps, counted); for a stopped one `{error: "not running (State.Pid …)"}`; when the init's `ns/pid` link cannot be read `{error: "TARGET_INVALID: pid …: <exception class>", target_pid}` |

Each process record is slice 1's: `pid`, `ppid`, `state`, the `status` fields `Uid`, `Gid`, `Groups`, the five
capability sets, `NoNewPrivs`, `Seccomp`, `NSpid`; the cgroup v2 path; `argv0`'s last segment, the first absolute
path among the next three arguments and the count; the `exe` and `ns/pid` links. A process outside the namespace is
listed only when its parent is inside. `limits` are `memory.max`, `cpu.max` and `pids.max` of the init's cgroup.

**How it is built.** The readers are verbatim copies of slice 1's `OsFs`, `parse_stat`, `parse_status`,
`parse_cgroup`, `parse_cmdline`, `summarize_argv`, `_text`, `_error`, `_process`, `_pids` and `_limits`, with its
constants `SNAPSHOT_FORMAT`, `STATUS_FIELDS`, `LIMIT_FILES`, `ARG_MAX` and `SCRIPT_SCAN`; a test compares each
copy's syntax tree with slice 1's, so a change to slice 1's readers fails until the seed follows. One `/proc` scan
serves every container (slice 1 scans once per target; the per-container result is the same, shown by the tests).
It runs no command, reads no environment and no file but slice 1's (`/proc` listing, `stat`, `status`, `cgroup`,
`cmdline`, the two links, the three cgroup files), and keeps no argument value but `argv0`'s last segment and one
path. Its call is wrapped like the boot facts' optional sections: an exception becomes `{error}` and the rest of the
report is written as before. The whole report still passes the reporter's existing secret redaction.

**Within the STOP conditions of the dispatch:** no input from the agent beyond the request file's existence; no
environment or file-content read beyond slice 1's (the reporter already read `/proc/<pid>/cmdline` of
`docker-proxy` for its listener facts); no existing report field changed (a test fixes the report's key list:
the 19 existing keys in order, then `containment`).

**Independence.** Slice 1's argument holds: the container view is still taken inside the container through the
bash route; the guest-root view is still read by root from the guest's `/proc` and cgroup files, and judged against
`docker container inspect`'s `HostConfig` and `State.Pid` by slice 1's unchanged `host_verdict`. What differs is
who runs the reads: a fixed root reporter seeded at create, triggered by a file whose content it never reads,
instead of slice 1's file sent at run time; the agent supplies no code and no argument to it, and the report it
writes is root's (`/run/aieh`, `0644`), read by `agent`.

## 2. F-6: the driver's default vantage

`tools/guest.py`:

- `host_snapshot_from_report(report, state_pid)` returns slice 1's host snapshot for the container whose init is
  `state_pid`, `truncated` removed, or raises `Refused('HOST_VANTAGE', …)`, which the driver records as the vantage's
  gap (the step UNKNOWN, never PASS), when: the report has no `containment` section (a guest seeded before this
  change); the section is an error or not of its shape; there is no entry, or more than one, for that init; the
  entry is an error; a list is truncated or the truncation count is missing; the snapshot lacks one of slice 1's
  keys or is not a host snapshot; a process record lacks `pid` or `ppid`, one of `state`, `status`, `cgroup`,
  `argv0`, `script`, `argc`, `exe`, `pidns`, or a `status` field. A read slice 1 itself records as failed (its
  `{pid, ppid: None, error}` record of an unreadable `stat`, a `status` of `{error}`) is passed to slice 1's
  judgement unchanged, as `collect host` would have printed it, so it fails there.
- `facts_host_vantage(facts)` is the driver's default `host_vantage`: in each observation, after the container
  snapshot (slice 1's order), it requests a new report through the existing facts channel (`GuestFacts`, as
  `agent`) and takes the snapshot of the container's `State.Pid` from it. `no_host_vantage` and its gap text are
  removed. The `host_vantage(record, state_pid)` seam is unchanged.
- A run makes two more reports than before (one per observation, steps 5 and 8): nine in all, inside the units'
  20 per 60 s.

## 3. F-8: the turn's end and `ACP_ASSUMED`

`ACP_STATUS_VALUES` is the image's enum (`idle`, `running`, `paused`, `waiting_for_confirmation`, `finished`,
`error`, `stuck`, `deleting`); `ACP_TURN_TERMINAL` the SDK's `is_terminal` set; `ACP_TURN_HALTED` the two halted
states. The wait goes on only while the status is `idle`, `running` or not yet read; any other value ends it at
once. Step (7)'s outcome, from the status read after the wait:

| `execution_status` | Ends the wait | Step (7) | Recorded `outcome` | Stop |
|---|---|---|---|---|
| `finished` | yes | PASS | `terminal` | no |
| `error`, `stuck` | yes | FAIL | `terminal` | no |
| `paused` | yes | FAIL | `halted` | no |
| `waiting_for_confirmation` | yes | FAIL | `halted` | yes: "a turn waiting for a confirmation (nothing may confirm on the Owner's behalf)"; steps 8 to 10 skipped, the key search, revocation and teardown still run |
| `deleting` | yes | FAIL | `deleting` | no |
| any other value (another string, a number) | yes | FAIL | `outside the status enum` | no |
| `idle`, `running`, none, at the ceiling | no | UNKNOWN | `not ended within the ceiling` | no |

`paused` is FAIL, as every non-`finished` end already was: the ruling keeps it from PASS and has it recorded
distinctly; it is not made UNKNOWN. The decision rule's text (`ACP_QUALIFICATION_RULE`, fixed before any run; no run
has happened) states step (7)'s ends and adds the confirmation stop.

`ACP_ASSUMED` cites the D-1 record for every item (message, status, events, inner, agent) and names what that read
did not cover (the outer proxy's dispatcher value, the inner server's address, the events `limit` bound).

**The 429 note is disclosed, not added.** The image's `send_message` documents that a 429 from starting the run
means the message is saved and `/run` should be retried. The driver sends every request once and retries nothing
(no step has a retry; a lost or refused answer is FAIL or UNKNOWN), so a retry of `/run` does not fit its rules:
a 429 stays step (4) FAIL with its status recorded, the later steps are not reached, and the saved message goes
with the conversation at teardown. `ACP_ASSUMED['message']` says so.
