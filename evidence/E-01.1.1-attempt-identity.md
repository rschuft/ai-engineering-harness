## 2. The stop and the rulings

The dispatch said a new ordinal could be reserved only after every earlier one had `failed`, and
"never after one is `confirmed`". The Builder stopped before writing code. The blueprint requires
further attempts after a confirmed one on the same Work, at the same design revision and stage:
"Substantiated findings create another bounded attempt on same Work; fresh review of new SHA";
"Failing evidence → same Work item, new attempt/commit". Dispatch step 02 asks only to "Prevent
concurrent claims". The Overseer ruled:

| Ruling | As built |
|---|---|
| R1 claim rule, option A | a new ordinal only when every earlier ordinal on the triple is terminal (`confirmed` or `failed`) with no gap; never while one is `reserved`, `dispatched` or `unknown`; no cap encoded (section 4) |
| R2 stage | `implement` and `review`, held in the lookup table `attempt_stage` with frozen-vocabulary triggers, as `attempt_state` is; rework is another `implement` ordinal, a fresh review another `review` ordinal |
| R3 design revision | `openspec:changes/<change>@<commit>`, from the planning adapter's `CHANGE_ID` and full `COMMIT` grammars, derived from a task's pointers through `Pointer.parse` (`design_revision_from_pointers`) |
| R4 attempt UUID | `attempt_id = uuid5(ATTEMPT_NAMESPACE, operation_key)`, namespace `078cbf65-575e-463b-9e56-93efe59ba38c`, distinct from `CONVERSATION_NAMESPACE`; UNIQUE, immutable, pinned by a test |
| R5 workRef | the stored intent carries `workRef = backlog:<work_id>`; a trigger checks it against the typed column |
| R6 inputs | `agent_manifest_digest` nullable (no approved catalog yet; E-01.2.1 makes it required); `planned_workspace` a relative identifier under `persistent/workspaces`; `profile_digest` the sha256 of the `profile.json` bytes |
| R7 checkout path | the blueprint's OWN panel says "checkout path"; dispatch step 02 says "planned workspace", and decision 0009 point 10 says "Nothing under the root records the checkout path as identity". The record holds the planned workspace identifier, never a host path |

## 3. Schema and key

`attempt_identity`, 1:1 with `attempt` (STRICT):

| Column | Constraint |
|---|---|
| `operation_key` | PRIMARY KEY; references `attempt`, deferred to COMMIT (the identity is written first) |
| `attempt_id` | UNIQUE; UUID text shape |
| `work_id` | CHECK `work_id_grammar`: `planning_adapter.TASK_ID_RE`, upper case, at most 64 characters |
| `design_revision` | CHECK `design_revision_grammar`: `openspec:changes/` + `CHANGE_ID` (at most 128) + `@` + 40 or 64 hex |
| `stage` | references `attempt_stage` (`implement`, `review`) |
| `ordinal` | CHECK 1 to 999999; UNIQUE with the triple |
| `profile_digest`, `policy_digest` | CHECK 64 lower-case hex |
| `agent_manifest_digest` | NULL, or 64 lower-case hex |
| `planned_workspace` | CHECK `planned_workspace_grammar`: the planning adapter's `ARTIFACT_PATH`, at most 255 |
| `live` | 0 or 1; written only by triggers |

The key is `attempt/v1/<work_id>/<change>@<commit>/<stage>/<ordinal>`. No part's grammar contains
`/`, so it is unambiguous without escaping. The longest identity gives a key of under 300
characters, within the 512-character limit, and leaves room for a 32-character stage. The
admission trigger refuses any identity whose key is not this encoding of its columns. The
conversation ID stays `uuid5(CONVERSATION_NAMESPACE, key)`. A Backlog.md id is stored upper case
because Backlog.md and the planning adapter compare ids without case (`planning_adapter.py`
line 429, `lineage_resolve.py` line 378); otherwise `task-1` and `TASK-1` would be two triples.

The intent stored is the caller's intent plus `workRef` and `attemptIdentity` (the identity's
fields, `format: attempt-identity/v1`). The intent digest therefore covers profile, manifest,
workspace and policy: the same key with any of them changed is `ConflictingReservation`.

## 4. Claim mechanism and why

- A partial unique index `attempt_identity_one_live_claim` on (`work_id`, `design_revision`,
  `stage`) `WHERE live = 1` makes two live rows on a triple impossible. It is structural, so it
  holds even if the trigger were bypassed. The test proves it with the trigger dropped.
- `live` cannot drift. It is inserted as 1 (the admission trigger refuses anything else). An
  `AFTER UPDATE OF state` trigger on `attempt` sets it from `attempt_state.terminal`. A
  `BEFORE UPDATE OF live` trigger refuses any value that disagrees with the attempt's current
  state, so a direct write can only restate the truth.
- The admission trigger (`BEFORE INSERT ON attempt_identity`) refuses:
  - a non-canonical key;
  - a row not inserted live;
  - a row attached to an existing attempt;
  - a live claim on the triple;
  - an ordinal that is not the next one.

  It gives the ordinal rule and named refusals.
- `attempt_typed_admission` (`BEFORE INSERT ON attempt`) reserves the `attempt/` key namespace
  for typed attempts. It requires them to start `reserved`, with an intent carrying the same
  identity and `workRef`. The deferred reference means an identity without its attempt never
  commits.
- `reserve_attempt` applies the same rules first, in one `BEGIN IMMEDIATE` transaction, with typed
  errors: `ConflictingReservation`, then `RestoreEpochOpen`, then `LiveClaim`, then
  `OrdinalOutOfSequence`. An identical request returns the existing reservation with
  `created=False`.

Why a flag and an index rather than a trigger alone: a trigger is code that can be dropped or
bypassed by a later migration's mistake. A unique index expresses "one live" as data. SQLite
partial indexes cannot reference another table, so the attempt state is mirrored into `live`
under triggers that keep it exact.

## 8. Gaps recorded, not repaired here

- **Lineage, the design kind:** `lineage_resolve.DesignResolver` resolves only the P-02.1
  artifact pointer (`openspec:changes/<change>/<artifact>@<commit>#sha256=<digest>`). The lineage
  schema says the change-level form "is not a form here". So a typed attempt's `design_revision`
  is not a resolvable lineage reference today.
- **Lineage, the intent:** lineage reads only `workRef` and `outcomeRef` from a reservation's
  intent (`lineage_trace.py` `WORK_KEY`, `OUTCOME_KEY`), not the typed columns. R5 keeps it
  working unchanged: every typed reservation carries `workRef`. `outcomeRef` stays the caller's
  to supply.
- **Planning, unrelated-but-detected, not repaired here:** `planning_adapter.Pointer.parse` and
  `TASK_ID_RE.match` accept a trailing newline, because Python's `$` matches before a final
  newline. Observed: `Pointer.parse(pointer + "\n").text == pointer`, and
  `TASK_ID_RE.match("TASK-1\n")` is truthy. The store guards itself: it uses `fullmatch` and
  requires a pointer to equal its canonical text. Planning is read-only for this leaf.
