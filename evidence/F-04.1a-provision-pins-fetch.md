## 4. `tools/guest.py provision-fetch`

What it does (also in `docs/development.md`, Execution guests):
1. Reads the lock only after its bytes match `provider.provision_lock.sha256`
   (`LOCK_MISMATCH` otherwise); checks schema, profile, https URLs, sizes, sha256s, safe
   path components and the image digests before any network use.
2. Downloads each index file, `.deb` and the release binary with urllib (redirects to
   https only), streaming into `<name>.part` with a size ceiling and sha256; renames on
   a match; a mismatch is kept as `<name>.rejected` and refuses (`HASH_MISMATCH`).
3. Installs crane into `{state}\tools\crane\v0.22.1\`: the archive is checked, the single
   regular `crane.exe` member is checked, written through `.part`, and the archive is
   deleted. An existing `crane.exe` is re-hashed before use.
4. Runs crane with a scrubbed environment (`SYSTEMROOT`, `WINDIR`, `SYSTEMDRIVE`, and
   `DOCKER_CONFIG`/`USERPROFILE`/`HOME`/`TEMP`/`TMP` pointing at new empty directories in
   the work area): `crane manifest` of the index and of the platform manifest must hash to
   the locked digests, the index must name exactly the locked linux/amd64 manifest, and
   that manifest's config and layers must equal the lock. Then
   `crane pull --platform linux/amd64 ghcr.io/openhands/agent-server@sha256:b43ee580… <part>`.
5. Verifies the archive with `tarfile` and `hashlib`: only regular members, exactly
   `manifest.json`, the config and the layers it names; the config member hashes to the
   locked config digest, and each layer, in order, to its locked digest and size.
6. Refuses if crane wrote into its empty home; writes `staged.json` (lock path and sha256,
   image digests, crane pin, every file with role, size and sha256); refuses stray
   files; renames `{lock sha256}.partial` to `{lock sha256}`; writes a run record under
   `{state}\provision\records\`. An existing stage is re-verified in full (inventory,
   every file, the image archive against the lock) and reused.

Unit tests: `tools/tests/test_provision_fetch.py`, 21 tests, no network (an in-memory
opener and a fake crane that asserts it runs from the verified install with an empty,
private home). Negative controls, each refusing with nothing staged:
- a tampered `.deb` (same size, different bytes) → `HASH_MISMATCH`, kept as `.deb.rejected`;
- a download one byte longer than locked → `HASH_MISMATCH`;
- a wrong locked image config digest → `DIGEST_MISMATCH` after the two `crane manifest`
  calls, before any pull;
- a pulled archive whose config differs → `IMAGE_MISMATCH`, kept as `agent-server.tar.rejected`;
- index bytes not hashing to the locked digest → `DIGEST_MISMATCH`;
- an index naming another platform manifest → `DIGEST_MISMATCH`;
- a crane member hash mismatch → `HASH_MISMATCH` before any crane call; an installed
  `crane.exe` that changed → `HASH_MISMATCH` before any crane call;
- the lock not matching the profile pin → `LOCK_MISMATCH`;
- an `http://` URL → refused before any download; a `../` filename → refused;
- a staged file changed, or an extra staged file → `STAGED_MISMATCH` on reuse;
- an archive with an extra member → `IMAGE_MISMATCH`.
Positive cases: staging, resume after interruption (a complete file reused, a stale
`.part` replaced), and reuse with no download or crane call. `CommittedLock` checks the
committed lock's pin, shape and agreement with `components.lock.json`.

`tools/check_profile.py` now hash-checks `provider.provision_lock` and its shape (https
URLs, sizes, sha256s, one snapshot timestamp across indexes and packages, `ref =
repository@index_digest`, `image_id = config_digest`, layers, the crane member and
checksums source). Five new negative tests in `test_check_profile.py`.

## 7. Findings

1. **Defect, introduced by this slice, fixed before commit.** Run 1's result recorded
   each download's full final URL. For GitHub that is a pre-signed
   `release-assets.githubusercontent.com` URL carrying a signature and a token (public
   asset, expiring 05:01Z). `fetch_file` now records only the host (`final_host`), with a
   test. The run-1 record in `D:\aieh-guest-state\provision\records\` still holds the
   expired URL; it is outside the repository and was left as the run's record. No such
   URL is in this file or any commit.
2. **apt 3.0.3 `--print-uris` prints MD5Sum, not SHA256** (exposed by this slice: the
   design expected SHA256). The SHA256 values come from `apt-cache show` over the
   signature-verified lists, cross-checked on the host against the pinned index.
3. **The archive carries the tag `ghcr.io/openhands/agent-server:i-was-a-digest`**
   (go-containerregistry's placeholder for a digest reference). `docker load` in slice
   (b) will create it. It looks like a floating tag; slice (b) must remove it and keep
   only the local immutable tag whose image ID is checked.
4. **`resolution_digest` differs from F-01.2** only through the lock file's own hash
   (section 1). Not a defect.
5. **`composition/lock/README.md`** describes `conversation_image` without the new
   `config_digests` field (exposed by this slice; outside this slice's write paths).
   Carried to the Overseer.
6. **Base image:** apt, apt-utils and libapt-pkg7.0 have a 3.0.4 security update at the
   snapshot. Not part of the closure; recorded for slice (b) and R-03.x.
7. **Process disclosures.**
   - To read the image manifests before the lock existed, the builder installed the
     same verified `crane.exe` by hand (archive and member sha256 checked) and ran it
     with the same empty-home environment. It was deleted before run 1, so run 1 shows
     the tool's own install.
   - One `ls -la` of named `D:\aieh-guest-state` children printed their `..` entry,
     which is the state directory's own metadata line, not a listing of it.

## 8. Inference (not observed)
- Slice (b) can install the closure with `apt-get install --no-install-recommends ./*.deb`
  on a guest from the same base image build: apt resolved this exact set against that
  installed base. A different base image build may need more packages.

  so dockerd's default bridge and overlay2 should load them as root. Not observed
  (nothing ran as root).
- The archive's whole-file sha256 is probably not reproducible across crane runs; only
