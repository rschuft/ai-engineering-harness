## 1. The exposure boundary

Where the synthetic key is, and every way out of that place:

- **The key lives in one process's memory:** the qualification launcher reads it from standard input
  (`SyntheticKeyProvider`) and runs the broker's own `serve`, whose `ProviderKey` holds it. It is in no argument,
  variable, file or configuration (slice 4, constraints 2 to 4).
- **That process's outputs** are the only places it could be written: (a) its request to the upstream (the
  family's auth header: the key *must* be there, by design, toward the fake upstream on host loopback); (b) the
  inference listener's answers, which the SSH remote forward relays unchanged to the guest's endpoint, so that
  they are exactly what a conversation container receives from the plane; (c) the control listener's answers
  (the attempt token the dispatcher hands to the job); (d) its standard output (the `serve` report) and standard
  error (the launcher's line with the fingerprint, the serving line); (e) the integration store (receipts); (f)
  the audit directory. There is no other channel from that process toward a guest.
- **What a guest or container can read besides** comes from processes that never hold the key: the seed
  (`seed.iso`), `tools/guest.py`'s ssh sessions and API requests (the create request, the job scripts, the
  attempt token, sealed), the instance directory. `tools/guest.py` holds the key only with the new
  `--provider-key-stdin`, on the host, to search; it never sends it (a test checks every argument and standard
  input sent to the fake guest).

| Surface | Reachable by a guest or container | Searched offline (this slice) | Searched live (prepared) |
|---|---|---|---|
| Inference answers (what crosses the forward) | yes, by design | every byte, `test_key_search_boundary` | each answer as received in the job and by the guest login, whole up to 64 KiB (`job-access-probe --provider-key-stdin`) |
| Inference requests from the job | yes (the job wrote them) | every byte | in the job's own collection (below) only |
| Control answers (the token handed on) | the token is, by design | every byte | `issue`'s output is the token alone; its standard error the fingerprint (the reports) |
| Broker standard output and error | no (host), searched as reports | every byte | redirected to files in the reports directory, `tree` |
| Integration store, audit directory | no (host) | every file, the store also row by row | `tree` over the managed root's `state/integration` and `persistent/logs/inference` |
| Fake upstream records | no (host) | every byte | in the reports directory |
| The guest's files, process environments and records | yes | not applicable (no guest) | `inspect --provider-key-stdin`: the P5 collection (as the agent user) and `seed.iso`, `launch.json`, `serial.log` |
| The instance directory (with the job and inspect records) and the reports | the seed and records cross; searched as reports | not applicable | `tree` over the instance directory and the reports |
| The search's own process environment | n/a | yes | `environ:self` (the shell's environment, which the launcher inherited) |
| The broker's request to its upstream | no (host loopback) | every byte: **must** hold the key (a natural positive control) | not captured live |
| Process memory | n/a | **not searched** | **not searched** |

## 2. The search (`inference_key_search.py`)

Standard library only; it imports nothing of the broker, so its evidence is independent of the broker's own I7
scan (which checks raw and UTF-16LE) and report.

**Forms** (each of the whole key and of its body, the key without the public prefix
`aieh-qualification-synthetic-`), with why each is plausible here:

| Form | Why |
|---|---|
| raw | the key as written; JSON string escaping, URL and form encoding (`quote`, `quote_plus`, `urlencode`), HTML escaping and shell quoting are identities on this alphabet, so they are this form (the positive control plants them through the real encoders) |
| hex, HEX | a bytes value dumped or logged as hex |
| base64, base64url, each at the three alignments | HTTP Basic credentials; cloud-init `write_files` with `encoding: b64` (the seed path); a base64 JSON document or archive; JWT-like tokens. The needle is the encoding of the groups lying wholly inside the value, so it matches wherever the value sits in a larger encoded stream |
| UTF-16LE, UTF-16BE | Windows wide strings (PowerShell transcripts, the registry, .NET, credential blobs) |
| body (each form above) | a copy with the public prefix stripped |
| raw fragments | windows of 16 body characters at a stride of 8: any raw run of 23 body characters is found (a truncated or masked copy) |

**Views:** the raw bytes, read in 1 MiB chunks that overlap by the longest needle less one byte (a copy split
across a read boundary is found once); a blob starting with the gzip magic also decompressed, every member,
bounded; an SQLite database also row by row from an in-memory copy (a value split across overflow pages is whole
there; the file is never opened by SQLite); a tar stream member by member, with member names and link targets;
an HTTP/1.x capture also message by message, de-chunked (a copy split across two chunks is whole there) and
decoded from gzip or deflate.

**Surfaces:** `capture`, `http` (in memory), `file`, `tree` (links and junctions not followed, counted), `tar`,
`environ`. Each reports `searched`, `complete`, bytes per view, items, `unreadable` and `incomplete` by error
type, `not_followed`, `found` (needle occurrences), matches per form and per view, and `where` (names, withheld
when a name holds a match).

**Positive controls** (`Search.controls()`): 16 carriers made by the standard library's encoders (raw, JSON,
`urlencode`, `quote`, hex, HEX, base64 and base64url at three alignments, UTF-16LE/BE, the body, a fragment),
planted in memory in every kind of surface and view: a capture, a copy across the read boundary at the real
chunk size, gzip, a file, an SQLite row, an SQLite row split across an overflow page (the raw view must find no
whole copy), an HTTP body split across two chunks (likewise), a gzip-encoded HTTP body, an environment variable,
a tree, a tar stream plain and gzip-compressed, and a member *name* holding the key (which must be withheld): 191
cases. Each must be found **in the view it controls**; the verdict is `invalid` otherwise. A surface may also be
declared to hold the key (`expect='present'`); missing it there makes the verdict `invalid`.

**Verdicts:** `found` (a match on a surface expected not to hold the key) before `invalid` before `incomplete`
before `not-found`. The `not-found` statement reads: "the key (fingerprint) was not found, raw or in any listed
form, in the N bytes of the M surface(s) expected not to hold it, and the positive controls found every planted
copy. This covers those bytes only: it is not proof that the key is absent anywhere else (see not_covered)".

**Never kept:** the key from standard input only (a terminal refused), the synthetic shape required (the
launcher's, asserted equal in a test), and the key of `--expect-fingerprint` (the start receipt's); every
refusal is by stable code without what was read; the report is searched for the key in every form before it is
printed and withheld if it holds one (`OUTPUT_WITHHELD`, exit 1); the module calls no `print`, imports no
`logging`, `tempfile`, `socket`, `http` or `subprocess`, opens files `rb` only and SQLite `:memory:` only (a
syntax-tree test), and a command-line test sees nothing on `sys.stdout`/`sys.stderr`, only `rb` opens and its
directory unchanged.

## 4. Wired for the live qualification (prepared, not run)

- `tools/guest.py inspect --provider-key-fingerprint FP --provider-key-stdin`: the synthetic key (one line of
  standard input, the key of FP) searched for in the P5 collection and in `seed.iso`, `launch.json`,
  `serial.log`, on the host, in memory (`provider_key_search`). A new P5 check, `provider key itself, raw and
  encoded (synthetic key, S-03.2)`: PASS on `not-found`, FAIL on `found`, UNKNOWN on `incomplete` or `invalid`,
  and, **for a guest with the inference composition, UNKNOWN without the search** (a choice of this slice: the
  fingerprint check stays as decision 0015 section 4.5 has it, but a P5 PASS no longer rests on it alone). A
  record that would hold the key is not written.
- `tools/guest.py job-access-probe --attempt-token-stdin --provider-key-stdin --provider-key-fingerprint FP`
  (the token, then the key, on standard input): the job's token script returns each answer whole up to 64 KiB
  (`answer_b64`, else `answer_omitted`); the host takes it out of the result before anything is recorded, keeps
  it in memory, and a new step searches the guest login's answer and the token step's three answers
  (`forward_answers_search`); a found key is a stop condition, an omitted answer a failure.
- `inference_key_search.py search` for the host-side surfaces.

**The prepared order** (each command in the Owner's PowerShell session; steps of the slice 3 plan in brackets):

1. Record acts A2, A3, A4 (slice 3 plan step 0). Make the key in the session's memory, never typed or shown:
   `$k = 'aieh-qualification-synthetic-' + [Convert]::ToHexString([Security.Cryptography.RandomNumberGenerator]::GetBytes(24)).ToLower()`.
2. Fake upstream with its records to a file in a reports directory outside the checkout; then
   `$k | <tools python> -I -B integrations/inference/inference_qualification.py broker --provider ID`, standard
   output and error redirected to files there; FP is the fingerprint on its standard error (and in the start
   receipt) (steps 2 to 4).
3. `create --provision --inference`, `inspect`, `inference-forward --action start` (steps 5, 6).
4. `& { <tools python> -I -B integrations/inference/inference_control.py issue ...; $k } | python -I -B
   tools/guest.py job-access-probe ... --attempt-token-stdin --provider-key-stdin --provider-key-fingerprint FP`
   (steps 7, 8).
5. Containment catalogue (step 9).
6. `$k | python -I -B tools/guest.py inspect ... --provider-key-fingerprint FP --provider-key-stdin` (step 10).
7. Stop the forward, the broker and the fake upstream; then `$k | <tools python> -I -B
   integrations/inference/inference_key_search.py search --expect-fingerprint FP --surface instance=tree:<instance
   directory> --surface reports=tree:<reports directory> --surface store=tree:<managed root>\state\integration
   --surface audit=tree:<managed root>\persistent\logs\inference --surface shell=environ:self`; then
   `Remove-Variable k`.
8. Acceptance reads the three verdicts (the job-access-probe step, the inspect P5 check, the search command),
   never the broker's own report.

## 9. Not covered, not verified, findings

- **Not covered by any search here:** process memory (the broker holds the key there by design); bytes on no
  listed surface; forms outside section 2 (two encodings stacked, encoded fragments such as line-wrapped base64,
  case-changed text, encryption, a hash of the key, compression other than gzip and HTTP gzip/deflate: zip, xz,
  bzip2, zstd, compressed disk-image clusters); a copy split across storage that is not contiguous (disk-image
  clusters; text split across server-sent events or JSON fields); SQLite write-ahead-log frames never
  checkpointed (raw view only). The report lists these in `not_covered`.
- **The jobs, live:** the P5 collection runs as the agent user, so a container's writable layer and the
  environments of processes it cannot read (root's, counted in `unreadable-pids`) are not in it; the job's own
  view is covered by the answers it received (all the plane sends it) and the existing in-job fingerprint scan
  of 43-character tokens, which does not find this key. Searching a container's filesystem for the raw key would
  need the key in the guest or the container's contents brought out; neither is built.
- **Not verified:** everything in section 4 (acts A2, A3, A4); the PowerShell script block that pipes the token
  and then the key into `job-access-probe` (and `issue`'s pipe check inside it); `ToHexString` on the Owner's
  PowerShell; the answer capture through the Agent Server's bash route; Linux and macOS.
- **Finding (a), not changed:** the broker relays the upstream's answer (status, headers except those it does not
  relay, body) untranslated and does not scan it for the key, as decision 0015 section 3.2 designs ("the broker
  translates nothing"); an upstream that echoes the key would put it on the forward. The planted reflecting
  upstream shows this search finds such a copy. The qualification's fake upstream answers a fixed text and
  cannot echo it; whether a real provider's answers (for example an error that repeats a key, masked or not) can
  is S-03.3's to establish with the real key. Not a leak by the broker's own behaviour, so not a stop condition
  of the dispatch; reported for the Overseer.
- **Choice made (b):** for an inference-opted guest, `inspect`'s P5 is UNKNOWN unless the key itself was
  searched (section 4). Reversible: one condition in `p5_checks`.
