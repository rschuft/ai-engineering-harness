## 2. The checker

`tools/check_network_matrix.py` (`task policy:network-check`), with 23 offline tests in
`tools/tests/test_check_network_matrix.py`. It fails when:

1. an ordered domain pair has no row, an untrusted or contained domain has no external row, or a
   row cannot be classified (verdict, status, protocol, endpoint, enforcement kind or place) or
   carries an unknown key;
2. an `allow` from an untrusted or contained domain into a trusted one (or the TCB) names no
   profiles P7 class other than `management`, targets a management or credential asset, or uses
   a privileged credential;
3. an `allow` names no prevention mechanism, a `disclosed` row no finding, a `deny` no
   enforcement;
4. an id does not resolve (domains, externals, assets, credentials, findings, plan leaves,
   profile endpoints), an inventory asset has no class, or a class contradicts the asset's kind
   or privileged credentials;
5. an `observed` row lacks evidence or an inspection command, a `planned` row a leaf, a
   `decided` row a decision source or its building leaf;
6. an active profile's endpoint or `launch.argv` forward is in no `allow` row (active: provider
   validation passed);
7. an observed Owner act lacks a bootstrap-log approval quoted verbatim;
8. a machine path appears, the README omits an edge id, or its generated block differs from
   `--render`.

Every failure code was killed by a test in a rule-disabling sweep (each code dropped in a scratch
copy of the checker in turn: 18 of 18 killed). Wrongly typed values give named failures, never
exceptions (type fuzzing in the tests).

## 5. The egress sweep

**Targets (predeclared):** TCP `1.1.1.1:443` and `8.8.8.8:53`, UDP `8.8.8.8:53` (public
literals); TCP `10.0.2.2:{ssh_port}`, `10.0.2.2:{qmp_port}`, `10.0.2.2:13300` (SLIRP's host
loopback alias: the SSH forward, QMP, the host Gitea), TCP and UDP `10.0.2.3:53` (SLIRP's
resolver alias); TCP `10.0.2.100:7000` (an unconfigured guestfwd-class address). One attempt per
target from each of the two jobs, as the container's default user, 4 s ceiling.

**Decision rule (the dispatch's, fixed before observation and coded in `egress_verdict`):** PASS:
every target refused with the guard's reset or ICMP reject (ECONNREFUSED) and the guard's REJECT
counters incremented; FAIL: a timeout or "network unreachable" alone (topology, not policy);
STOP: any connection. Stated before the run as well: the profile's `egress_guard.rule` (commit
`d084b8d`) records that off-link destinations have no route in the guest and are answered by the
guest's routing before FORWARD; S-01.3.2's exploration had seen `8.8.8.8` "Network is
unreachable" from a container.

**Observed (identical in A and B):**

| Target | Both jobs | Attribution |
|---|---|---|
| TCP 10.0.2.2:{ssh_port}, :{qmp_port}, :13300 | ECONNREFUSED (0.01 s) | the guard: counters and log lines `aieh-egress-guard: IN=docker0 OUT=enp0s4 … DST=10.0.2.2 … DPT=<port> SYN` |
| TCP 10.0.2.3:53 | ECONNREFUSED (0.01 s) | the guard (counter, log) |
| UDP 10.0.2.3:53 | ECONNREFUSED (ICMP port-unreachable) | the guard's final REJECT (counter); SLIRP alone drops UDP (a timeout) |
| TCP 10.0.2.100:7000 | ECONNREFUSED (0.01 s) | the guard (counter, log); without it SLIRP answers no ARP for an unconfigured address |
| TCP 1.1.1.1:443, 8.8.8.8:53 | ENETUNREACH (0.00 s) | the guest's routing: no default route, so the packet never reaches FORWARD |
| UDP 8.8.8.8:53 | timeout (4.0 s) | the same; the guard's counters did not move for it |

Counters of `AIEH-EGRESS-GUARD` (IPv4, read from the on-demand root facts before and after the
sweep), in chain order RETURN, LOG, REJECT tcp-reset, REJECT: before `[0, 14, 14, 0]` (the
earlier S-01.3.2 step's 14 SLIRP-alias attempts, now also refused by the guard), after
`[0, 26, 24, 2]`: **+10 tcp-reset and +2 REJECT, exactly the 10 TCP and 2 UDP attempts that were
refused**; +12 log lines. IPv6 counters stayed 0 (the containers have no IPv6).

**Verdict under the fixed rule: FAIL** for the four public-literal attempts per run (ENETUNREACH
and a UDP timeout: topology, not policy); every other target PASS, with exact counter
attribution. **No connection, so no stop condition.** The deny holds for every target; for
off-link destinations it is held by topology (no route out, and SLIRP `restrict=on` behind it),
not by the guard. Reported, not changed: making the guard engage there would need a guest
default route or another routing change, which no ruling authorizes (it is a topology change,
and outside this leaf's bounds). Carried in `fd-container-network-deviations` and in the matrix
(`nm-ext-job-egress`, `nm-ext-review-egress`).
