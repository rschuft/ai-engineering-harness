## 1. What was built

**The allowlist (`profile.json` `guest_storage`).** This is the guest's complete approved
volume and mount table.
- **`block_devices`.** Each entry names its QMP node, file node, file, serial and
  read-only flag:
  - `root`: the overlay, with its read-only backing image;
  - `scratch`;
  - `seed`: a read-only, never-mounted configuration medium (P4 amendment).
- **`mounts`.** 25 entries:
  - `/` and `/boot/efi` on the root disk, and `/srv/scratch` on the scratch disk;
  - the image's own kernel, systemd and tmpfs mounts, each with its file system type and
    source;
  - three optional entries, each with a reason: `binfmt_misc` under its autofs trigger,
    `/run/credentials/*`, and `/run/user/1000`.
- **`directories`.**
  - exchange: `/home/agent/exchange`, `agent:agent`, mode `750`, on `/`;
  - scratch: `/srv/scratch/agent`, `agent:agent`, mode `750`, on `/srv/scratch`.
- **`forbidden_fstypes`.** The contract's share types and `fuse`.
- **`forbidden_paths`.** `/mnt/c` and `/mnt/wslg`.
- **`virtio_devices`.** Block 3, net 1, entropy 1.

**The exchange section (`profile.json` `exchange`).**
- the guest directory;
- staging under `{instance_dir}/exchange`;
- push bounds: 1 ref, 10,000 commits, 256 MiB, and a lower-case `.bundle` name pattern;
- pull bounds: 256 MiB, and a name pattern that admits no path separator.

**`tools/check_profile.py`** validates both sections. For QEMU, it checks the volume
table against `launch.argv` exactly:
- the node names, files, read-only flags, the backing node and the serials;
- no `-blockdev` or `virtio-blk-pci` that is not declared;
- the virtio counts.

24 new mutation tests make it FAIL.

**`tools/guest.py`.**
- **`exchange-push`.**
  - Exactly one `refs/heads/` branch, as a complete bundle within the bounds.
  - The bundle is built read-only from the named repository, by git with no system or
    global configuration, hooks disabled and a scrubbed environment.
  - Checks: the header (one ref, no prerequisites), the pack trailer recomputed, and
    `git bundle verify`.
  - It is sent by `sftp.exe -S <built-in ssh.exe> -F none …` with the per-instance key,
    to `<name>.partial` and then renamed. It never overwrites a guest file.
  - Finally the guest's `stat` and `sha256sum` are compared with the host's.
- **`exchange-pull`.**
  - One regular file of the exchange directory; a symbolic link is refused, and the size
    is bounded.
  - It lands in `<instance>\exchange\inbound\` through a `.partial` file, and the sha256
    is compared with the guest's.
  - A bundle is checked:
    - its header and pack trailer;
    - it is fetched into a fresh bare repository in the staging directory, after the
      pushed bundles only if it has prerequisites;
    - each reference is compared with its header;
    - then `git fsck --strict`.
  - Nothing is written to any Owner repository.
- **`canaries`, and `create --canaries`.** These plant the P5 canary set (section 3).
- **`inspect`.** It now records P3 to P6 as formal checks (sections 2 and 3).
- **`check-surfaces`.** This is the startup inspection test: `inspect` with a canary set.
  It exits 0 only when P3, P4, P5 and P6 are all PASS; UNKNOWN does not pass.

**Task targets.** `guest:push`, `guest:pull`, `guest:canaries`, `guest:create-canaries`
and `guest:check-surfaces`, with their direct commands in `docs/development.md`.

## 2. Method

1. **Reconnaissance (`f0331-r`, profile at `002431a`).**
   - `create`, then two read-only `exec` probe scripts:
     - `findmnt -J`, `lsblk -J`, `/sys/bus/virtio/devices`, `find -type s`, `ss -xlH`;
     - `stat` of the directories and `/proc/1/environ`;
     - cloud-init file modes, `env`, the tools present and `AcceptEnv`;
     - an AF_VSOCK probe and `ssh-add -l`;
     - a dry-run `tar | wc -c`.
   - An SFTP put, rename and get of a one-line synthetic file.
   - Then `destroy`.
   - The pseudo-mount part of `guest_storage.mounts` was declared from this observation;
     the root, scratch, seed and directories follow `launch.argv` and the seed template.
2. **The allowlist and the tools were committed (`0a0b5cc`) before any verification boot.**
   `create` refuses uncommitted changes under `profiles/`.
3. **Verification:** two fresh instances, each with its own fresh canary set and its own
   per-instance key. The commands were rendered mechanically from each Task target's
   `cmds` line (Task is not installed). `<scratch>` is a session scratch directory
   outside the checkout and the state directory.

   ```
   python -I -B tools/guest.py preflight --profile "profiles/strong-windows-qemu-whpx" --state-dir "D:\aieh-guest-state"
   python -I -B tools/guest.py canaries --out "<scratch>\f0331w\canaries"
   python -I -B tools/guest.py create --profile "profiles/strong-windows-qemu-whpx" --state-dir "D:\aieh-guest-state" --name "f0331-w" --canaries "<scratch>\f0331w\canaries"
   python -I -B tools/guest.py exchange-push --profile "profiles/strong-windows-qemu-whpx" --state-dir "D:\aieh-guest-state" --name "f0331-w" --repo "<scratch>\f0331v\fixture-repo" --ref "main"
   python -I -B tools/guest.py exec --profile "profiles/strong-windows-qemu-whpx" --state-dir "D:\aieh-guest-state" --name "f0331-w" -- "cd /home/agent/exchange && sha256sum -- f0331-w-20261106t165814z-2e03a7b6b1b7.bundle > push-receipt.txt"
   python -I -B tools/guest.py exchange-pull --profile "profiles/strong-windows-qemu-whpx" --state-dir "D:\aieh-guest-state" --name "f0331-w" --file "f0331-w-20261106t165814z-2e03a7b6b1b7.bundle"
   python -I -B tools/guest.py exchange-pull --profile "profiles/strong-windows-qemu-whpx" --state-dir "D:\aieh-guest-state" --name "f0331-w" --file "push-receipt.txt"
   python -I -B tools/guest.py check-surfaces --profile "profiles/strong-windows-qemu-whpx" --state-dir "D:\aieh-guest-state" --name "f0331-w" --canaries "<scratch>\f0331w\canaries"
   python -I -B tools/guest.py destroy --profile "profiles/strong-windows-qemu-whpx" --state-dir "D:\aieh-guest-state" --name "f0331-w"
   python -I -B tools/guest.py preflight --profile "profiles/strong-windows-qemu-whpx" --state-dir "D:\aieh-guest-state"
   ```

   Cycle 1 (`f0331-v`) ran the same sequence. Its `exec` also appended `stat` and the
   bundle's first 16 bytes to the receipt. Each step exited 0, except cycle 1's first
   `destroy` (Defect 1).

### P5: canaries, the Owner-class scan and the key
**Canary design.** All values are synthetic. Each holds a fresh 128-bit random core; the
search looks for the full value and for its core. The set has 13 labels.
- **Environment of the process that runs `create`.** QEMU inherits a scrubbed copy of it.
  - `AIEH_CANARY_ENV`, and `AIEH_CANARY_API_TOKEN` (a credential-looking name);
  - `GITHUB_TOKEN` (`ghp_`-shaped), `ANTHROPIC_API_KEY` (`sk-ant-`-shaped),
    `AWS_SECRET_ACCESS_KEY`;
  - `DOCKER_HOST`, a fake `tcp://…invalid` URL. It is also a P6 tripwire.
  - `LC_AIEH_CANARY`. The guest's sshd has `AcceptEnv LANG LC_* COLORTERM NO_COLOR`, so
    any client that sent it would deliver it to the agent's session.
- **A fake home, with `HOME` pointed at it.** HOME is what git and MSYS tools read, and
  the git under `create` inherited it. The home holds `.ssh/id_ed25519`, a key-shaped
  file, and `.ssh/config`, which has `SetEnv LC_AIEH_CANARY_SSHCONFIG=…`,
  `ForwardAgent yes` and `IdentityFile`. It also holds `.git-credentials`,
  `.aws/credentials` (with an `AKIA`-shaped id) and `.gitconfig`. A careless client that
  read this home would have forwarded the canaries or used the fake key.
- **Values never travel to the guest.** The guest's data comes to the host and is
  searched there. Records carry the label and the sha256 of each value only.

### P6: host-management surfaces
- **QMP:** `query-chardev` lists `qmp` and `serial0` only, and `/dev/virtio-ports` is
  absent: `ls: cannot access '/dev/virtio-ports': No such file or directory`.

  - The local CID is 1 (`VMADDR_CID_LOCAL`), so no guest-to-host transport is
    registered. Without one, Linux hands a connection to CID 2 to the loopback

    `vsock_use_local_transport`).
- **Host-management paths absent:**
  - `/var/run/docker.sock`, `/run/docker.sock`;
  - podman, containerd, Incus, LXD and libvirt sockets;
  - `/mnt/wslg`, and the per-user docker and podman sockets.

  `SSH_AUTH_SOCK`, `PULSE_SERVER`, `LIBVIRT_DEFAULT_URI`, `INCUS_SOCKET` and `LXD_SOCKET`
  are `unset` in the SSH session and in the login shell.
- **Socket inventory.**

## 7. Defects

1. **`destroy` could not delete read-only files. Introduced by this leaf, fixed forward.**
   - Git for Windows writes pack files (`objects/pack/*.idx`, `*.pack`) read-only, and
     `exchange-pull` creates its verification repository inside the instance directory.
   - Cycle 1's `destroy` raised `PermissionError: [WinError 5] Access is denied:
     '…\exchange\verify\…bundle.git\objects\pack\pack-10fa99f1….idx'`, after QEMU had
     already exited.
   - **Fix:** `remove_tree` clears the read-only attribute and retries. It does this only
     for entries inside the instance directory, never through a link (`destroy` already
     refuses links), and re-raises any other error.
   - **Validated by:**
     - a unit test with a read-only file inside the instance (removed) and one outside
       (left untouched);
     - the real second `destroy` of `f0331-v`;
     - the complete cycle `f0331-w`.
2. **Found before commit `0a0b5cc` by the tests or the gate, and fixed. Introduced by
   this leaf's own uncommitted work; no committed history was affected.**
   - `git rev-parse --symbolic-full-name --end-of-options <ref>` echoes
     `--end-of-options`. Branch names are now validated, and `--verify` is used.
   - A tampered pulled bundle passed, because the verification repository already held
     the pushed objects. Now the pack trailer is recomputed, and the pushed bundles are
     fetched first only when the pulled bundle has prerequisites.
   - The publication gate rejected the first commit attempt for two reasons:
     - a literal private-key block in the canary text: the armour is now assembled at
       run time;
     - personal-path fixtures in the tests: these now use the gate's generic `user`.
   - No allowlist was changed, and `--no-verify` was not used.
3. **Exposed by this leaf (not a defect of the profile): `sftp rename` overwrites.** In
   the reconnaissance guest, an SFTP `rename` onto an existing file succeeded (OpenSSH's
   `posix-rename`). `exchange-push` therefore checks, before it puts, that both the
   target and its `.partial` are absent.

## 8. Limits and inferences

- **The scan is the agent's view.** The scan runs as `agent` without sudo, so root-only
  guest files are not read (listed in section 3). The seed is scanned on the host
  instead. A guest root process is outside this test.
- **The P6 socket check is a deny-list, not an exact table.** The guest's own sockets
  vary with systemd units. The check:
  - refuses host-management names;
  - requires the channel devices to be absent;
  - requires no guest-to-host vsock transport;
  - records the full inventory.

  An exact guest-socket allowlist is not declared.
- **The test is a startup inspection.** It does not cover what a later guest-root process
  could mount or start (S-02.x).
- **The pseudo mounts came from observation.** The pseudo-mount entries of the allowlist
  were taken from one observed guest of this image. A new image or kernel may change
  them; the exact comparison will then FAIL until the declaration is re-derived.
- **Exchange staging is inside the instance directory.** It satisfies the binding (under
  `{state_dir}`, harness-owned, never an Owner repository), but `destroy` removes it.
  Where exported evidence should outlive a `fresh`-mode guest is not decided here (open
  item).
- **`strong-incus-vm`.** No Incus host exists, so its effective mount table cannot be
  observed. `check_profile.py` requires `guest_storage` and `exchange` for QEMU profiles
  only, and the Incus profile declares neither (open item).
