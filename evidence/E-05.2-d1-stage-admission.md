## 1. Design

- **Where the template lives.** `profiles/strong-windows-qemu-whpx/agent-server/d1-create.json`, a CANDIDATE.
  - Its fields are exactly E-01.2.2's body allowlist; there is no `secrets` field.
  - Its `agent_settings` is S-03.3 slice 2's ACP block: `agent_kind acp`, `acp_server claude-code`,
    `acp_command ["claude-agent-acp"]`, `acp_args []`, `acp_session_mode null`, `acp_isolate_data_dir true`,
    `mcp_config {}`.
  - `acp_model` is the sentinel `candidate-unselected`. No model is selected before S-03.3 (decision 0018
    point 3, S-03.5), and none is named from memory.
  - The tag is `e-05.2-d1-candidate`. sha256 `4cc5dde4bdb16ac6c42be30252a4ad6d4a8800f3daf11d5efdf82676615b1f47`.
- **How its digest is pinned, and by whom.** The profile declares
  `provisioning.agent_server.stage_create_template` `{stage, path, sha256}`.
  - There is one declaration per profile, for the D1 stage only. A-01.2 still owns the general per-stage
    materialization from role profiles.
  - The profile is approved by sha256 in a promoted manifest (decision 0020), so the template is reachable
    only through it.
  - `admission_policy(declared, profile, stage)` puts the pin in the policy's `create_template` for the named
    stage. The policy-inputs/v2 shape is unchanged, so the policy digest, and with it the reserved attempt
    identity, binds the template's sha256. No code constant duplicates the pin.
- **How the D1 stage is identified.** It is the stage the approved profile's `stage_create_template.stage`
  names. For D1 that is `implement`. A profile without the declaration, and every other stage, keep E-01.2.2.
- **The agent block and how it is compared.** The agent block is `agent_settings`.
  - The body is built from the pinned template, with only the reserved conversation id replaced.
  - Every allowlisted field is compared with the template as canonical JSON. An agent block other than the
    template's is `BODY_NOT_TEMPLATE` (field `agent_settings`).
  - The template itself must carry an ACP block. Its content is approved by its digest and never re-derived.
- **Refusals.** The two new codes are appended to `REFUSALS`.

  | Rule | Where | Code |
  |---|---|---|
  | the declaration names a known stage and pins a file under `profiles/<id>/` by sha256 | resolution, any stage | `PROFILE_ADMISSION_INVALID` |
  | it does not pin the profile's F-04.2 fixture (same path or same sha256) | resolution, nothing reserved | `STAGE_TEMPLATE_DISPOSABLE` (new) |
  | the template is not tagged disposable (a tag value ending `-disposable`) | admission and `send_create` | `STAGE_TEMPLATE_DISPOSABLE` |
  | the template carries `agent_settings` with `agent_kind` `acp` | admission and `send_create` | `AGENT_BLOCK_NOT_ACP` (new) |
  | the reserved policy's create template is the stage's pin | admission and `send_create` | `ADMISSION_MISMATCH` |
  | the body's agent block is exactly the template's | admission and `send_create` | `BODY_NOT_TEMPLATE` |
  | the template's bytes have the pinned sha256 | admission and `send_create` | `PROFILE_ARTIFACT_DRIFTED` |
  | the carried approved profile has the reserved profile digest (since `d9e9ebe`) | `send_create` | `PROFILE_DRIFTED`, `PROFILE_MISSING` |

- **The send re-check (since `d9e9ebe`).** `send_create` takes no profile reader. The `AdmittedCreate`
  therefore carries the approved profile's bytes (`profile_bytes`), as it already carried the template and the
  route allowlist. The send re-checks those bytes against the reserved profile digest and re-runs the content
  checks when they declare the attempt's stage as the D1 stage.
- **The real profile is not edited.** Pinning `implement` in the checked-in `strong-windows-qemu-whpx`
  declaration would change two things:
  - the existing assertion of `test_dispatch_admission.PositiveControlTests.test_the_checked_in_profile_declaration_admits_when_operational`,
    which admits that declaration on `implement` with the F-04.2 fixture;
  - the real profile's `implement` path, which the live drills and E-01.3.2's disposable attempt use.

  That is a STOP condition of the dispatch, returned as a finding. The engineering manager records the
  profile-pin decision.

## 7. Discovered: the D1 create's inference secrets

The real D1 create needs the inference attempt token and the guest inference endpoint. S-03.3's create
carries them as `secrets` (`ANTHROPIC_API_KEY`, `ANTHROPIC_BASE_URL`, both `StaticSecret`). E-01.2.2's body
allowlist refuses `secrets` (`BODY_FIELD_UNKNOWN`), and no D1 leaf (E-05.1 to E-05.5) adds them. E-05.2 does
not add them. The engineering manager raises the gap to planning.
