# E-01.4.3: the Agent Server start-up import race

- **Date:** 2026-11-09 (UTC).
- **Plan leaf:** E-01.4.3, "Eliminate or bound the Agent Server start-up import race". From the
  locked 1.60.1 source and the E-01.2.2(c) journals (finding F-15; E-01.2.2(b) F-5), establish
  the root cause of the intermittent start failure; adopt an upstream configuration control that
  removes the trigger, declared in the profile and requalified, or record why none exists; declare
  the start path's failure handling so that a retried or slow start is reported as such, never as a
  clean start; prepare the upstream report.
- **Decision rule (fixed before observation, from the plan; not altered).** With a control: 0
  main-process exits during start in at least 500 consecutive Agent Server restarts on a fresh
  disposable guest at the fixed commit, and the requalification the profile rules require passes.
  Without a control: every failed start retried to readiness within the declared ceiling, the
  distribution recorded, the limit recorded. Either way, the readiness wait reports a retried or
  slow start distinctly.
- **Profile:** `profiles/strong-windows-qemu-whpx`. **Labels (profiles P11):** `tier: strong`,
  `provider: qemu-whpx`, `nesting: none`.
- **Authority:** the plan leaf and the Overseer's dispatch; the Owner's extended guest-run
  authorization of 2026-11-07: "Moby and the Agent Server may run in disposable guests for any plan
  leaf's containment, admission and lifecycle testing, under the existing isolation conditions: no
  LLM or model credential, no repository content, no untrusted workload, no guest network,
  guestfwd, host share or new host port." Decisions 0003 and 0006 apply unchanged.
- **Commits:** `574d8db` (the control, the readiness wait, the boot facts, the inspect check, the
  restart-series drill and their tests; the fixed commit of every run), the commit that adds this
  file (documentation only), and the budgets re-proposed after it.

**Verdicts in short.**

- **Root cause: established** for the trigger and the failing path, from the bundled source and
  the journals (section 1); one link, which module lock the second thread waits on, is not
  established (section 1.3).
- **Control: adopted.** `LITELLM_LOCAL_MODEL_COST_MAP=True`, litellm's documented switch, in the
  server unit's environment, declared in `provisioning.agent_server.start_race` (section 2).
- **Decision rule: PASS.** On the fresh guest `e0143-c` at `574d8db`: **500 consecutive restarts,
  0 main-process exits during start, 0 failed starts, 500 outcomes `start=clean`**. The
  requalification passes (section 6). The same series on a guest without the control (a defective
  control, `e0143-b`, run alongside) hit the race once: restart #220, the same ImportError.
- **Reporting: PASS.** The readiness wait now stops at once when the main process has exited (2.0 s
  instead of 280 s on #220), and its outcome line names the start: #220's retry said
  `start=retried … restarts=1`; a SIGKILLed server's `Restart=on-failure` start said
  `start=retried` on both guests; a slow or unverified start cannot say `clean` (unit tests; not
  observed live). `inspect` has a new stable check that fails on any start other than a clean one.
- **Upstream report:** prepared, **not filed** (section 9); the Owner routes it.

**Not claimed.**

- No LLM, model credential, message, repository content or untrusted workload entered any guest.
  The conversations are the pinned F-04.2 fixture (conversation-smoke) and the probes' own fixed
  ones. No guest network, `guestfwd`, host share, new host port, firewall rule or elevation.
- The drill guests are not profile instances (their seed carries the test-only root helper

- 0 in 500 is not proof that the race is gone; the control's case rests on the source (the path is

  pooled uncontrolled rate seen so far (3 in 772 starts), an unchanged server would also show 0 in

- The control does not reach conversation containers (section 2, finding F-2).
- No upstream patch. `status.operational` and every decision are unchanged.

## 1. Root cause

### 1.1 What the pinned binary contains

Temporary failure in name resolution); retrying in 2.3s` (the retry thread) and
`get_model_cost_map.py:672 - … Failed to fetch remote model cost map …` (the main thread). Seen on
the E-01.2.2c guests and on `e0143-b`.

### 1.3 The mechanism, from the source

1. `openhands/sdk/logger/logger.py:16` runs `import litellm` while the server's main thread is
   still importing the SDK: it holds the module import locks of that chain, `litellm`'s among them.
2. `litellm/__init__.py:563` calls `get_model_cost_map(url=model_cost_map_url)` during that import.
3. `get_model_cost_map` (`get_model_cost_map.py:618`) checks `LITELLM_LOCAL_MODEL_COST_MAP`
   (`:643`); unset, it tries the remote fetch once. Offline the fetch fails with a retryable error,
   so it **starts the daemon thread `litellm-model-cost-map-retry`** (`:657-670`), then logs its
   own warning (`:672`).
4. The thread's first act, before it sleeps, is `_next_retry_wait` (`:309`), which **logs a
   warning** (`:315`). Two threads now log through the `LiteLLM` logger at the same moment while
   `litellm` is still initializing (`mark_litellm_import_complete()` runs only at
   `__init__.py:2548`; the thread waits for it, `:599`, only before adopting a fetched map, not
   before logging).
5. The `LiteLLM` logger carries `DiagnosticProcessingFilter` (`_logging.py:886`); its `filter`
   (`:551`) calls `_process_record`, which calls `diagnostics.run` (`:455`), which **imports
   `litellm.rust_bridge.catalog` lazily, on first use** (`rust_bridge/diagnostics.py:47`). That
   first import executes `catalog.py`, which imports `litellm.types.secret_managers.main`
   (`catalog.py:15`) and, through it, more modules.
6. Two threads perform that first import concurrently while the main thread holds `litellm`'s
   import lock. CPython's per-module import locks detect a cycle in the wait graph, and the wait for
   a module another thread is initializing (`Python/import.c` `import_ensure_initialized`, then
   `importlib._bootstrap._lock_unlock_module`, `_bootstrap.py:463-477` at v3.13.18) **swallows
   `_DeadlockError` and returns the partially initialized module** ("Concurrent circular import,
   we'll accept a partially initialized module object"). The main thread's from-import then finds no
   `LoggerContext` yet; the ImportError leaves `import litellm`, the bootloader's child dies and the
   parent exits 1.

**Not established:** which module lock the thread side waits on to close the cycle. A static
closure of `catalog.py`'s module-level imports inside litellm finds no statement that waits for
`litellm` itself, and a host reproduction did not reproduce the race: 600 fresh `import litellm`
runs of the same wheel on the Windows host (CPython 3.12.10, no PyInstaller, the fetch refused on a
closed loopback port so that the retry thread starts; importlib's `_lock_unlock_module` wrapped to
record any deadlock avoidance) gave 600 clean imports, 0 deadlock avoidances, 0 thread exceptions,
each with the cost-map warning. What is read from the source agrees with every observed line (the
thread name, the two warnings in the same second, every frame, the "partially initialized"
wording, which CPython produces only for a from-import of a module still initializing). It is
timing-dependent: 2 in 272 (E-01.2.2c), 1 in 500 (`e0143-b`), 0 in 600 on the host.

### 1.4 Why a failed start took five minutes

`aieh-agent-server.service` is `Type=exec` with `ExecStartPost=` (the readiness wait) and
`Restart=on-failure`. When the main process died at 1.5 s, systemd did not stop the running
`ExecStartPost`: the wait polled `/ready` to its 280 s ceiling, the start job then failed ("the
control process exited with error code"), and only then did `Restart=on-failure` apply. The wait
printed `not ready within 280.0 s`, the same line as for a server alive and slow.

## 2. The control

**`LITELLM_LOCAL_MODEL_COST_MAP=True`**, litellm's own switch (the docstring of
`litellm_core_utils/get_model_cost_map.py`: "This can be disabled by setting the
LITELLM_LOCAL_MODEL_COST_MAP environment variable to True"), set as an `Environment=` line of the
server unit in `profiles/seed/user-data.tmpl` and declared in `provisioning.agent_server.environment`
and `provisioning.agent_server.start_race` (root cause, control, scope, reconsider condition). With
it `get_model_cost_map` returns the map bundled in the pinned binary at `:643`, before any fetch:
no `litellm-model-cost-map-retry` thread starts and neither warning is logged during
`import litellm`. It removes the trigger (step 3 of 1.3), not merely its odds.

What else it changes:

- The start-up fetch of `raw.githubusercontent.com`, which always failed in the guest (no DNS, no
  route, `IPAddressDeny=any`), is no longer attempted: one outbound attempt fewer, the same
  isolation. No network, credential, host share, port, mount or capability changes.
- The cost map is the copy in the pinned binary instead of a live download: pricing and
  context-window metadata for LLM calls; the inspection-only server configures no LLM (decision
  0006).
- **Scope: the outer server only.** The 1.60.1 Docker runtime builds a conversation container's
  environment from a fixed list (`openhands/agent_server/docker_runtime/registry.py`,
  `forwarded_env_names`: `HOME`, the `OH_*` runtime variables, `DEBUG` and the observability
  variables). The variable is not on it and no server configuration adds one, so a container's inner
  server still fetches at its start, and can hit the race there: observed, its start logs both
  warnings (section 6); a container start failure was not observed. Recorded as the control's limit
  (`start_race.scope`, finding F-2) and in the upstream report. Changing the image or the container
  environment is outside this leaf.

## 3. Start-failure handling and its reporting

Declared in `provisioning.agent_server.service.readiness`; implemented in the seeded
`/usr/local/sbin/aieh-agent-server-ready` (the unit's `ExecStartPost`).

| | Before | Now |
|---|---|---|
| argv | `127.0.0.1 8000 280` | `127.0.0.1 8000 280 30 ${MAINPID}` |
| main process exits before ready | the wait ran to its 280 s ceiling, then the start job failed and `Restart=on-failure` applied (about 5 minutes per failed start) | the wait reads `/proc/<MAINPID>/stat` at its start and at every 0.5 s poll and stops **at once**, exit 1, when the process is gone, a zombie, or another process (a different start time); the job fails and `Restart=on-failure` starts the server again after `RestartSec=5` |
| alive but never ready | 280 s, `not ready within 280.0 s` | 280 s, `not ready start=timeout …` (inside `TimeoutStartSec=300`) |
| outcome line | `ready` for every successful start | `ready start=<class> seconds=<s> restarts=<n>`; `<class>` is `clean` only when ready within 30 s **and** the unit's `NRestarts` is 0, else the comma-joined `retried` (NRestarts > 0), `slow` (over 30 s), `unverified` (the count could not be read) |
| restart count | none | `systemctl show --property=NRestarts --value aieh-agent-server.service`, run by the wait as `openhands` over the system bus; it works under the unit's hardening (every outcome line on every guest carries a number; none says `unverified`) |

The systemd behaviour this relies on, observed: `$MAINPID` is set for the `ExecStartPost` of this
`Type=exec` unit (in the 1,005 series starts no live main process was read as exited); a running `ExecStartPost` is not
stopped when the main process exits (F-15); a `Restart=on-failure` start increments `NRestarts`
before its `ExecStartPost` runs (`restarts=1` after #220 and after each SIGKILL); a manual
`systemctl restart` sets it back to 0 (every series row; the manual restart after each SIGKILL).

The boot facts keep this boot's outcome lines (`agent_server.start`), and `inspect` has a new stable
check, **"Agent Server start (E-01.4.3)"**: the control in the unit's environment and in every
server process's environment (names only), `NRestarts` 0, and this boot's last outcome line
`start=clean`. A retried, slow, unverified or failed start fails it; an unparsable last line fails
it. "Agent Server service" already failed on `NRestarts` other than 0.

### 5.3 What the two series show

- The decision rule is met: 0 in 500 with the control, at the fixed commit, on a fresh guest, and
  the requalification passes (section 6).
- The race was live under the same conditions: the uncontrolled guest, run at the same time, hit it
  once. Pooled with E-01.2.2c, 3 in 772 uncontrolled starts.
- The path itself is gone with the control: no start of `e0143-c`, `e0143-x`, `e0143-q` or
  `e0143-s2` logged a `get_model_cost_map` line or a `raw.githubusercontent.com` URL in the outer
  server's start-up log (inspect's "Agent Server start-up log"), where every uncontrolled start
  logs both.
- A failed start now costs about 14 s instead of about 5 minutes, and it is reported twice and
  distinctly: `start=main-exited` for the failed attempt, `start=retried` for systemd's retry.

## 9. Upstream report (draft, to be filed by the Owner)

Not filed: filing is an external publication; the Overseer routes it. Primary: BerriAI/litellm

### To BerriAI/litellm

**Title:** `import litellm` can fail with "ImportError: cannot import name 'LoggerContext' from
partially initialized module 'litellm.rust_bridge.catalog'" when the model cost map fetch fails
(race with the `litellm-model-cost-map-retry` thread)

**Version:** litellm 1.105.1, as bundled in the OpenHands agent-server 1.60.1 Linux x86_64 release
binary (CPython 3.13.18). Later releases not checked.

**What happens.** In a process without network access, `import litellm` fails intermittently,
about 1.5 s after the process starts. A systemd service that imports litellm at start-up failed in
3 of 772 offline starts; the process exits 1:

```
Exception in thread litellm-model-cost-map-retry:
Traceback (most recent call last):
  ...
  File "litellm/__init__.py", line 563, in <module>
  File "litellm/litellm_core_utils/get_model_cost_map.py", line 672, in get_model_cost_map
  File "logging/__init__.py", line 1537, in warning
  File "logging/__init__.py", line 1670, in _log
  File "logging/__init__.py", line 1681, in handle
  File "logging/__init__.py", line 867, in filter
  File "litellm/_logging.py", line 551, in filter
  File "litellm/_logging.py", line 455, in _process_record
  File "litellm/rust_bridge/diagnostics.py", line 47, in run
ImportError: cannot import name 'LoggerContext' from partially initialized module 'litellm.rust_bridge.catalog' (most likely due to a circular import)
```

The traceback is the main thread's, from `import litellm`; the background thread's "Exception in
thread" header lines are interleaved with it.

**Why, from the 1.105.1 source.**

1. `litellm/__init__.py:563` calls `get_model_cost_map(url=model_cost_map_url)` while `litellm` is
   still being imported.
2. `get_model_cost_map` tries the remote fetch once. On a retryable failure (no DNS, connection
   refused) it starts the daemon thread `litellm-model-cost-map-retry` (`get_model_cost_map.py`
   lines 657-670), then logs "Failed to fetch remote model cost map" (line 672).
3. The thread's first act, before it sleeps, is `_next_retry_wait`, which logs "model cost map fetch
   attempt 1/3 failed" (line 315). Two threads log through `verbose_logger` at the same moment
   while `litellm` is still initializing; both lines carry the same timestamp on every offline start.
4. `verbose_logger` has `DiagnosticProcessingFilter` (`_logging.py:886`); its `filter` calls
   `_process_record` (`:551`), which calls `diagnostics.run` (`:455`), which imports
   `litellm.rust_bridge.catalog` lazily, on first use (`rust_bridge/diagnostics.py:47`).
5. When both threads make that first import while the importing thread still holds `litellm`'s
   import lock, the module locks can form a cycle; CPython's deadlock avoidance
   (`importlib._bootstrap._lock_unlock_module`) then returns the partially initialized module
   instead of waiting, and the from-import of `LoggerContext` fails. When that is the main thread,
   `import litellm` fails.

We could not establish which lock the background thread waits on, and 600 plain `import litellm`
runs on CPython 3.12 (Windows) did not reproduce it; the failure has only been seen in the
PyInstaller-built binary on CPython 3.13.18 (Linux).

**Workaround.** `LITELLM_LOCAL_MODEL_COST_MAP=True` (documented in `get_model_cost_map.py`): the
bundled map is returned before any fetch (line 643), so no thread starts and nothing is logged
during import. With it: 0 failures in 500 consecutive restarts; without it, under the same
conditions at the same time, 1 in 500.

**Suggested fixes** (any one removes the race):

- start the retry thread, or let it log, only after `mark_litellm_import_complete()` (the thread
  already waits for it before adopting a fetched map, but not before its first warning);
- import `litellm.rust_bridge.catalog` and the rest of what `diagnostics.run` needs eagerly in
  `_logging.py`, so that a logging filter never makes a first import during `import litellm`;
- do not fetch the cost map during import when the fetch has to be retried; defer it to first use.

**Environment.** Debian 13 guest without network (DNS fails at once), systemd service; the
agent-server imports litellm at start-up from `openhands/sdk/logger/logger.py:16`. Release binary
sha256 `b2fbcf8cf1495bdbef97f26583917bc188b765c71c181effc3e47c14da08ce72`.

### To OpenHands/software-agent-sdk (companion note)

**Title:** agent-server 1.60.1 can exit at start-up when offline (litellm cost-map retry-thread
import race); the workaround cannot reach conversation containers

- The 1.60.1 release binary bundles litellm 1.105.1, and `openhands/sdk/logger/logger.py:16`
  imports it at start-up, so the litellm race above makes the agent-server exit 1 during start-up in
  an offline deployment (3 of 772 starts here).
- `LITELLM_LOCAL_MODEL_COST_MAP=True` in the agent-server's environment removes it for that
  process (0 of 500).
- The Docker runtime builds the container environment from a fixed list
  (`docker_runtime/registry.py`, `forwarded_env_names`), so a deployment cannot pass the variable
  to the conversation container's server, whose start-up has the same import and logs the same two
  warnings. Consider setting it in the image, forwarding it, or a documented allowlist.
- Consider pinning a litellm release with the fix once there is one.
