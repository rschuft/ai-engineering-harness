## 4. The fixture, and why it stopped

The fixture is Gitea administration (`op-gitea-administration`), performed during bootstrap by the
Owner's account. Gitea's CLI cannot create organizations, collaborators or protection rules, so
`gitea_roles.py fixture` mints a short-lived token for `aieh-site-admin` with the CLI (scopes
`write:organization,write:repository`, nothing under `admin`), applies the fixture through the API
and revokes the token with `DELETE /api/v1/token`.

**What happened (one run, about 17:50Z).** The CLI minted the token (no password involved). The
tool's first API calls were refused; the call that raised was
`PUT /repos/aieh-authz-fixture/authz/collaborators/aieh-bot-planner`: **HTTP 403, "You must change
your password. Change it at: http://127.0.0.1:13300/user/settings/change_password"**.
`aieh-site-admin` still carries `must_change_password` from F-06.1 (the Owner has not signed in).

**Inference, not observed directly.** Gitea applies this refusal to every API call of that account:
it is the same per-request check that refuses unauthenticated calls on every route ("Only signed in
user is allowed to call APIs.", F-06.1 section 5 and this leaf's anonymous probes). The earlier
`GET /orgs/aieh-authz-fixture` and `GET /repos/aieh-authz-fixture/authz` therefore returned 403 rather
than 404, so neither creation request was sent, and nothing of the fixture exists. The tool's
`DELETE /api/v1/token` in its `finally` block met the same refusal, so **that admin token is most
probably not revoked**.

**The dangling token.** `aieh-site-admin`, token name `aieh-s0122-fixture-20261107T17…Z` (the exact
stamp was in the lost report; it is the only token of that account with this prefix), scopes
`write:organization,write:repository`. Its value existed only in the memory of the tool's process,
which has exited; it was never printed, logged, stored or put on a command line, and it was sent
only in `Authorization` headers. While the account must change its password, Gitea refuses it. Once
the Owner has changed that password it becomes usable by whoever holds the value, and nobody does.
**Owner action:** at the first sign-in as `aieh-site-admin`, delete it under Settings, Applications.

**Defect, introduced by this leaf and fixed forward.** The first version of `fixture()` revoked in a
`finally` block but let the exception discard its report, so the revocation outcome was lost. It now
(a) checks the token with `GET /api/v1/token` before any administration call and stops with
`ADMIN_FIRST_LOGIN_PENDING`, and (b) reports the revocation outcome in every outcome, naming the
token and the Owner's deletion step when it was not revoked
(`TestFixture.test_first_login_pending_stops_and_reports_the_unrevoked_token`,
`test_a_failure_midway_still_revokes_and_reports`).

**STOP.** Continuing would need the site administrator's first sign-in, which uses the human
account's password, so the dispatch's stop condition applies. The alternatives were refused:
clearing `must_change_password` with the CLI would falsify the first-login state that
`gitea:finish-first-login` verifies; giving a bot organization or administrator scope would break
the segregation under test.

**Planned fixture** (applied by the same command after the first sign-in; its unit tests use a fake
Gitea): organization `aieh-authz-fixture` (private), repository `authz` (private, default branch
`main`), collaborators builder and planner `write`, reviewer and verifier `read`, `aieh-owner` `write`
(Gitea admits only writers to a merge allowlist). Protection: `main` (no push, no force-push, merge
allowlist `aieh-owner` only, admin merge override blocked, one approval from the reviewer bot);
`work/*` (push allowlist planner and builder, no force-push); `**` (no push). Protected branches
cannot be deleted. It is to be kept as a documented fixture so that the live suite can rerun.

## 6. The revocation contract, exercised

During exploration a probe sent each of the four first-issue tokens once as a deprecated
`?token=` / `?access_token=` query parameter (Gitea answered 404). Gitea's router log may record
request URIs, and this leaf may not read Gitea's managed state outside its CLI and API, so this is a
**suspected exposure** (a trigger of the contract) caused by the leaf's own probe. All four tokens
were revoked and re-issued at once with `gitea_roles.py rotate <role>`:

| Role | Revoked fingerprint | `DELETE /api/v1/token` | Next call with it (`GET /api/v1/token`; repository read) | New fingerprint | New token check |
|---|---|---|---|---|---|
| builder | `sha256:d611a5f1ba72cd43` | 204 | 401; 401 | `sha256:2edcc7070632f15d` | 200, `write:repository` |
| planner | `sha256:366f833552e70875` | 204 | 401; 401 | `sha256:4d6ca76123e574f0` | 200, `write:repository` |
| reviewer | `sha256:924c6c59e2b95eac` | 204 | 401; 401 | `sha256:89283518bd0ba23e` | 200, `write:repository` |
| verifier | `sha256:37692cfefd5cbae8` | 204 | 401; 401 | `sha256:2ccc9194a8068394` | 200, `read:repository` |

Gitea fails closed at the revoked token's next call. **Receipt** (the contract's fields; the
integration-store receipt was not written, because no dispatcher exists and the integration store is
outside this leaf's write bounds): fingerprints as above; roles planner, builder, reviewer and
verifier; trigger `suspected-exposure`; revoker the token itself through `DELETE /api/v1/token`, run by
`owner-os-account` (the matrix names `gitea-site-admin`, whose path is unknown, section 3); affected
attempts none (no agent attempt has held a token). Gitea's audit logging is off by default and was
not enabled. Any copy of a revoked value in Gitea's log no longer authenticates.

## 7. Secret files and agent workspaces

**Agent workspaces in the guest.** No token store or managed-root path is mounted in, or exchanged
into, the execution guest:

- the strong Windows profile declares `host_shares: []`, and its launch has no 9p, virtiofs, fsdev,
  SMB, virtio-serial or vsock device. The only host files it names are pinned inputs (image,
  firmware, seed) and per-instance files below the instance directory, which is in the guest-state
  root, not the managed data root (`profiles/strong-windows-qemu-whpx/profile.json`);
- F-03.3.1 observed this at run time: P3, P4 and P5 PASS on two fresh guests (mount table equal to
  the declaration, no share device, no Owner-class secret, positive control found all five classes)
  ([evidence](F-03.3.1-guest-surfaces.md));
- the exchange is a git bundle over the management channel (P4); the bundle is the repository only;
- **new mechanical check:** `TestNoTokenStoreReachesTheGuest` (offline, in `task gitea:test`) fails
  if the profile gains a host share or a share-type device, if a launch path is anything but a pinned
  input or per-instance file, if the launch or exchange names the managed root, a profile variable,
  Credential Manager or Gitea, or if a seed template names Gitea, the managed root or a bot entry.

**Bootstrap limit (accepted, `fd-bootstrap-shared-identity`; decision 0010).** Host-side agents run
as the Owner's account. Any process of that account can read the `AIEH Gitea bot <role>` entries
(`CredReadW` needs no prompt), Gitea's `app.ini` and database, and can run Gitea's CLI, which mints a
token for **any** account, `aieh-site-admin` and `aieh-owner` included, without a password: this
leaf did exactly that for the site administrator. Decision 0010 puts same-account processes outside
the threat model; the boundary against agents is the guest, where none of this is reachable.
