## 3. What Gitea 28.3.0 can and cannot express

Scope vocabulary: the CLI's help gives examples; the OpenAPI document (`/swagger.v1.json`, version
28.3.0) lists `read:`/`write:` scopes of `activitypub`, `issue`, `misc`, `notification`,
`organization`, `package`, `repository` and `user`, plus `all`. Gitea's refusals also name
`read:admin` and `write:admin`. Token scopes are categorical.

| Intended by the matrix | Gitea 28.3.0 | Realization |
|---|---|---|
| Per-repository and per-branch reach of an agent token | **Not expressible in a token.** Realized by collaborator permission and branch protection (fixture, section 4) | shown (section 5) |
| Planner writes planning artefacts only (path level) | **Not expressible** in a token. Protected and unprotected file patterns exist on protected branches only | **unknown**: pending the planning-artefact layout (decision 0007, point 2) |
| Reviewer reads and reviews only | **No review-only scope.** A review with `read:repository` answers 403 `required=[write:repository]` (the reviewer's own read-scoped probe token). Read permission bounds it, but a read collaborator can open a PR (201) | **failed in part** (`fd-gitea-reader-opens-pr`) |
| Token bounded to one attempt | **Not expressible:** no token lifetime in the CLI or in `CreateAccessTokenOption` (name and scopes only). Rotation is the fallback | rotation shown; per-attempt delivery **unknown** (no dispatcher, S-01.3.1) |
| Site administrator revokes a bot's token | The CLI has no token deletion. The administrator, by basic authentication, lists another account's tokens (200) and deletes one (204); that token then answers 401 | **shown** (section 7) |
| Bots have no interactive sign-in | A Bot account has no password | shown |

## 4. The human credentials and the fixture

**The first attempt (about 17:50Z).** `fixture` minted a site-administrator token with the CLI. Its
calls were refused with HTTP 403 "You must change your password", because `aieh-site-admin` still had
its temporary password. Its self-revocation was refused for the same reason. The run stopped there,
because finishing would have needed the human account's first sign-in. One defect was introduced
and fixed forward: the revocation outcome was lost; the tool now checks first and reports it in
every outcome. The leftover one (Gitea name `aieh-s0122-fixture-20261107T174944Z`) was inert while the account
had to change its password. Its value was never stored or shown.

**Credential finalization (Owner directive and approval, 2026-11-07).**
[F-06.1 section 8](F-06.1-gitea-loopback.md) records the mechanism and the redacted live report. In
short:
- both accounts got generated final passwords through Gitea's own forced change (the first live
  attempt stopped harmlessly at the sign-in, fixed by `c1a4e8a`);
- both are held in `AIEH Gitea site-admin` and `AIEH Gitea owner`; the temporary entries are deleted;
- the temporary passwords are rejected;
- no password was found in the managed root, the checkout or the report.

**Remediated exposure.** Finalization deleted every token of `aieh-site-admin` with its new
credentials immediately after the change: the leftover fixture token and two remediation probes. The
probe `aieh-s0122-fixture-remediation-probe-20261107T183528Z` (`sha256:e79b73ed8e76e7be`) answered 403
before and **401** after, and the account holds no token.

**The fixture** (`gitea_roles.py fixture --admin-merge-probe`):
- **Authentication:** as `aieh-site-admin`, by HTTP basic authentication with its harness-held
  password read from the credential provider into memory; **no token was minted for
  administration**, and the administrator held no token afterwards.

  - the site administrator's merge and its force-merge **both answered 405 "User not allowed to

The fixture is **kept as a documented fixture** so that `task gitea:authz` can rerun. Its proposal

## 7. The open questions

1. **Does `read:repository` suffice for the reviewer to submit reviews?** **No.** A probe token
   of the reviewer bot with `read:repository` answered 403 "token does not have at least one of
   required scope(s), required=[write:repository]" on `POST …/pulls/{n}/reviews`; the verifier saw the
   same. The reviewer therefore keeps `write:repository`, bounded by read permission, as F9-F14 show.
   The probe was revoked: `DELETE /api/v1/token` 204, then 401.
2. **The effect of `--restricted`.** The administrator API reports `restricted: true` for each bot.
   A public repository created by the administrator (`aieh-restricted-probe`, `private: false`)
   answered **404 "not found"** to all four bots. It was then deleted (204, then 404). A restricted
   account sees only what it is explicitly given.
3. **Can the site administrator revoke another account's token?** **Yes**, through the API with its
   own credentials (basic authentication):
   - `GET /users/aieh-bot-verifier/tokens` answered 200 with the names;
   - `DELETE /users/aieh-bot-verifier/tokens/{id}` answered 204;
   - the probe token then answered 401;
   - the verifier's real token was untouched.

## 8. Secret files and agent workspaces

**Agent workspaces in the guest.** No token store or managed-root path is mounted in, or exchanged
into, the execution guest:
- the strong Windows profile declares `host_shares: []`, and its launch has no 9p, virtiofs, fsdev,
  SMB, virtio-serial or vsock device; the only host files it names are pinned inputs and per-instance
  files (`profiles/strong-windows-qemu-whpx/profile.json`);
- F-03.3.1 observed this at run time: P3, P4 and P5 PASS on two fresh guests
  ([evidence](F-03.3.1-guest-surfaces.md));
- the exchange is a git bundle over the management channel (P4);
- `TestNoTokenStoreReachesTheGuest` (offline, in `task gitea:test`) fails if that declaration changes.

**Bootstrap limit (accepted; `fd-bootstrap-shared-identity`; decision 0010).** Host-side agents run as
the Owner's account. Any process of that account can:
- read the four bot entries and the two harness-held human entries (`CredReadW` needs no prompt);
- read Gitea's `app.ini` and database;
- run Gitea's CLI, which mints a token for any account without a password.

Decision 0010 puts same-account processes outside the threat model. No bot, test or ordinary Builder
or Reviewer context reads the human entries: only credential finalization and the fixture
administration read the site administrator's, and nothing reads the Owner account's yet.
