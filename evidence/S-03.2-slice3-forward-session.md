## 1. The forward session (`tools/guest.py inference-forward`)

`inference-forward --action start|status|stop --profile P --state-dir S --name N [--broker-port PORT]`
(task `guest:inference-forward`). Refused for an instance whose launch record has no `inference` block
(not created with `create --provision --inference`), for every action.

**The command line, as tested** (`test_inference_forward.ForwardRecords.test_forward_argv_over_the_instance_channel`,
the real `guest.Ssh` with its `ssh -G` check and the OpenSSH lookup stood in for):

```
C:/Windows/System32/OpenSSH/ssh.exe -F none -o IdentitiesOnly=yes -o StrictHostKeyChecking=yes
  -o UserKnownHostsFile=<instance_dir>/ssh/known_hosts -o BatchMode=yes -o IdentityAgent=none
  -o GlobalKnownHostsFile=none -o ConnectTimeout=15 -i <instance_dir>\ssh\id_ed25519 -p <hostfwd port>
  -N -v -o ExitOnForwardFailure=yes -o ServerAliveInterval=15 -o ServerAliveCountMax=3
  -R 172.17.0.1:8090:127.0.0.1:<broker inference port> agent@127.0.0.1
```

The head is the profile's `identity.ssh_client_options` and the harness's own options with the
per-instance key and the launch record's hostfwd port (`guest.Ssh`, unchanged); the forward's own options
are declared in the profile (`network.inference_composition.forward_session.ssh_options`) and checked by
`check_profile` (`-N`, `-v`, `ExitOnForwardFailure=yes`, both keepalives in range, nothing else: no
`-L`, `-D`, a second `-R`, `-f`, `-g` or `-A`).

| Requirement | As built |
|---|---|
| broker port from the broker's configuration | `integrations/inference/inference_control.py` reads `components.inference_broker` through the broker's own `load_config` (`dispatcher_ports`); `forward_target` refuses the control listener's port (`CONTROL_PORT_REFUSED`) and any port that is not the inference listener's (`FORWARD_PORT_REFUSED`); `start` also asks the control listener for its status and refuses (`BROKER_NOT_READY`) unless its inference listener is on that port (decision 0015 section 4.4: the broker first) |
| the record while held | a holder process starts ssh, waits for ssh's `-v` line `remote forward success for: listen 172.17.0.1:8090, connect 127.0.0.1:<port>` (or ssh's end, or `establish_ceiling_s`, 60), then writes `{instance_dir}/inference-forward.json` atomically and exclusively: `schema`, `instance`, `pid`, `binary`, `created_epoch`, `holder_pid`, `started_at`, `ports` (endpoint, broker, hostfwd), `argv` (the profile's `forward_session.fields`) |
| removed when the session ends | the holder waits on ssh and removes the record (when it still names this session) as soon as ssh ends; a refused bind (`ExitOnForwardFailure`) or no establishment writes none |
| a dropped session claims nothing | every reader (`status`, `start`, `inspect`) trusts a record only while its ssh process runs: same pid, same binary, same creation time (within 1 s); a record whose process is gone is stale, never held |
| idempotent start | a held session is returned (`existing: true`), no second holder; a stale record is removed and replaced (`replaced_stale`); a second holder that loses the exclusive write ends its own ssh and the start returns the winner |
| re-establishment | an explicit re-run of `start`; there is no retry loop (the holder never restarts ssh) |
| status and stop | `status` reports held or not and removes a stale record; `stop` terminates the recorded ssh, waits for the holder to remove the record (ceiling 30 s), and removes it itself only if the holder could not |
| ssh's output | the holder keeps no `debug` line; up to 40 other stderr lines go to `{instance_dir}/inference-forward.log`, with the establishment and the end |
| guest lifecycle | `destroy` stops a held session first; `recreate` carries the composition from the launch record (section 5) |
| no console window | the holder starts with `CREATE_NO_WINDOW | CREATE_NEW_PROCESS_GROUP`, ssh with `CREATE_NO_WINDOW` (section 9) |

`inspect` now reads the record through the same liveness rule (`forward_state`), so its listener check
(`inference endpoint listener (decision 0015)`) compares the listener against a session that is held, not
against a file that exists.

## 2. The token steps of the job probe

`job-access-probe --attempt-token-stdin` (an opted-in guest only; refused otherwise, and for a token not
of the broker's shape, with a message that never repeats the input) reads one attempt token from
standard input, never argv. The Owner (or a later dispatcher) issues it for the probe's own conversation
(the fixture's conversation id). The new step `inference with the attempt token from inside its job`
runs after the inference sweep and, from inside the token's conversation container:

| Phase | Expected (rule fixed before observation) |
|---|---|
| the token's family's first declared route and auth header shape (from the broker's status), the token's first model | the upstream's answer: 2xx, no broker refusal (`forwarded`) |
| the probe revokes the token through the control listener (`attempt end`, revoker `tools/guest.py job-access-probe ...`) | the grant answers `revoked` |
| the same request | 401 `TOKEN_REVOKED` at once |
| the forward session stopped (`inference-forward stop`), the same request | `ECONNREFUSED` (fail closed, no hang) |
| the forward re-established (`start`), the same request | 401 `TOKEN_REVOKED` again |

The token never echoed in an answer. **Stop conditions:** a revoked token answered 2xx; any answer
while no forward is held. A final step (`always`) revokes the token if the token step did not run or
did not reach revocation, so the probe always ends its attempt's access.

**How the token travels.** On the host it is held in memory only. To the guest it goes **sealed**: the
API probe's requests and the token are written into the script's own text on ssh's standard input
(`sealed_api_probe`), so neither ssh's argv nor the guest `python3`'s argv carries it, and the API probe
redacts it from every answer and counts the echoes (`sealed_occurrences`). Inside the container the
bash route runs `printf '%s\n' '<token>' | python3 /tmp/aieh-job.py <spec>`: `printf` is a bash builtin,
so no process argument carries it, and the script reads it from standard input. **Disclosed:** the
command text, and therefore the token, is in that conversation's bash events in the guest
(`bash_events` of the conversation's store), the attempt's own record, which decision 0015 section 8
already discloses ("persists in that conversation's record in the guest until revocation"); the probe
revokes it before it ends and deletes the conversation. The harness's records carry the fingerprint
only: before the record is written, every occurrence of the token is replaced (`redact_secret`) and
counted (`attempt_token.redacted_from_record`, 0 expected). The provider key is never involved.

**The guest's own login.** The inference sweep now also asks the endpoint once from the guest's
operator login (outside every container) without a token: the expected answer is 401 `TOKEN_MISSING`;
an answer of 2xx is a stop condition (section 6.3).

### 3.2 Findings for the plan

**(a) The provider key for a fake upstream.** The broker reads its key only from the credential
provider the harness chooses from the running system (`credentials.select_provider`, invariant I6:
never configuration or the environment); on this host that is Windows Credential Manager. Two
offline-safe ways exist, neither writing the Owner's store:

1. **Already supported, no key at all:** a family whose `upstream` is a loopback `http` origin may have
   no `provider` (decision 0015 section 2.4, the degenerate case), and is then ready without a key
   (`Broker.readiness`); the broker forwards with no auth header. This proves "forwarding to a fake
   upstream with a valid family-bound token", revocation and forward loss. It does not show the key
   substituted for the token, and the P5 provider-key needle has no fingerprint to look for (that
   `inspect` check stays UNKNOWN).
2. **A synthetic key, not built:** the broker's command line already takes a whole `Context`
   (`inference_broker.main(argv, context)`, the seam its tests use with an in-memory provider). A
   qualification-only launcher that reads a synthetic key from standard input into an in-memory
   provider and calls `main(['serve'], context)` would show the substitution and give the P5 needle a
   fingerprint, with nothing written anywhere. It is a new way to start the broker's listeners (A2's
   scope), about forty lines with tests, and not test-only, so it is not built here.

Writing a synthetic entry into Credential Manager is the only other way and is excluded (it writes the
Owner's real store).

**(b) The child-conversation clause** ("A child conversation launched by an agent driven by the fake
upstream runs inside the parent container and under its caps") **cannot be met without a model call's
plumbing that the re-scope dropped.** The evidence: `fd-child-conversation-tool` (S-01.3.1) established
that `start_child_conversation` posts to the conversation's own inner server, so a child runs in the same
container, and "a valid child launch ... would start an agent step and an LLM call". For an agent to be
"driven by the fake upstream" its LLM calls must reach the broker, which needs the create to carry LLM
settings (native: `model`, `base_url`, `api_key`) or the ACP `secrets`; the pinned template sends
`agent_settings: {"agent_kind": "openhands", "mcp_config": {}, "tools": []}` and no LLM fields, the
typed create refuses every other field (E-01.3.1), and the `settings`, `llm` and ACP routes are
`dispatcher: not-used` (recommendation section 1.1). The template's `tools: []` also gives the agent no
tool to call, so even an LLM-driven agent could not start a child under it. Ways forward, each the
Overseer's or Owner's decision and none taken: move the clause to S-03.3, which has a disposable pinned
create fixture with provider settings; admit a disposable test-only create fixture with LLM settings and
the child tool for the S-03.2 qualification; or record a weaker observation (a child created by the
probe through the inner children route) as what it is.

**(c) Issuing the probe's token.** No harness command issues a token: the dispatcher's issuance belongs
to the typed create's change (A-01.2, E-03.1), which this slice does not make. The qualification needs
one issuance call (step 7). The smallest option: `ControlClient.issue` and an `issue` command in
`inference_control.py` that writes the token to standard output only, for a pipe into
`job-access-probe --attempt-token-stdin`. Not built.

## 9. Process notes

- **Incident: console windows on the Owner's screen (introduced by this slice; fixed forward in
  `60a68cd`).** `forward_spawn` in `573d71e` started the holder with `DETACHED_PROCESS`, copying
  QEMU's launch. A detached process has no console, so every console process it starts gets a
  console window of its own: each run of the test that starts a real holder opened one window (its
  fake ssh), and the first mutation run (ten workers, mutants that reach the real holder) opened
  many. The coordinator stopped the work; I stopped the run and its waiting loop and ended 18
  leftover processes (fake ssh interpreters and one holder) by their command lines; a recheck found
  none. In real use the Owner would have seen an ssh window for every forward session: a product
  defect, not only a test nuisance. The fix: the holder starts with `CREATE_NO_WINDOW |
  CREATE_NEW_PROCESS_GROUP` (never `DETACHED_PROCESS`, under which `CREATE_NO_WINDOW` is ignored) and
  starts ssh with `CREATE_NO_WINDOW`; QEMU's launch is unchanged. A test asserts both launches'
  flags without starting a process; the tests that start a holder or a fake ssh record every
  launch, require `CREATE_NO_WINDOW` on each, end every process they started (the whole tree) and
  assert none is left alive. Before the mutation run resumed, the forward tests ran once alone and
  left no new process (no holder, no `conhost` child). The mutation harness then ran with four
  workers, every launch `CREATE_NO_WINDOW`, each mutant in a job object; 0 leftovers after it.

  docs sentence in which the word for the SSH identity was followed by a comma and an ssh option in
  code; the sentence was reordered, nothing was allowlisted.
- `inspect`'s forward-session reading changed from "the record exists" to "the record's ssh runs":
  a narrowing of slice 2's check, made so that a dropped session claims nothing.
- Paths beyond the dispatch's list: none. Worker memory under `.claude` only.
