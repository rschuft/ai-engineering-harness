**Effects schema** (all tables STRICT and canonical; no projections):

- `effect_state`, `effect_origin` and `effect_transition` (from, to, origin): frozen
  vocabularies.
- `effect_receipt`: key, key inputs, operation kind, target, the five authority fields,
  origin, actor, state, reconciliation status, result, sequence numbers and times.
  Identity, deletion and result rewrites are blocked by triggers.
- `effect_event`: the hash-chained journal. A trigger enforces contiguous sequence
  numbers and the previous-hash link. A foreign key from (from, to, origin) to
  `effect_transition` restricts each transition.
- `restore_epoch`, `restore_epoch_closure`, `reconciliation_record`: append-only.
- Gate triggers: `effect_reservation_gate` (no executor insert while an epoch is open)
  and `effect_apply_gate` (no move to `applying` while an epoch is open).

### Custody check

**Mechanism.** `effects_custody.read_security` calls `GetNamedSecurityInfoW` with
OWNER and DACL information, which reads what the OS holds for the path, not the
template the store meant to apply. It reads:

- `GetSecurityDescriptorControl` for `SE_DACL_PROTECTED`;
- `GetAce` for each ACE: its type, flags (INHERITED 0x10), mask, and SID through
  `ConvertSidToStringSidW`.

`evaluate_windows` then compares the result with the template. For the root it
requires:

- a protected DACL, with no inherited ACE;
- an owner of SYSTEM, Administrators or the configured principal;
- every ACE SID in that set;
- allow or deny ACEs only.

For files and directories inside the root, inherited ACEs are expected, since they come
from the protected root, but the owner and SID rules still apply.

The check runs on every open, before the connection is made, for the root and for the
database, `-wal`, `-shm` and `backups/` directories. It runs again after migration, and
on backup. On POSIX, `evaluate_posix` checks for a 0700 directory, 0600 files and the
owner uid (unit-tested only).

`(0, 0x03, 0x1F01FF, S-1-5-18)`, `(0, 0x03, 0x1F01FF, S-1-5-32-544)` and
`(0, 0x03, 0x1F01FF, <test-user-SID>)`. The store opens.

## Inference (not directly observed)

- **Exclusive custody.** Every WAL connection holds a shared lock on the database file
  for its whole life. That is why an idle connection in another process makes the
  `BEGIN EXCLUSIVE` under `locking_mode=EXCLUSIVE` fail. This was observed with an
  idle worker; the general claim rests on SQLite's documented WAL locking.
- **Atomic replacement.** The final restore step, `stage.backup(live)` in a single
  `sqlite3_backup_step(-1)`, writes the destination in one transaction. A crash during
  it therefore leaves either the old store or the new one. This was not crash-tested.
  A crash before that step leaves the live store untouched, because the epoch and the
  projection drop happen on the staged copy.
- **The live custody template.** Its effect on another principal (actual denial) is not
  shown: the fixtures prove that the check reads and refuses correctly, not that the OS
  denies other accounts. That is G-04.2.2's proof.

## Recorded limits

- **Fixture oracle.** The `FixtureOracle` and `OracleFixture` in the tests stand in for
  real probes of the target. Those come with G-04.4.2 and G-04.5 for effects, and with
  E-01.4.x (OpenHands) for the integration store.
- **Fixture repository.** A synthetic git repository with OpenSpec- and Backlog.md-shaped
  files stands in for adopted OpenSpec and Backlog.md (decision 0004, point 8).
- **OS-crash durability is UNKNOWN.** The crash tests kill processes, with `os._exit`
  and `Popen.kill`. They do not cut power or crash the OS. `synchronous=FULL` is set
  and read back, but power-loss durability is not verified.
- **Live identity separation cannot be proved** before G-04.2.1 (executor principal,
  Owner act A4) and G-04.2.2. Today the fixtures use the test account as the
  principal. On this host, bootstrap agents run as the Owner's account, and UAC consent
  is not a security boundary (decision 0004, point 9).
- **The effects CLI success path** needs a conforming, Owner-created root outside every
  profile. None exists, so only the CLI's refusals were exercised. The library path,
  which the CLI calls, is what the tests exercise.
- **POSIX custody** (modes 0700/0600, owner uid) is unit-tested on synthetic values only.
- Decision 0004 is still **Proposed**; the Owner's acknowledgement is pending.

## Interpretations made within the accepted constraints (for review)

- **`observed` versus `completed`.** A receipt that already existed and was found
  performed by reconciliation becomes `completed`, with origin `reconciliation`.
  `observed` is reserved for receipts created by reconciliation, where the store had no
  receipt for the key (the lost tail). Reconciliation also adds the transitions
  `reserved` -> `completed` | `unknown`. The executor's transitions are those of the
  brief.
- **"Not performed: key cleared".** A `reserved` receipt is cleared and stays reserved.
  An absent candidate is only recorded. An `applying` or `unknown` receipt becomes
  `failed`, and its key stays spent: a retry needs new inputs, for example an attempt
  number. This is a carried question for G-04.x.
- **Starting an effect during an epoch.** `begin` (`reserved` -> `applying`) is refused
  while an epoch is open, as well as new reservations.
- **The integration store's high-water mark** counts attempt events only. Restore-epoch
  rows are bookkeeping and are kept in the superseded copy. Restoring the same backup
  twice is therefore not a rollback there, whereas in the effects store the epoch event
  is in the chain, so it is.
- **Closing an integration epoch** needs no `dispatched` or `unknown` attempt. A
  `reserved` attempt may stay, because its deterministic conversation ID (decision
  0001) makes a re-dispatch idempotent.
- **An unreadable live store** is never replaced by the tool, because it cannot be
  preserved aside. The Owner must move it away first.

## F-05 parent proof

F-05's proof is: "Crash and reopen preserve an unfinished receipt; rebuilding
projections never rewrites canonical OpenSpec/Backlog data."

- **Unfinished receipts survive crash and reopen**, in both stores. For F-05.1, a
  `reserved` attempt survives `os._exit`. For F-05.2, a `reserved` and an `applying`
  effect receipt survive `os._exit`; the `applying` one is flagged for reconciliation;
  and a killed open transaction leaves nothing.
- **A rebuild never rewrites the canonical sources.** The synthetic OpenSpec and Backlog
  repository has the same HEAD, tree, refs, status and file bytes after rebuilds. The
  canonical tables are byte-identical across rebuilds. The authorizer refuses writes
  outside the projection (F-05.1 tests).
- **Assessment:** the F-05 proof is satisfied on fixtures, within the limits above. The
  real OpenSpec and Backlog sources, the real target probes, OS-crash durability and
  live identity separation remain with their named later leaves.
