The mapping is the only one consistent with the records: each credential is in the dispatcher's
`custodian_of`, its issuance row says `delivered_by: management-dispatcher`, it is granted to that role and
denied to the other (`policy/role-tokens.json`); the store's stage set is exactly `implement` and `review`.
The planner, verifier and protection auditor are never delivered (no stage maps to them).

`attempt_role_token(store, key, provider=, port=, http=)` takes no stage, role, bot or entry: it re-reads
the attempt's record and refuses anything but a `confirmed` attempt (`ATTEMPT_NOT_CONFIRMED`), reads only
the stage's one entry (`ROLE_TOKEN_MISSING`, `ROLE_TOKEN_MISMATCH` for another account or a value that is
not a token, `ROLE_TOKEN_UNAVAILABLE` for a failing provider), and asks Gitea for the token's own view:
`401` is `ROLE_TOKEN_REJECTED`, a lost or malformed answer `ROLE_TOKEN_UNVERIFIED`, another login or
other scopes `ROLE_TOKEN_MISMATCH`. Inside the context the token is in memory only; `record()`
(`role-token-delivery/v1`) carries its fingerprint; the object refuses copy and pickle. While it is open,
`AgentServerClient.call`, the dispatcher's one way to the Agent Server, refuses any call whose path or body
holds the token (any 40 consecutive lower-case hex digits whose sha256 is held) or its fingerprint
(`ROLE_TOKEN_EXPOSURE`), before the transport. Holds are counted: two attempts of one stage share one
standing token while there is no per-attempt rotation (section 3, F-1).

## 3. Findings and the decisions they need (STOP)

**F-1. Per-attempt rotation needs a privilege the role model does not grant (dispatch STOP condition 2).**
What Gitea 28.3.0 allows, from this repository's own observations (the pinned source was not read: no
network was authorized and no source tree is in the checkout): no token lifetime, neither in the CLI nor in
`CreateAccessTokenOption` (S-01.2.2 section 3, "Token bounded to one attempt: Not expressible"); a token can
revoke itself with `DELETE /api/v1/token`, which needs no scope (S-01.2.2 section 6; OA-16's source reading
in `integrations/gitea/protection_check.py`); a new token is minted only by Gitea's CLI
(`admin user generate-access-token`, which reaches the database directly, `op-gitea-administration`) or
through `/users/{username}/tokens` with basic authentication, which a Bot cannot use (no password,
S-01.2.2 section 1); the site administrator's basic authentication lists and deletes another account's
tokens (S-01.2.2 section 7), and whether it can also mint one there was not established here. So the dispatcher can
revoke at attempt end, but it cannot issue the next token: the role model makes it the `rotation_owner` of
the bot tokens (`policy/role-tokens.json`, `builder`/`reviewer` revocation rows) while issuance is
`gitea-site-admin`'s (decision 0007 point 4) and the dispatcher holds neither `cred-gitea-admin` nor
`op-gitea-administration`. Revocation alone at attempt end would leave the role without a token until an
administrator acts. Not built. **Decision needed:** who issues the per-attempt token (for example, the
dispatcher revokes and requests issuance from the site administrator's act, during bootstrap the Owner's
account through `gitea_roles.py rotate`; or the dispatcher is granted issuance; or rotation stays at
`gitea_roles.py rotate` on its other triggers and the per-attempt residual is recorded as a limit).

**F-2. The management key's sole custody and the op-as-* cut-over cannot be built within this dispatch
(STOP condition 3; condition 1 in part, since decision 0013 point 1 keeps `tools/guest.py`'s bootstrap
role "unchanged"; and the path boundary).**

- *No dispatcher principal exists in the guest, and none is decided.* The key file is `root:agent 0440` in a
  `root:agent 0750` directory, written by the seed's root step (`profiles/seed/user-data.tmpl`,
  `agent_server_secrets`) and declared in `profiles/strong-windows-qemu-whpx/profile.json`
  (`provisioning.agent_server.session_key`: owner, group, mode). `agent` is the one guest login: exec,
  exchange, provisioning upload, facts requests and API probes. "Moving the key to a separate guest identity
  (a dispatch group that agent is not in) is proposed to the Overseer, not done"
  (`fd-guest-login-name-and-key`); ruling R9 keeps the file where it is; decision 0013 point 1 says the
  Owner's account performs the dispatcher's role through `tools/guest.py` "(unchanged)". Which principal
  reads the key after the cut-over (a new guest login with its own per-instance SSH key, a group, or another
  form), where its host-side key is kept, and what remains of `agent` is an unmade design decision.
- *The realization is outside this dispatch's paths.* Both files above are read-only here; changing the
  profile changes its sha256, which every approved-input manifest pins, and the profile's operational
  status rests on E-01.2.2's live requalification.
- *The cut-over would break live paths that pending Owner acts depend on.* Every `tools/guest.py` command
  that calls the management API reads the key as `agent` through `GuestApi` (`sealed_api_probe`):
  `conversation-smoke`, `admission-probe`, `job-access-probe`, `containment-probe` and `drill` (and through
  it `integrations/dispatch/tests/live_admitted_create.py`); `inspect` and `provision` handle the host copy.
  S-03.2's guest qualification, awaiting the Owner's acts under OA-12 (A3, A4) and OA-19, runs through
  `job-access-probe`. Removing `agent`'s read before those commands move to the new principal breaks them.
- **Decision needed (D-1):** the guest dispatcher principal and its key custody; with it, the
  authorization to change `profiles/seed/user-data.tmpl`, the profile declaration and `tools/guest.py`'s
  API channel together, and the requalification that a profile change requires.

**F-3. "A read ... by the UI is refused" needs a reading (decision 0013 point 6).** During bootstrap the Owner
UI (`apps/owner-host`) and the dispatcher's stand-in run as the Owner's account. The host copy of the key
in the per-instance directory (`op-session-key-export`) is therefore readable by the UI's process: decision
0013 point 6 puts same-account host processes outside the threat model ("disclosed rather than
prevented"; `fd-bootstrap-shared-identity`). In the guest the UI has no login; its only path is a
dispatcher-owned forward to one conversation's inner server (decision 0013 point 3), a new host port that
needs OA-07, and the runtime-credential route that U-01.2 verifies. **Decision needed (D-3):** whether the
proof's UI read means the guest file through the UI's own channel (then it needs that forward), or the host
copy (then it conflicts with point 6 until the dispatcher has its own OS identity, which no leaf builds).

### 8.1 The live transport (ruling F-2, the bootstrap reading of decision 0013 point 1)

`integrations/dispatch/guest_transport.py`: `GuestTransport(api, profile, api_login=)` is the transport of
`AgentServerClient`, one request per call through `tools/guest.py`'s `GuestApi`, as the guest login the profile
declares (`identity.guest_user`, `agent`), the login that reads the key from its `root:agent 0440` file. It returns
`{"status", "body"}` for every HTTP answer and raises `TransportError` (`NO_ANSWER`) for none; an answer that
carried the key is `SECRET_IN_ANSWER`; a profile that does not declare that custody is `KEY_CUSTODY_UNDECLARED`,
a channel of another login `LOGIN_MISMATCH`. The key is read in the guest only; the transport never opens the host
custody copy; `calls` holds statuses and body digests only. `tools/guest.py drill --kind admitted-create` and
`live_admitted_create.py` use it (the one-POST bridge and the precondition bridge are removed); the drill checks
that exactly one create was sent, by digest. No seed, profile, `GuestApi` key handling or probe vantage changed
(`job-access-probe` untouched). `GUEST_API_LOGIN` names `Ssh.run`'s default login.

### 8.2 The standing bot credential (ruling F-1 as corrected by the Owner)

1. **The standing bot credential**, in the host's credential provider, is issued, rotated and revoked only by the
   administrative lifecycle (`gitea_roles.py provision`, `rotate`, `retire`) on defined security and lifecycle
   triggers, never on routine attempt completion. `rotate` now resumes as `retire` does: a token Gitea already
   refuses (401) is not revoked again, and the new one is minted (its receipt says which).
2. **Its per-attempt use** is `attempt_role_token`'s bounded context: obtained only for a confirmed attempt, held
   in memory, released at the end. Releasing the in-memory reference is not Gitea revocation; nothing in the
   dispatch package revokes, mints or writes an entry.
3. **The per-attempt inference token** (decision 0015) is unchanged: broker-issued, revoked at attempt end.

Residual, recorded on the builder and reviewer rows of `policy/role-tokens.json`: concurrent attempts of a stage
share one standing token, and re-issue is an administration act between attempts. Disclosed same-account limit:
during bootstrap the Owner's account can read the standing credentials (decision 0013 point 6).

### 8.3 The custody probe (prepared, not run)

`tools/guest.py` `custody_probe`, driven by `integrations/dispatch/tests/live_custody_probe.py`, under
`CUSTODY_PROBE_RULE`, fixed before any run and quoted in every record:

> PASS iff every step passes: (1) the key file and its directory have the owner, group and modes the profile declares (inspect); (2) the positive control: the key the dispatcher login reads in the guest has the fingerprint of the host copy and of the one the root step published (inspect); (3) zero hits of the outer key's fingerprints and of the builder's and reviewer's token fingerprints in the files and process environments of both conversation containers, which hold no credential file (job-access-probe, its credentials step and verdict); (4) a conversation runtime credential minted by the dispatcher answers 401 on every key-gated route of the outer server (HTTP 401, a WebSocket refused) and 2xx on its own conversation's inner server, which refuses a request without it; (5) one confirmed implement and one confirmed review attempt each get exactly the stage's mapped bot (Gitea's own view of the token) and their delivery records carry fingerprints only. FAIL when a step observes a violation; otherwise UNKNOWN when a step is UNKNOWN. STOP (FAIL, the run ends): a 2xx from the runtime credential on an outer route; a credential-provider write; a need to change the seed or the profile (the declared custody is not the bootstrap one); a new host port (the instance's forwarded ports change). Revocation and re-issue of a standing bot token are not part of this rule: they are the administrative lifecycle's (gitea_roles.py rotate), an optional separate step.

The runtime-credentials answer is read under `ASSUMED_CREDENTIAL_SHAPE` (a `session_api_key` string), to be
checked live (U-01.2); another shape makes step (4) UNKNOWN. The route is `not-used` in the dispatcher's
allowlist, so the probe mints through the dispatcher's guest channel (`GuestApi`) directly, not through
`AgentServerClient`. The optional administrative-lifecycle step (`--rotate-report`: the Owner's own `rotate`
report shows the old token refused with its receipt read back, and the run delivered the new token) is outside
the routine rule.
