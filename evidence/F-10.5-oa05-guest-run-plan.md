## 4. Isolation, and the profile fields that enforce it

| Condition | How it holds | Profile field (`profiles/strong-windows-qemu-whpx/profile.json`) |
|---|---|---|
| No guest network | SLIRP with `restrict=on` and `ipv6=off`: the guest reaches nothing on the host or outside except explicit forwards; none toward the host exists in this profile's argv | `network.mode`, `network.posture`, `network.enforcement_point` (qualified by F-03.3.2), `launch.argv` `-netdev user,id=net0,restrict=on,ipv6=off,hostfwd=tcp:127.0.0.1:{ssh_port}-:22` |
| No guestfwd | none in `launch.argv`; the `inference` and `provision` endpoint classes are deferred | `network.endpoints[3..4].status` ("deferred"), `launch.argv` |
| No host share | no 9p, virtiofs, SMB or other share device; `-nodefaults` | `host_shares: []`, `guest_storage.forbidden_fstypes`, `launch.notes` |
| No new host port | only the profile's two management endpoints, chosen free on 127.0.0.1 at create and held for the guest's life: SSH hostfwd (`{ssh_port}` -> guest 22; operator exec and the exchange's SFTP) and QMP (`{qmp_port}`, host only) | `network.endpoints[0..2]`, `network.port_allocation`, `network.local_exposure` |
| No credential or model key | no canaries, no provisioning (`create` without `--provision`), no Agent Server, no LLM; the only credential is the per-instance SSH key `create` generates in the instance directory and `destroy` deletes | `identity.ssh_key`, `identity.ssh_client_options` (`-F none`, `IdentitiesOnly=yes`, known_hosts in the instance), `provisioning.create` |

Inside the guest the transport tests serve a stand-in git server on the guest's own loopback

provisioning only"); it is not one of the Owner-UI or dispatch connections that OA-07 covers.

## 5. Resource effects

- **Disk** (under `D:\aieh-guest-state\instances\f105-linux` only): two thin qcow2 files, the
  root overlay over the pinned image (40 GiB virtual) and the scratch disk (120 GiB virtual), the
  seed ISO, the SSH key pair and known_hosts, `launch.json`, logs and operation records. Allocation
  is bounded by the profile at 160 GiB; the expected use is small (boot writes plus about 1.4 MB
  sent and the corpus's few MB), well under 1 GiB (an estimate: earlier evidence does not record
  instance file sizes). The run records the two disk files' sizes before destroy. The image, the
  provider and every other path under the state directory are untouched.
- **RAM and CPU:** up to 16 GiB of host RAM and 8 of the host's 32 logical CPUs for the guest's
  life (QEMU with WHPX, an ordinary user process; no elevation).
- **Duration:** about one to two minutes expected. Readiness was 9.7 s in F-03.2.2b; the suite
  took 2.4 s on Windows; SFTP of 1.4 MB is under a second at the observed ~125 MiB/s. Ceilings:
  readiness 600 s (guest.py's default), each guest.py command 900 s in the script.
- **Host files created** (all in the session scratch, `<session scratch>\oa05-run\`, which the script creates
  new): `run.jsonl` (every step, its argv, exit code, time and bounded output), the payload
  archive, `f105-report.json`. guest.py's SFTP batch file is created there and deleted.

## 6. Teardown

- `destroy` (step 10) stops the guest if it runs (QMP quit, then that process only) and deletes
  `D:\aieh-guest-state\instances\f105-linux`: disks, seed, SSH keys, logs, records and the staging
  copy of the report. It refuses with `DESTROY_FAILED` if the directory still exists.
- Removal is verified twice: a second `destroy` must report `absent`, and no QEMU process with
  `guest=f105-linux` may remain.
- What persists: only the run directory in the session scratch (section 5) and the report in it.
  No guest image, provider or other state directory content changes. No record is written to the
  repository by the run.

## 7. Failure handling

- **Before create** (checkout, wheels, runner, payload digests, preflight): the script stops; no
  guest exists.
- **create refuses because `f105-linux` exists:** not this run's guest. It is left untouched and the
  script stops (exit 2). Any other create outcome (refusal after the instance directory was made,
  `not-ready`) is followed by destroy.
- **After create, any failure** (mkdir, transfer, digest mismatch, extraction, manifest, the suite
  could not run, the pull did not verify, an exception): the script stops that step and always runs
  destroy and the teardown check (`try`/`finally`).
- **A failing test** is a result, not a stop: the report is collected, the guest destroyed, and the
  verdict is DIFFERENT (exit 1).
- **If teardown cannot be verified,** the script prints the exact command to repeat
  (`task guest:destroy PROFILE=P STATE_DIR=S NAME=f105-linux`) and exits 2; the Overseer reports it.
- A failed run is not retried under this approval.

## 10. Deviation to note

The leaf's action says "transferred by SFTP (decision 0006 pattern)". No Taskfile target puts an
arbitrary file (`guest:push` carries one git bundle, and the provisioning upload is tied to the
provisioning lock). The script therefore calls guest.py's own `Sftp` helper, the same code and
the same management forward, key and client options the exchange and provisioning use, from a
small driver. The alternative is `guest:exec` with the file on standard input (SSH, not SFTP).
