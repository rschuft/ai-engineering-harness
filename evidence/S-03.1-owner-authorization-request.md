# Owner authorization request: model access for engineering conversations (S-03.1)

Prepared 2026-11-10 at `7b93fb3` for the Owner-action queue (`evidence/bootstrap-log.md`, Needs Owner now, **OA-12**). Origin: plan leaf S-03.1 and the [Proposed decision 0015](../decisions/0015-inference-broker-placement-provider-credential-custody-and-guest-inference-endpoint.md). This page is complete on its own; the decision holds the reasoning.

## What this is about

Today a conversation in the execution guest can run but cannot call any model: the guest has no network at all, and no provider key exists anywhere in the harness. S-03.1 asks you to authorize, or refuse, one specific way of giving conversations model access. Nothing below has been done. If you refuse any item, nothing is built and the guest stays as it is.

The shape in one paragraph: a small **broker** program runs on your Windows host, listens only on `127.0.0.1`, and is the only thing that ever holds the model provider's key. Each conversation in the guest gets a **temporary token** for its own attempt, not the key. The conversation's containers reach the broker through **one new path out of the guest**: a port-forward carried inside the SSH connection the harness already uses to manage the guest. The broker forwards each request to **one provider address** with the real key, and writes an audit line without the prompt text.

## What you are asked to decide (choices)

1. **Which provider and which model(s).** Name the provider (for example Anthropic, OpenAI, or a local model server on this host) and the model name(s) a conversation may use. The broker refuses any other model name.
2. **Which key.** A key created for this harness alone, with a spend cap set in the provider's console, that you can revoke there at any time. Not your personal key and not the login your coding assistant uses.
3. **Budgets.** A ceiling per attempt (requests and tokens) and per day. Defaults will be proposed by S-03.2 if you give none; the broker refuses requests beyond them.
4. **The first run.** Whether S-03.2 may make the first model call: one disposable guest, one conversation, a fixed test prompt ("reply with one word"), no repository content.

## What stays unauthorized (unchanged by a yes)

- Any other network for the guest or its containers: no other outbound destination, no DNS to the internet, no resolver, no package or image sources, no GitHub.
- Any other host port, forward or `guestfwd`; the Owner-UI connection (OA-07) remains a separate decision.
- Repository content in the guest or sent to a model: the first run uses a fixed test prompt. A model run on real repository content needs your separate approval under the standing condition "no repository content".
- Untrusted agent workloads; any second provider; any change to Windows, WSL2, the host firewall or services; any elevation.
- Reading, listing or copying any other credential of your account.

## Resource and data effects

- **Data leaving the host:** every prompt and completion of an authorized conversation goes to the provider you chose, under that provider's terms. The broker records who asked, when, which model, how many bytes and tokens, and the result code. It never records the prompt or the answer.
- **Money:** usage is billed to the key you create; the broker enforces request and token ceilings, and the provider's spend cap is the hard stop.
- **Disk:** the broker's audit lines under `<managed root>/persistent/logs/inference/`; a per-attempt summary in the existing integration store; the broker's non-secret configuration in `config.yml`. No new store.
- **Processes:** the broker and one SSH session per guest, both as your account, both visible in the host census.
- **Reversal:** stopping the broker, revoking the key at the provider, or deleting the credential entry ends all model access; the guest then runs exactly as today.

## What S-03.2 will prove before anything is declared working

- A conversation reaches the model only through the broker: direct provider addresses, public resolvers, host services and the peer container stay refused from inside a container; the full S-02 containment catalogue is re-run with the new allow in place and every case passes.
- No container, guest file, record, log or report holds the provider key (searched by fingerprint).
- A request with no token or a revoked token is refused; a request for a non-allowlisted model or path is refused; budgets stop requests.
- The broker's outbound connections go only to the one provider address.
- Losing the SSH session makes the next model call fail at once, not hang; re-establishing it restores service without restarting the guest.
- A child conversation started by an agent runs inside the parent container and under its caps (as already observed).
