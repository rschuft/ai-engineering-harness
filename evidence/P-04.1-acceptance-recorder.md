## 3. How "authored by a model" and "attributed to the Owner" are decided

`statement_verdict` judges the statement from its own fields, in this order:

1. **missing** (`ACCEPTANCE_MISSING`): no statement, empty or blank `text`, or no `reference`
   (absent, empty or `missing:<what>`);
2. **authored by a model** (`ACCEPTANCE_MODEL_AUTHORED`): `attributedTo` is `agent:<id>` (in the
   intent-record/v1 attribution grammar an agent is a model), or the `reference` is an `openhands:`
   engineering conversation (the lineage `attempt` kind: a model's own transcript);
3. **not attributed to the Owner** (`STATEMENT_NOT_OWNER`): `attributedTo` is anything but `owner`
   (`person:<id>`, other text such as `Owner`, or absent);
4. **malformed** (`STATEMENT_INVALID`): a field outside the four, a channel that is not a
   lower-case token, a reference outside the intent-record grammar.

The recorder then admits only an Owner message (`conversation:<thread>/<message>`, the lineage
`message` kind) or an accepted decision record (`decision:<id>`) as the reference, and never the
request itself (an Original Quote's `source`, invariant 4): `ACCEPTANCE_REFERENCE_INVALID`.
`recordedBy` may be an agent (the bootstrap transcriber).

**Evidence base and limit (inferred, stated plainly):** these are declarations by whoever
transcribed the statement, checked for consistency, not authentication. No Owner conversation
store exists (U-02.x), so whether the referenced message is the Owner's, and whether `text` is its
verbatim content, is not checked. This is the same limit P-04.2's plan text records for the
bootstrap channel ("proves a declared decision bound to an exact revision, not an authenticated
Owner").

## 6. The repository module's commit write (decision 0014)

P-04.1 is the first leaf that needs a commit, so the write is added here (section 8), as
`Repository.write_commit(files, message, *, identity, expected_head, when=None, check=None)`
(`commit(revision)` is already the read). Observed:

- No hook runs and none is skipped silently: a repository with a client hook (`core.hooksPath`, or
  a non-sample file under `hooks/`) is `HOOKS_UNSUPPORTED` before anything is written (no new
  object; `test_client_hooks_are_refused_before_anything_is_written`).
- Objects first (blobs, trees, commit; trees read through the verified read path), then the
  optional `check`, then Dulwich's `set_if_equals` on the branch (compare-and-set under the
  reference's lock), then the work tree and the index. A branch that moves before the update is
  not overwritten (`head-moved`); `check` raising leaves the branch and the work tree unchanged.
- **git as the oracle** (`test_a_commit_is_written_in_process_and_the_checkout_follows_it`):
  `git fsck --strict` passes, `git status --porcelain --untracked-files=all` is empty, `git
  reflog` shows `commit: recorded`, the module's own `status` is empty, and a later `git commit
  -am` keeps the change (no stale cache-tree).
- Refusals: detached HEAD, `commit.gpgSign`, unmerged index entries and mandatory (lower-case)
  index extensions, local changes, untracked files in the way, path conflicts, nothing to commit,
  invalid paths (`.git`, `..`, absolute); git's own split index is `GIT_FAILED` (Dulwich cannot
  read it). No process is launched by the write (`subprocess.Popen` patched to fail).
- **Launch census:** `tools/tests/test_launch_census.py` passed with the new files in the index
  (the tools suite run at `5e205f3`'s content, and the three profiled runs at `5e205f3`): no new
  launch site, no allowlist change. The tests' git launches go through the existing fixed helpers
  (`repository_corpus.git`, `two_task_fixture.git`), which are already the allowlisted sites.

## 8. Decisions this leaf had to make (for the Overseer's confirmation)

Decision 0008 and the plan fix the record's fields, the declaration's form and the refusals; they
do not fix the following, which change durable form. Each is implemented as stated and is a
one-constant change if ruled otherwise; no real repository holds any of them yet.

1. **Where the record lives:** `openspec/changes/<change>/owner-decisions/<decisionId>.json`,
   committed in the same commit as the item and the declaration, so it moves with the change on
   `openspec archive` and is read at the same revision. The lineage resolver ignores it.
2. **A `format` field** (`owner-decision/v1`) ahead of the plan's fields, as the repository's other
   durable records carry one.
3. **The challenge:** `prepare`/`record` with a stateless challenge (`owner-decision-challenge/v1`)
   held by the caller; its nonce's single use is decided from the committed records (no recorder
   state, so nothing is written under the managed root); expiry 60 minutes by default, at most 7
   days. The Owner's statement is not required to repeat the nonce.
4. **The reference kinds admitted:** an Owner message or `decision:<id>`; the item's
   `acceptance` is the statement's reference itself (as the P-03.2 example declares it).
5. **`--amend`** is required to re-record an item that has its id; re-recording the same
   acceptance is refused.
6. **The commit:** author and committer from `--identity` (not from git configuration), time
   UTC, trailers `AIEH-Decision-Id`, `AIEH-Outcome-Id`, `AIEH-Recorder: acceptance-recorder/1`.
7. **The module's name for the write:** `write_commit` (decision 0014 calls it `commit`, which is
   the read's name).

## 9. Findings

1. **Exposed-by P-04.1 (the first write): Dulwich 1.2.21 writes the index's extensions back as
   read.** A commit that updated index entries through Dulwich would keep git's cache-tree for the
   changed directories, and the next `git commit` would write the old trees back (silently
   reverting the change). Repaired in the new write before commit: the optional extensions git
   rebuilds are dropped, resolve-undo kept, mandatory ones refused; the oracle test commits with
   git afterwards and keeps the change. Pin-sensitive (`Index._extensions`), recorded in the
   repository README.
2. **Unrelated-but-detected: Dulwich 1.2.21 cannot read git's split index or sparse index**
   (`ChecksumMismatch` on the `link` and `sdir` extensions). Every module call that reads the
   index (`status`, `index_entries`, `listing`, and now `write_commit`) fails closed with
   `GIT_FAILED` in such a repository. The README already lists split and sparse indexes as not
   verified; no repair here (a reader change outside this leaf).
3. **Unrelated-but-detected, repaired:** `docs/development.md`'s `setup` row said "the thirteen
   commands" while Quick start said fifteen; both now say sixteen (this leaf adds one).
4. **Exposed-by P-04.1:** Dulwich's `set_if_equals` writes only the branch's reflog, and always,
   whatever `core.logAllRefUpdates` says. The write adds HEAD's line itself, as git writes it;
   `core.logAllRefUpdates=false` is not honoured (recorded as not verified).
5. **Introduced and repaired before commit:** the first `declare_outcome` put a new entry after
   comment lines that close an `x-outcomes` block (caught by
   `test_an_entry_is_added_to_an_existing_block_with_its_indentation`).
