## What was built

- **The repository's name** (decision 0022 point 1): `aieh-authorization/authorizations`, in a private
  organization of its own. The name is `gitea_roles.AUTHORIZATION_ORG` and `AUTHORIZATION_REPO`, and nothing else in
  the harness spells it. It contains neither "fixture" nor "d1".
- **Admission** (decision 0022 point 2):
  - Every recorder context carries its own admitted set, `Context.policies`. A context without one is refused, and
    no global admits a repository (`admitted_policies()` is removed).
  - `managed_context` admits exactly the authorization repository (`managed_policies`).
  - Exercise contexts (P-04.2's suites, the live exercise, the envelope and selection suites) admit the S-01.2.2
    fixture alone (`exercise_policies`).
  - One non-fixture repository is admitted, so `envelope_decisions.candidates` needs no repository predicate yet.
- **Declarations** (decision 0022 point 3): `gitea_roles.DECLARATIONS` holds one entry per repository, and
  `protection_check.declaration` reads it.
  - The fixture's entry is unchanged.
  - The authorization repository's entry is its own, today equal to the fixture's but for the name, so that G-03.1
    can change one without the other.
  - Any other repository or branch is `NOT_DECLARED`.
  - The auditor's reach (`AUDITED_REPOSITORIES`) is the fixture and the authorization repository.
- **The proposal act** (decision 0022 point 4), `authorization_proposal.py propose MANIFEST`
  (`task owner:propose`), with bot tokens only:
  - The builder bot adds `operations/<id>.json` with the given bytes on `work/<id>` and opens one pull request into
    `main`.
  - The act reads back the pull request, its single added file and the manifest at its head. A differing sha256 is
    `DIGEST_CHANGED`, and nothing is approved.
  - The reviewer bot approves exactly that head. The approval must read back as an official, current, undismissed
    `APPROVED` review by the reviewer bot of the head (`APPROVAL_UNCONFIRMED` otherwise).
  - An existing operation id is refused before anything is written: on `main`, with its branch present, or in an
    open pull request, whose files are paged.
  - Only a 4xx answer to the first write means nothing was written by this run (a refusal). Any other stop after a
    write is never a refusal: it names what was written, or may have been written.
  - Its route allowlist (`BOT_ROUTES`) is separate from the recorder's and holds no merge route. It never merges.
- **OA-30's module**, `gitea_roles.py authorization-repository --owner-act OA-30`, built and tested on fakes and
  never run:
  - It refuses without the flag, reading and sending nothing.
  - Before any write, each check a refusal: the managed store holds no `owner-authorization/v1/` receipt (read
    with SQLite `mode=ro` and `query_only`; the database content is never written, though SQLite may create
    `-wal`/`-shm` sidecars); the bots and `aieh-owner` exist; the auditor's entry is present; the site administrator
    holds no token; the fixture verifies with its recorded baseline.
  - Then, as the site administrator by basic authentication with no token minted, in order: the private
    organization, the auto-initialized repository, its settings, collaborators and rules.
  - Then: a field-for-field read-back, including `main`'s initial commit alone and no pull request; no
    administrator token afterwards; `protection_check verify` as the auditor, with its baseline reported; and the
    fixture verified again with its baseline.
  - Every write is recorded in order with its outcome.
  - After the first write, any stop is reported with its writes and printed (exit 1). This covers a non-2xx
    answer, a lost answer ("may have been written"), a read-back difference, a held token, a verdict other than
    verified, the fixture, and any exception.
  - An existing organization or repository is never adopted. A second run on a verified repository writes nothing.
