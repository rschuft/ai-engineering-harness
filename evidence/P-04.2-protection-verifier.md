## 4. Rule precedence as found at the pin

S1-S4: Gitea sorts a repository's rules by `priority` ascending, then plain before glob, then creation
time, and the first rule that matches the branch is the one `GetFirstMatchProtectedBranchRule` returns,
which the merge handler, the pre-receive hook and the branch view all use. A plain name matches
case-insensitively (a rule `MAIN` matches `main`); a glob uses `/` as the separator (`work/*` does not
match `main`, `**` matches everything). A rule created without a priority gets the highest plus one. For
the fixture's `main` the matching rules in order are `main` (1) and `**` (3), and `main` is enforced.
The check computes this order from what it reads, requires Gitea's own `effective_branch_protection_name`
to be its first (else `PRECEDENCE_UNVERIFIED`), and the declared one (else drift: a shadowing rule such as
`ma*` with priority 0, `main` lowered below `**`, `main` missing). Ties at equal priority and plainness
are ordered by creation time in Gitea; the check orders them by `created_at` text, but a tie can only
arise with a priority that already differs from the declaration (drift).

## 8. Gitea's merge-time enforcement and the time-of-check limit

(Also in [`integrations/gitea/README.md`](../integrations/gitea/README.md#the-protection-check-oa-16) and
`fd-protection-check-toctou`.) At the merge Gitea 28.3.0 evaluates the protection rule as the row is then,
in the merge handler (`CheckPullMergeable`) and again in the pre-receive hook of the merge push (S12). It
enforces: the merge allowlist; required approvals counted from the approvals allowlist; rejected reviews;
official review requests; code-owner reviews; an outdated head branch; required status checks; protected
files; signed commits; dependencies; the recorder's `head_commit_id` (409 "head out of date"). It lets a
bypasser (an account or team on the bypass allowlist, or a repository administrator when
`block_admin_merge_override` is false) force-merge past those gates. It does not: compare the rule with any
declaration (a changed rule is enforced as changed); evaluate a manual merge (`Do: manually-merged`, when
the repository allows it) against anything but the merge allowlist (hence `allow_manual_merge` false in
the declaration); audit a protection change made through its API (only web-made changes reach its audit
log, which is shown through web pages only).

**The remaining limit.** No API spans the check and the merge. A repository or site administrator (the
site administrator, whose credential is harness-held, is inside the trusted computing base of decision
0010) can change a rule between the check and the merge, about one request round-trip on host loopback.
The recorder asks the check again after the read-back and records both answers in the receipt: a change
that is not reverted within the window is disclosed (`PROTECTION_CHANGED_AFTER_MERGE`), not prevented.
Team membership is not readable with `read:repository`, so who belongs to the Owners team (whose members
administer the repository and could make that change) is not compared.
