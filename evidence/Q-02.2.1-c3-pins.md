### Findings for the next dispatch (data for the Overseer; nothing changed)

1. **The declared exchange mount would be dropped.** `policy/ci-runner-profile.json` declares the
   exchange as `--volume=/home/agent/exchange:/aieh/exchange:ro` in `container.options` beside
   `container.valid_volumes: []`. At 6.0.0 the binds parsed from `container.options` pass through the
   same valid-volume filter (`docker_run.go` 653, 1130-1159), so that bind is ignored with a warning.
   The two ways the source offers are an entry in `container.valid_volumes` (which the policy requires
   empty) or the new `container.volumes` key (`config.example.yaml` 274-282; `run_context.go` 284,
   290-311), which mounts on every job, service and Docker-action container and lets workflow volumes
   reuse the source with the same access. A decision for the profile; neither is chosen here.
2. **`container.enable_ipv6` is not a key at 6.0.0.** The key is
   `container.network_create_options.enable_ipv6` (`config.go` 204-207); an unknown key only warns
   (`config.go` 291). The policy rule's path names the old key.
3. **Keys and environment the declared configuration does not yet pin:** `container.volumes`,
   `container.bind_workdir`, `container.sweep`, `container.require_docker`, `runner.tool_cache_mode`
   (`none`), `runner.hooks` and the runner process's `ACTIONS_RUNNER_HOOK_JOB_*` fallbacks
   (`config.example.yaml` 153-160), `runner.post_task_script`, `runner.extra_headers`, `metrics`,
   `health_check`, `log.job.dir`; the daemon's `--labels` default from `GITEA_RUNNER_LABELS`
   (`cmd.go` 56); `OTEL_*` (export off until an endpoint is set, `docs/telemetry.md` line 3); the
   runner's `HTTP(S)_PROXY`, which reaches every job (`proxy.go` 31-67).
4. **The runner's own options do not cover services or `uses: docker://` containers** (row 4). The
   governance workflow's rules (no `container:`, `services:` or `uses:`) carry that; they also keep
   a workflow's `container.options` from overriding `--user` and the limits.
5. **The runner itself posts to `/api/actions_pipeline/`**: the job-summary upload with the job's
   runtime token when Gitea advertises the capability (`act/runner/job_executor.go` 540-575). The
   proxy allowlist denies that path; whether Gitea 28.3.0 advertises the capability was not read.
6. **The registration token's paths into the runner:** `--token` (visible in the process list),
   `--token-file`, or `GITEA_RUNNER_REGISTRATION_TOKEN` (`cmd.go` 36-37; `register.go` 88, 197-215).
   The saved `.runner` holds the runner token Gitea returns, not the registration token
   (`register.go` 392-402; `internal/pkg/config/registration.go` 15-25), at `runner.file`
   (default `.runner` in the working directory, `config.go` 337-339).
7. A job's Docker image is pulled when absent; an image pinned by digest is never re-pulled
   (`config.example.yaml` 288-293).

**Recommendation: `docker.io/library/python:3.12-trixie`**, pinned by the index digest with its
linux/amd64 manifest and image id above. It is an official, maintained upstream image; it holds git
and exactly the CPython minor the repository's tools lock targets (3.12, `cp312`); its base is the
CI guest's own Debian 13; it carries no Docker CLI and no sudo. The UBI image is the strongest
alternative where a non-root default user matters more than the distribution match; the Gitea runner
image carries more than the lane should hold. Whichever is chosen, two questions stay for the
profile: how the Python tools set reaches a job with no network (a derived image is a build, not an
adoption; a staged wheel set is another option), and how a non-root `--user` meets the workspace
volume and a missing home directory.
