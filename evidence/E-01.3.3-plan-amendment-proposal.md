## 1. Why the text changes

- **The dispatcher principal (ruling F-2).** "The dispatcher principal" has three senses that the proof conflates:
  the code path (the dispatch module as the only path for op-as-* on Work), the guest login that reads the key
  (today `agent`), and a host identity distinct from the Owner's account, which no leaf builds. Decision 0013 point 1
  makes the bootstrap dispatcher the Owner's account. With one host account, a second guest login would be a second
  door on the same key ring, so "a read by the operator login (after the cut-over) is refused" cannot be shown
  without custody theatre. The ruling: the bootstrap reading as written; the key file stays `root:agent 0440` (R9);
  the cut-over is the code path; the operator-login separation waits for the dispatcher's own host identity.
- **The standing bot credential (ruling F-1, as corrected by the Owner).** Gitea 28.3.0 cannot bound a token to an
  attempt and gives the dispatcher no way to issue a replacement (the CLI is the site administrator's). The Owner
  separates three lifecycles: (1) the standing bot credential, issued, rotated and revoked only by the existing
  administrative authority (`gitea_roles.py provision`, `rotate`, `retire`) on defined security and lifecycle
  triggers, never on routine attempt completion; (2) its per-attempt use, held in memory in the dispatcher's
  bounded attempt context and released when the operation ends, which is not Gitea revocation; (3) the per-attempt
  inference token (decision 0015), issued by the broker and revoked at attempt end, unchanged. "Rotate role tokens
  per attempt where Gitea allows it" does not describe that.
- **The UI clause (ruling F-3).** "A read by the UI is refused" is read as the UI's credential class: a conversation
  runtime credential minted by the dispatcher is refused on every key-gated management route and admitted only by
  its conversation's inner server. The host copy of the key is the disclosed limit (decision 0013 point 6); the UI's
  forward channel stays U-03.1's.

## 3. Proposed text (exactly)

**action** (the management-key insertion after "sole reader of the Agent Server management key", and "rotate role
tokens per attempt where Gitea allows it" replaced)

> Make the dispatcher's identity the sole reader of the Agent Server management key (during bootstrap the Owner's account through the dispatch module and the guest login it holds, decision 0013 point 1; the host copy disclosed under point 6) (decision 0013, points 1 to 4, and its ruling R9; fd-guest-login-name-and-key) and move the bootstrap op-as-* operator path to the dispatcher. Map each stage to its bot role token, used only in the dispatcher's attempt context and never inside a container; records carry fingerprints only; use the stage's standing bot credential per attempt only in the dispatcher's bounded attempt context, never in a container, and release it when the operation ends (releasing the in-memory reference is not Gitea revocation); the standing credential is rotated or revoked only on defined security and lifecycle triggers under the existing administrative authority (decision 0007 point 4), because Gitea 28.3.0 gives the dispatcher no replacement mechanism; the per-attempt inference token stays revoked at attempt end (decision 0015). Every host-to-guest forward is still a recorded Owner approval (decision 0013).

**proof** (and `agent_contract.completion_evidence`, identical to it)

> On a disposable guest, the key file's owner, group and mode equal the profile's declaration and it is readable in the guest only by the login the dispatcher holds the key of (during bootstrap agent, decision 0013 point 1); a container's read is refused and no container file or environment holds the key's or a role token's fingerprint; a conversation runtime credential minted by the dispatcher is refused on every key-gated management route and admitted only by its conversation's inner server; each stage uses exactly its mapped bot, and a confirmed attempt cannot acquire another stage's credential; two sequential attempts of one stage succeed with the authorized standing credential, and concurrent attempts of one stage cannot invalidate one another (releasing one leaves the other's credential usable, and nothing revokes); an actually revoked Gitea credential fails closed until the administrative lifecycle restores it (rotate, or retire then provision, replacing the entry), after which delivery works again; no stage credential or its raw value reaches the guest, through the Agent Server client or through the live transport's request path; records carry fingerprints only.

The token clauses of the proof are the five checks of the Owner's correction: each stage its mapped bot and no
other stage's credential; two sequential attempts of a stage on the standing credential; concurrent attempts that
cannot invalidate one another; an actually revoked credential failing closed until the administrative lifecycle
restores it; no stage credential reaching the guest through the Agent Server client or the live transport's request
path. The key-file, container and credential-class clauses are the rulings' wording. One refinement of the Owner's
wording, flagged for the Owner: the correction says "`rotate` or `provision` replacing the entry"; `provision`
mints only for an absent entry (it keeps an existing one, `integrations/gitea/gitea_roles.py`), so the proposed
text says "rotate, or retire then provision, replacing the entry".

**notes** (the sentence appended at the end)

> The separation of an operator login from the dispatcher's guest login is decided with the dispatcher's own host identity (no leaf; routed to the Owner; reconsider at the leaf that changes the seed for the Owner UI forward).
