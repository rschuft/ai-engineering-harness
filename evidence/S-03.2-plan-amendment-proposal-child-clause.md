# S-03.2 plan amendment proposal: the child-conversation clause (OA-19)

> **Recorded by the Overseer (2026-11-11). A proposal for the Owner's decision; nothing in the plan is changed.**
> It comes from an Architect consultation (gates A and G, advisory) on a finding of S-03.2 slice 3
> ([evidence](S-03.2-slice3-forward-session.md) section 3.2 (b)). The Overseer weighed that advice and
> adjusted it as noted in section 3. The plan is integrity-tracked, so any change goes through the
> integrity process on the Owner's approval, as the 2026-11-10 amendment did.

## 1. The finding

S-03.2's proof, as amended on 2026-11-10 (Owner decision (d) on OA-12), ends:

> A child conversation launched by an agent driven by the fake upstream runs inside the parent container
> and under its caps, as observed. No model call is made.

The same amendment dropped the LLM-settings create from S-03.2's proof, following the Architect's
recommendation (`S-03-acp-coding-provider-recommendation.md` section 3.2, row S-03.2: "Drop A6 and the
LLM-settings create from its proof; keep the child-conversation clause"). That leaves no way to meet the clause:

- For an agent to be driven by the fake upstream, its model calls must reach the broker. The create carries
  model settings in only two ways: LLM settings (native agent) or the ACP `secrets` (decision 0015 amendment 1,
  item 2). The pinned create template carries neither
  (`profiles/strong-windows-qemu-whpx/agent-server/conversation-create.json`).
- The template gives the agent no tools at all (`tools: []`), so no agent could start a child under it.
- The typed create refuses any field that differs from the template's (E-01.3.1, `integrations/dispatch/README.md`).
- `fd-child-conversation-tool` (S-01.3.1) records that a valid child launch starts an agent step and an LLM call.

The Architect confirms the analysis and classifies the defect as introduced by its own recommendation (carried into
the plan at `13cb939`) and exposed by slice 3. The clause began as a restatement of S-01.3.1's
structural observation, in a version of the leaf that still had the first model call. The amendment added
"driven by the fake upstream" and "No model call is made", which together demand an LLM-driven act without an LLM.

## 2. What the clause protects

Blueprint `#agent-skills`, "Delegation is not privilege reduction", and the `#containment-final-decision` row
"Subagent unexpectedly inherits MCP". The property: a delegated agent neither widens nor escapes the parent's
container, caps and mounts, and cannot create a conversation on the outer server. Its structural half is
already observed (S-01.3.1 section 4.3):
- `start_child_conversation` posts to the conversation's own inner server, with the same local runtime and the
  same container;
- the outer children route is unreachable.

The dynamic half, an agent's own tool call, can be seen only where an agent runs live.

## 3. Proposed amendment

**S-03.2 proof:** replace the last two sentences with:

> A child conversation created from inside the conversation container by the probe, through the inner
> server's children route with the conversation's own key (the route and key the start_child_conversation tool
> uses, S-01.3.1), starts in the parent container under its caps, as observed: no new container, no new
> listener, the outer server's conversation count unchanged, and its agent step fails closed without a model; if
> the inner server refuses a child without model settings, that refusal is the observation. An agent's own
> launch of a child is shown by the first leaf that runs that kind of agent live (S-03.3 for the ACP provider's
> delegation; the first leaf that runs an openhands-kind agent for its start_child_conversation tool), not here.
> No model call is made.

Also in S-03.2's proof, after "Agents cannot read the provider credential", insert:

> (shown with a synthetic key served through a qualification-only launcher and a loopback fake upstream; the
> real key's fingerprint search is S-03.3's)

**S-03.3 proof:** after "each boundary shown independently", append:

> Every process the provider starts, including any sub-agent or nested session it delegates to, runs in the
> same container as a descendant of the inner server under the same limits, shown by the process inventory and
> an independent docker inspect; no conversation is created on the outer server during the run. The provider
> key's fingerprint appears nowhere in the guest, the jobs, the instance directory, the records or the reports
> (decision 0015 section 4.5).

**S-03.3 notes:** append:

> Whether the fixed prompt asks for one delegated step is part of A6's presentation. Its disposable create
> fixture needs the ACP agent_settings block and the two secrets names, which admission refuses today
> (BODY_FIELD_UNKNOWN) and which A-01.2 owns; S-03.3 makes that change to its qualification profile itself

**S-03.4 proof:** append:

> A child conversation started by the native agent's start_child_conversation tool runs inside the parent

**Overseer adjustment to the Architect's wording:** the Architect named S-03.4 as the home of the native agent's
child launch. S-03.4 is optional and nothing depends on it, so on its own that could leave the property never
shown. The S-03.2 text above therefore names "the first leaf that runs an openhands-kind agent". The S-03.4
sentence makes it concrete there, and any earlier leaf that runs that kind of agent carries it instead.

## 5. The synthetic-key launcher (Overseer ruling, gate G advice)

The Architect finds no conflict with decision 0015's credential custody (sections 2 and 6; invariant I6
binds `select_provider` on the production path), provided that:
1. the launcher refuses to start unless every declared family's upstream is plain http to a loopback IP literal;
2. it reads the key from standard input only, refuses a terminal, and requires a mandatory synthetic prefix,
   so a real key pasted in is invalid as sent;
3. its start receipt records the key's fingerprint with the source `stdin-qualification`, and the evidence is
   labelled "substitution shown with a synthetic key";
4. it is a separately named qualification command, never a flag or variable on `serve`, and `select_provider`
   never returns an in-memory provider.

**Overseer ruling:** accepted. It is built offline under the Owner's decision (d), and it writes nothing. Running
it is part of act A2, whose presentation names it. No new Owner act. It gives the provider-key fingerprint search
a positive control, which the keyless upstream cannot.
