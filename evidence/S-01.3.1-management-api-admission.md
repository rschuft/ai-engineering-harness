## 3. The admission configuration (`provisioning.agent_server.admission`)

### 3.1 The Agent Server's own mechanisms
- **The session key** on every key-gated route (the unit's `EnvironmentFile`, F-04.1c). The
  config forbids `session_api_keys`, `allow_cors_origins`, `allow_cors_origin_regex`,
  `web_url`, `app_backend_public_url` and `deferred_init` (already enforced by
  `check_profile`), so CORS stays at its default (localhost only, a browser concern), the
  Canvas App ingress stays unconfigured and init is never deferred.
- **Fail closed without a key.** Because 1.60.1 serves an unsecured API when its key list is
  empty, a seeded `ExecStartPre` (`/usr/local/sbin/aieh-agent-server-keycheck`, as
  `openhands` with the environment file) refuses unless the session key and `OH_SECRET_KEY`
  are 43-character `token_urlsafe` values, distinct, and no other session-key variable
  (`OH_SESSION_API_KEYS_<n>` for n > 0, `SESSION_API_KEY`) is set. systemd then never runs
  `ExecStart`. It prints variable names only.

### 3.2 Guest-level controls (where the server cannot express the rule)
- **Listener:** `127.0.0.1:8000` only, and the unit's `IPAddressDeny=any` with
  `IPAddressAllow=localhost` (F-04.1c) drops any non-loopback packet of the server's cgroup.
- **Container guard** (seeded `aieh-container-guard` and its unit). In the filter table's
  `INPUT` chain, for IPv4 and IPv6, a packet that arrives from `docker0` or a `br-+` bridge
  jumps to `AIEH-CONTAINER-GUARD`:

  ```
  -A AIEH-CONTAINER-GUARD -m conntrack --ctstate RELATED,ESTABLISHED -j RETURN
  -A AIEH-CONTAINER-GUARD -m limit --limit 10/min --limit-burst 20 -j LOG --log-prefix "aieh-container-guard: "
  -A AIEH-CONTAINER-GUARD -p tcp -j REJECT --reject-with tcp-reset
  -A AIEH-CONTAINER-GUARD -j REJECT
  ```

  A container therefore opens no connection to any listener of the guest itself, at any of
  its addresses (`host.docker.internal` is `docker0`). Replies to the guest's own connections
  (`docker-proxy` to a container's port 8000) are `RELATED,ESTABLISHED` and pass. Forwarded
  traffic is untouched (S-01.4).
- **Fail closed:** a seeded drop-in makes `docker.service` `Requires=` and start `After=` the
  guard. If the rules cannot be installed, Moby does not start and no conversation container
  can be created (finding 1 shows it happening).
- **`icc: false`** in `daemon.json`: Moby's own control, no connection between two containers
  on the default bridge.
- **Verified at provisioning:** a new root step `admission`, right after Moby's first start and
  before the Agent Server is installed, enables the guard unit and requires the unit active,
  the declared rules in both families, `docker.service`'s dependency and the bridge's
  `enable_icc` `false`. Evidence run: 0.2 s, all true.
- **Reported and inspected:** the boot facts carry `admission` (the guard unit, both
  families' rules, the drop-in, the dependency, `enable_icc`, the key check's
  `ExecStartPre`); `inspect` adds the stable check `provisioning / management API admission
  (S-01.3.1)`. The on-demand facts carry the guard's per-rule counters, its kernel log lines
  and the server's own refusal log lines.

### 3.3 The allowlist
Each route's `dispatcher` field: `allowed` (22: the F-04.2 lifecycle, the inspection reads and
the public metadata), `validation` (1: the conversation proxy that `admission-probe` uses for
its own commands), `not-used` (170). **The Agent Server cannot scope its key per route**, so
this is the trusted dispatcher's own allowlist (E-01.2.x), not a server control; what the
server and the guest enforce is admission by key and by network.

### 3.4 What a refused caller sees (the rejection behaviour)

| Caller | Sees | Logged |
|---|---|---|
| HTTP, key-gated route, no key or a wrong key | `401 {"detail": "Unauthorized"}` | the server, `HTTPException 401 on <method> <path>` (330 lines in run A: the 164 key-gated HTTP routes twice, and `inspect`'s own two) |
| WebSocket, no auth message or a wrong key in it | handshake 101, then close 4001 "Authentication failed" | the server, warning `WebSocket first-message auth failed: …` |
| WebSocket, wrong key in the query or header | handshake 403 | the server, warning `WebSocket authentication failed: invalid API key` |
| Canvas App backend proxy | HTTP 503 (ingress not configured); WebSocket handshake 403 | - |
| A conversation container, any guest address and port | TCP reset (connection refused); other protocols ICMP port-unreachable | the kernel, `aieh-container-guard: IN=docker0 … SRC=<container> DST=<guest> … DPT=<port> SYN` (rate-limited) |
| A conversation container, another container | no answer (icc off: dropped; the probe's 4 s ceiling) | - |
| The server with a missing or invalid key file | the unit does not start (`ExecStartPre` exit 1, names only) | the unit's journal |
| The trusted dispatcher | 2xx when admitted, 401 with no detail for a missing or wrong key, 422 for an invalid body, 503 while the server is not ready; it never retries a 401 with another credential | - |

## 6. Session-key custody (finding `fd-guest-login-name-and-key`)
- **Today:** the key lives in the server's root-only environment file, the operator login's
  `root:agent 0440` file in the guest, and the instance directory on the host (fingerprints
  only in records). No dispatcher exists. **The dispatcher's role is performed by the Owner's
  account through `tools/guest.py`**, over the instance's host-loopback SSH forward with the
  per-instance key, as the operator login `agent`, which reads the key inside the guest from
  its file (never on a command line).
- **No agent workload ever has that login.** An engineering agent runs in a conversation
  container as 999:989 in its own namespaces: it holds no SSH key, cannot reach `sshd` (refused
  at every guest address), cannot reach the management listener, and can read only its own
  conversation's keys (section 4.3).
- **Status:** narrowed from unknown to a limit. The name still collides with the
  engineering-agent role, and anyone given the login would hold the full key.
- **Proposal to the Overseer (not done):** move the key file to a dedicated guest group (for
  example `aieh-dispatch`, `root:aieh-dispatch 0440`) that `agent` is not in, and give the
  dispatcher its own guest identity when it exists. It is cheap in the root step, but it
  changes the P5 contract and every probe's vantage, so it is a contract decision.

## 7. Findings
1. **The first guard rules never matched their listing** (introduced by this leaf; fixed
   before commit). The first shakedown guest (`s0131-y`) failed provisioning at
   `containerd-config`: "A dependency job for docker.service failed". The guard had declared
   `--log-level 4`; `iptables -S` omits the LOG target's default level (4, warning), so the
   guard's own verification failed and, as designed, Moby did not start. Fix: no
   `--log-level` (the default is the intended level), and the guard writes its result to the
   console as well, so the host's serial log shows it. `s0131-z` and run A passed. This is
   also the live demonstration that a failing guard fails closed.
2. **1.60.1 serves an unsecured API when its key list is empty** (exposed; upstream
   behaviour). Mitigated by the key check (section 3.1); recorded in the credential's notes.
3. **The agent can read its own conversation's keys** from `/proc/1/environ` (exposed;
   upstream: the inner server runs as the same uid as the terminal). Those are the
   conversation's scoped keys (`cred-conversation-keys`), already readable by `openhands` and
   root through `docker inspect` (F-04.1c); with them the agent reaches only its own inner
   server.
4. **The guard logs the guest's own LLMNR multicast** looped back on `docker0` (observed on
   `s0131-z`: `SRC=172.17.0.1 DST=224.0.0.252 UDP 5355`). It is refused harmlessly and costs
   log budget only.
5. **Unrelated but detected, not fixed:** the scratch clone could not check out one test
   fixture (`tools/tests/fixtures/intent_qualification/…/.gitattributes`: "Filename too long" on
   Windows); the guest tooling does not use it.
6. **Path boundary:** none breached. Reads stayed in the checkout, the scratch directory and
   the paths the guest tool uses under the guest-state root (`instances/`, the verified
   provision stage, whose binary and image archive were read as data).
