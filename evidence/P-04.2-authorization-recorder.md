How it works is in the [owner README](../integrations/owner/README.md#the-owner-authorization-recorder-plan-leaf-p-042).
In short: `prepare OWNER/NAME PULL` reads the pull request as aieh-owner and writes a challenge to
`<state>/owner-authorization/challenges/<nonce>.json`; `record --challenge NONCE --statement FILE
--recorded-by ...` checks authenticity, binding, freshness, policy, identity and single use, writes the
decision record to `<state>/owner-authorization/decisions/<id>.json` and the write-ahead receipt
`owner-authorization/v1/<nonce>` (format `aieh-owner-authorization/1`) to the integration store,
merges with `Do: merge` and `head_commit_id` and the six trailers, and reads back; `resolve` resolves an
unknown receipt by reading only (an open, unmerged pull request leaves it unknown: section 12).

## 5. STOP finding: the protection read-back is not expressible as aieh-owner

The action requires "policy (the protection and repository rules exactly as expected)". In Gitea
28.3.0 `GET /repos/{owner}/{repo}/branch_protections` (and `/{name}`) sits behind
`reqToken(), reqAdmin()`: repository or site administrators only. aieh-owner is a write collaborator
and must not be an administrator (decision 0012 draft, point 3), and the recorder holds only its
credential (custody separation from `cred-gitea-admin`). So the recorder can compare only what a write
collaborator reads (owner README, "What the policy check can see"): the repository's merge settings
and aieh-owner's permission, and the protected branch's `protected`, `required_approvals`,
`enable_status_check`, `status_check_contexts`, `user_can_push` and `user_can_merge`. It cannot see who
else is on the merge or push allowlists, force push, `block_admin_merge_override`,
`block_on_outdated_branch`, the approvals allowlist, `block_on_rejected_reviews`, the bypass allowlist
(`enable_bypass_allowlist`, `bypass_allowlist_usernames`, `bypass_allowlist_teams`: who may force-merge
past every gate) or `block_on_codeowner_reviews` (added by finding F-A, section 10), or the rule's name.
The build implements that observable check (`Policy.unobservable` names the rest) and proves drift
refusals for it; it does not choose how the rest is covered. Open decision for the Overseer (with the
Architect if wanted): whether that residual is (a) detected, not prevented (G-03.2 or the verifier,
by a principal that can read the rule), (b) checked before each merge by another principal's read
handed to the recorder, or (c) something else. Until then the proof clause "protection drift refused"
holds for observable drift only. **Superseded on 2026-11-10:** the Owner declined detection (OA-15a)
and decision 0012 point 6 now requires a fail-closed check; the recorder refuses every merge until that
check exists (section 13).

## 8. The live exercise (opt-in, not run)

Reworked on the Owner's decision OA-14 (2026-11-10): the exercise never constructs, defaults, templates
or paraphrases an Owner statement, and a general approval to run it authorizes no operation. It runs in
two separately invoked phases on Windows with the managed Gitea running, each an Owner-approved act and
skipped by default; the module docstring of `test_live_authorization.py` states each step and its
expected outcome.

1. **prepare**: `AIEH_AUTHZ_RECORDER_LIVE=prepare AIEH_AUTHZ_RECORDER_RUN_DIR=<an existing, empty
   directory> <tools python> -I -B -m unittest discover -s integrations/owner/tests -p
   test_live_authorization.py -v`. The builder bot proposes two manifests (kind `fixture-no-op`,
   expiring in 24 hours) on `work/authz-recorder-<stamp>-a` and `-b`; the reviewer bot approves both.
   Negative controls that need no Owner authority: each of the four bot tokens attempts the merge of
   each pull request with its `head_commit_id`; each must be refused (403 or 405) and main must not
   move. Any success is a **SECURITY FAILURE**: the test fails naming it and stops, with no presentation.
   The recorder's real `prepare` then issues each one-time challenge (180 minutes) into the run
   directory's own recorder state (`<run dir>/recorder`), and the phase writes `presentation.json` and
   `presentation.txt`: per challenge the repository, the pull request, the base, the approved head, the
   manifest path and its digest, the operation id, kind, target and expiry, the challenge nonce and its
   expiry, the effects the merge will have, the expected outcome and the recorder's own summary; which
   pull request is the stale-head control (B, expected refusal 409); whether a protection verifier was
   available; the bot controls' statuses. Nothing is merged. Then the custody inspection.
2. **The Owner, between the phases.** The Overseer presents the presentation. Only if the Owner then
   authorizes in his own words, naming the operation id(s), does the Overseer write that reply verbatim
   into a statement file (`{text, attributedTo: owner, channel: main-session, reference}`).
3. **record**: `AIEH_AUTHZ_RECORDER_LIVE=record`, the same `AIEH_AUTHZ_RECORDER_RUN_DIR` and
   `AIEH_AUTHZ_RECORDER_STATEMENT=<the file>`. The statement is read exactly as written and checked with
   the recorder's own statement checks before any Gitea call or credential read; a missing, empty or
   non-JSON file, a model-authored or non-Owner statement, or one naming none of the challenged
   operations is refused. `record` runs for each challenge the statement names, the stale-head control
   first (its head is moved by a hook on the recorder's merge call, after the recorder's checks: 409,
   `HEAD_STALE`, receipt failed; first, so that A's merge does not leave it behind main, finding F13);
   then the read-backs (main's head, zero tokens on aieh-owner), closing every pull request left open,
   and the custody inspection (the password searched in the managed root, the checkout, the run
   directory and the process environment).

**The fail-closed state.** No protection verifier exists until OA-16's mechanism is built, so the
prepare phase records that none was available and states the expected outcome of record as
`PROTECTION_UNVERIFIED` for every challenge: nothing is sent, nothing merged, no receipt written. A
presentation that says a verifier was available when none is now (or the reverse) is refused
(`VERIFIER_CHANGED`). The plumbing of both phases is tested offline against the fake Gitea
(`test_live_phases.py`, section 13).
