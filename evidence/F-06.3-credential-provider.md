## 2. The interface and the factory

- **Interface.** `CredentialProvider` (`get`, `set`, `delete`, `exists`) stays defined in
  `platform_contract.py`, where F-06.2 put it and where decision 0011 calls it "the contract", and
  `credential_provider.CredentialProvider` is the same object. The credentials module depends on the
  contract (its `LifecycleError`, `fingerprint`, `ExposureGuard`), so defining the class in the
  credentials module would make the contract load it in a cycle (finding 3).
- **Windows.** `WindowsCredentialProvider` over `CredentialStore`, the F-06.1/S-01.2.2 code. Its five
  methods and the provider's four are **AST-identical** to `f6e82bc`'s (checked mechanically); only the
  class attributes `name` and `mechanism` and a `describe()` method were added. The factory constructs
  `CredentialStore()` (loads advapi32 and sets argtypes; no `Cred*` call) and never imports keyring.
- **Linux, macOS.** `qualify_keyring` imports `keyring.backends.SecretService` or `keyring.backends.macOS`
  by name, instantiates its `Keyring` class explicitly, removes from the instance the properties
  `KeyringBackend.__init__` copied from `KEYRING_PROPERTY_*` environment variables (and the macOS class's
  `keychain`, taken from `KEYCHAIN_PATH`), and qualifies it: `.priority` must not raise and must be a
  number above zero, and the class must override keyring's default `get_credential` (which needs the user
  name) so that an entry can be found by its name alone. One entry per name: service = entry name, user
  name = the credential's user, password = the secret; a replacement under another user is stored first,
  the old entry deleted after. keyring errors become `CREDENTIAL_PROVIDER_LOCKED` (`KeyringLocked`,
  `InitError`) or the call's failure code, by type only.
- **Factory.** `select_provider(system=None)`: the system is `platform.system()` (never configuration or
  the environment); Windows, Linux, Darwin as above; anything unqualified is `NO_CREDENTIAL_PROVIDER` with
  its remedy; there is no file or plaintext fallback.
- **doctor.** `credential_provider.py doctor` (`task credentials:doctor`): the provider, its mechanism and
  viability (for keyring the backend, its priority and what it ignored), or the refusal and remedy;
  `entries_touched: 0`; its output passes the I7 scan. Run on this host at `437a578`: exit 0,
  `windows-credential-manager`, `viable: true`, `keyring_imported: false`, I7 clean.
- **Receipts.** `ActReceipt` writes an integration-store receipt per rotate or retire act through the
  store's own API: `reserve` before anything changes (no receipt, no act), `dispatched` before the upstream
  change, then `confirmed` with the outcome's fingerprints, `failed` (a harness refusal on what it
  observed) or `unknown` (an uncertain outcome; reconciliation required); then it reads the receipt back
  and fails `CREDENTIAL_RECEIPT_UNREAD` unless the intent and the last detail are what was written. Intent
  fields: format `aieh-credential-act/1`, verb, service, entry, user, role, `fingerprint_before`, provider,
  trigger, revoker, `affected_attempts`, `started_at` (decision 0007 point 5). The act's exposure guard
  scans what the receipt holds before it is written and after it is read back.

## 8. The real-store cross-read, prepared and not run

`TestCrossReadRealStore` in `integrations/credentials/tests/test_crossread.py` is the cross-read against
the real Credential Manager. It needs the Owner's approval and has **not** been run.

- **Command** (from the repository root, Git Bash):
  `AIEH_CREDENTIALS_REAL_STORE=1 "<tools python>" -I -B -m unittest discover -s integrations/credentials/tests -p test_crossread.py -v`
  (`<tools python>`: `python -I -B integrations/paths/tools_install.py --python`). In PowerShell:
  `$env:AIEH_CREDENTIALS_REAL_STORE = '1'; & "<tools python>" -I -B -m unittest discover -s integrations/credentials/tests -p test_crossread.py -v; Remove-Item Env:AIEH_CREDENTIALS_REAL_STORE`.
- **Environment variable:** `AIEH_CREDENTIALS_REAL_STORE=1` (the opt-in pattern of `AIEH_GITEA_AUTHZ=1`);
  without it, or off Windows, the class skips with its reason.
- **Name pattern:** `AIEH test cross-read ` followed by 32 random hex digits (`secrets.token_hex(16)`);
  the child process refuses any name without that prefix.
- **What it touches:** one generic credential of that name, user `aieh-test-cross-read`, comment
  `Throwaway entry of the F-06.3 cross-read test; deleted by it.`, value `secrets.token_urlsafe(24)`
  (random, protecting nothing), persisted per local machine for the user, through the factory's
  Windows provider: `CredReadW` (absent), `CredWriteW`, a child process's `CredReadW` (it prints the user
  and the value's fingerprint), `CredDeleteW`, a second child's `CredReadW` (absent), `CredReadW`
  (absent), and in cleanup `CredReadW` plus `CredDeleteW` only if a step failed. No other entry is read,
  written or deleted; `CredEnumerate` is never called. Then the I7 scan of both children's output for the
  value. The same command also runs the default file-mode cross-read (a temporary directory only).

## 9. Findings

1. **introduced-by the F-06.3 working tree (before `437a578`), fixed before commit; a residue under the
   managed root.** In the first draft, `gitea_roles.rotate` and `retire` opened the managed root's
   integration store when no receipt store was passed, and the not-yet-updated tests in
   `test_gitea_roles.py` called them without one: one gitea suite run created
   `%LOCALAPPDATA%\AIEH\persistent\state\integration\integration.sqlite` (and its directory) and wrote
   synthetic test receipts into it. By the code and the tests that ran, five receipts: four `confirmed`
   (a rotate, three retires) and one `failed` (a retire), naming the bot roles and holding only the
   fingerprints of the fake CLI's tokens; no real token or entry was involved, and the store was not read
   to confirm this. The existence of the file and its directory was checked once by exact path (no
   listing). **Fix:** a caller that gives its own context must give its own store (`receipt_store`
   raises `ValueError` otherwise), every test passes one, and
   `test_a_fixture_context_never_reaches_the_managed_store` holds it. **Not removed:** the file is under
   the protected managed root; whether to keep or delete it is the Overseer's or the Owner's decision.
   It also bears on F-07.2 (finding 4).
2. **Design gap, for the Overseer (macOS, F-06.5).** keyring 25.7.0's `macOS.Keyring` does not override
   `get_credential`, and its `find_generic_password` matches the exact account, so an entry cannot be
   found by its name alone. The factory therefore instantiates `macOS.Keyring()`, checks its priority,
   and refuses `NO_CREDENTIAL_PROVIDER` on macOS as it stands (fail closed). A macOS realization needs a
   decision (for example the user name stored with the entry, or a lookup that takes the user), not made
   here. `SecretService.Keyring` does find by service alone.
3. **Placement within the design, for review.** The `CredentialProvider` interface stays defined in
   `platform_contract.py` and is published by the credentials module (section 2), avoiding a load cycle.
4. **Placement within the design, for review.** Receipts go to `<state>/integration/integration.sqlite`,
   the integration store's location under decision 0009, which F-07.2 has not adopted yet (its legacy
   default is still the per-user `ai-engineering-harness` tree). F-07.2's "copy into
   `<state>/integration/`" must then meet an existing store (finding 1 already created one).
5. **Semantics chosen within the design, for review.** `finalize-credentials` counts as the contract's
   rotate (one receipt per account, also on an "already final" rerun); a `retire` with nothing left to
   revoke still writes a confirmed receipt; the trigger of a command-line act is `owner direction`;
   `affected_attempts` is empty (no dispatcher attempts exist yet); a harness refusal after the
   upstream call is `failed`, any other exception `unknown`.
6. **Act outside the dispatch's list, reported.** `dev:install` ran once: the dev lock mirrors the tools
   set (a contract test keeps them equal), so the required pytest run needed the dev venv for the new
   lock. It is the product's own installer, the same mechanism as `tools:install`.
7. **unrelated-but-detected, fixed forward in `437a578`.** `docs/development.md`'s setup paragraph said
   "thirteen commands" and left the platform suite out of its list since F-06.2; it now says fifteen and
