## 1. The lifecycle tool

`tools/guest.py` is standard-library Python, run with `python -I -B`. Windows process
control goes through `ctypes`. It implements the profile's bindings as follows.

- **preflight:**
  - OS and arch, and the Windows 11 floor;
  - the state directory rules (named, existing, outside the checkout and
    `%USERPROFILE%`, no comma);
  - both provider binaries and the firmware against their sha256 pins;
  - `-accel help` listing `whpx`;
  - the image sha256.

  Each failure names its Owner act (A1, A2, A3). `create` refuses with
  `TIER_UNAVAILABLE` when preflight is not `available`.
- **create:**
  - refuses an existing instance directory, before anything else;
  - records `git rev-parse HEAD` and refuses uncommitted changes under `profiles/`;
  - creates the directory and its `ssh\` subdirectory;
  - generates the key with Windows' built-in
    `%SystemRoot%\System32\OpenSSH\ssh-keygen.exe -q -t ed25519 -N "" -C <name>`;
  - re-checks the image sha256;
  - runs the profile's two `qemu-img create` command lines, as declared in
    `launch.per_instance_files`;
  - generates `seed.iso` with `tools/nocloud_seed.py`;
  - allocates two OS-chosen free ports on 127.0.0.1;
  - writes `launch.json` exclusively. It holds every boot input with its sha256
    (image, firmware, seed, provider binary, qemu-img, the instance public key), the
    full argv, the profile revision, the profile file's own sha256, the labels and
    the scrubbed environment;
  - launches QEMU detached.
- **launch:** every launch (create and start) re-hashes every input in `launch.json`
  first, and a mismatch refuses with `DIGEST_MISMATCH`. QEMU gets an allowlisted
  environment (P5): `SYSTEMROOT`, `WINDIR`, `SYSTEMDRIVE`, `NUMBER_OF_PROCESSORS`,
  `PROCESSOR_ARCHITECTURE` and `OS`, with `PATH` set to the QEMU `bin` directory and
  `System32`, and `TEMP`/`TMP` set to the instance directory. The launch then:
  - waits for QMP;
  - requires `query-accelerators` `enabled` to equal the profile's accelerator;
  - stops QEMU and refuses `TIER_UNAVAILABLE` on any `WHPX:` line.
- **Readiness:** one ceiling (default 600 s), and observable signals only:
  1. QMP;
  2. cloud-init's `BEGIN/END SSH HOST KEY FINGERPRINTS` and `… KEYS` blocks on
     `serial.log`. Every key must match a serial fingerprint before it is written to
     `<instance>\ssh\known_hosts`. ssh-keyscan is used only if cloud-init printed
     fingerprints without keys, and then every scanned key must match a serial
     fingerprint;
  3. an `SSH-` banner on the forward;
  4. `cloud-init status --wait --long` over SSH, which blocks in the guest until
     cloud-init finishes.

  The serial file and the forwarded port expose no completion signal, so they are
  polled once a second. The tool checks on every poll that QEMU is alive.
- **stop:** QMP `system_powerdown`, then a wait on the process handle
  (`WaitForSingleObject`) for `stop_timeout_s` (120 s). After that, QMP `quit` and a
  wait of up to 30 s; then `TerminateProcess` on that process id only.
  - The process id comes from `process.json`, written at launch.
  - It is trusted only if the process image is the profile's QEMU binary and its
    creation time matches the launch.
- **destroy:** absent reports `absent`. Otherwise:
  - refuse when the instance directory, or anything in it, is a symlink or junction;
  - if QEMU runs, force-stop it (`quit`, then terminate);
  - `shutil.rmtree` that directory only.
- **inspect:**
  - the QMP queries of the binding (`query-version`, `query-cpus-fast`,
    `query-memory-size-summary`, `query-block`, `query-pci`, `query-chardev`), plus
    `query-status`, `query-accelerators`, `query-named-block-nodes` and `qom-get`
    vmx/svm on each vCPU;
  - `qemu-img info -U` of root and scratch;
  - re-hashing of every launch input;
  - host bindings (`Get-NetTCPConnection` and `Get-NetUDPEndpoint`, by owning process
    and by port);
  - TCP connects to the host's non-loopback addresses and `::1` on both ports;
  - 45 guest probes over SSH (read-only inspection and egress probes);
  - a root SSH login attempt.

  It writes one record (`records\inspect-*.json`) that holds, per property, the
  declared value, observed value, method and PASS, FAIL or UNKNOWN. The process exits
  1 if any property FAILs.
- **exec:** ssh with the profile's `identity.ssh_client_options`, to
  `agent@127.0.0.1 -p <ssh_port>`. The tool adds:
  - `BatchMode=yes`, `IdentityAgent=none`, `GlobalKnownHostsFile=none` and
    `ConnectTimeout=15`;
  - `-i <instance>\ssh\id_ed25519`.

  **Safeguard, observed while building it:** `ssh -G` showed that Windows OpenSSH 9.5,
  given `-i` for a *missing* file, falls back to the default `~/.ssh/id_*`
  identities. So the tool refuses to run ssh when the per-instance key or
  `known_hosts` is missing. Before its first ssh command in each run, it also checks
  the `ssh -G` output: the identity list must be exactly the per-instance key, with
  `identityagent none`, `globalknownhostsfile none` and
  `stricthostkeychecking true`.
- **recreate:** destroy, then create, with the same name and profile.

Every operation prints one JSON object labelled per P11. Records (`create`, `start`,
`stop`, `inspect`, `exec`) are written under `<instance>\records\` and are deleted with
the instance (condition 2).

**Tests** (`tools/tests/test_guest.py`, 37 tests, no QEMU, no guest):
- **argv rendering:** the binary, all placeholders gone, the loopback `hostfwd` and QMP
  chardev, the seed and base paths, exactly one `-accel whpx`; an unknown placeholder
  and missing ports are refused; the `qemu-img` command lines; the scrubbed
  environment.
- **launch record:** fields, labels and digests; tampered and missing inputs are
  refused.
- **refusals:**
  - nine bad instance names;
  - five state-directory rules, each naming A3;
  - `create` on an existing directory, with the tree unchanged;
  - `start` with a tampered input (no `process.json` written);
  - uncommitted and untracked files under `profiles/`, using a throwaway git
    repository.
- **destroy:**
  - deletes only its directory, with a before/after digest of the whole state tree;
  - `absent`, with and without an `instances` directory;
  - bad names;
  - refuses a junction inside the instance, and a canary file outside it survives
    (this ran on Windows; it was not skipped).
- **host keys:**
  - parsing a serial sample with syslog prefixes and CRLF;
  - the `known_hosts` line format;
  - incomplete blocks keep waiting;
  - fingerprints-only with a matching and a non-matching keyscan;
  - an unvouched key, two blocks, and no fingerprints are refused.
- **ports and QMP:**
  - distinct free loopback ports; an in-use port is detected;
  - a fake QMP server, with the event before the reply skipped and the error reply
    raised.
- **probes and evaluation:**
  - probe script and parser;
  - blocked exit codes per probe kind;
  - the stdin regression below;
  - a passing observation, and 15 single mutations that each turn one property to
    FAIL.

## Findings

1. **`Ignoring request for interrupt vector 0`: recurred, harmless so far.** It was
   printed once per launch:
   - `2026-11-06T15:58:43.283672Z` (launch at 15:58:43);
   - `2026-11-06T16:06:13.911719Z` (launch at 16:06:13).

   It was never printed again while the guests ran: `stderr.log` held only that line
   at stop and at destroy. Both guests booted, ran cloud-init, served SSH and shut
   down cleanly (cycle 1 after 392 s of uptime).
2. **Egress layering (evidence toward F-03.3.2).** SLIRP's DHCP lease carries no
   router and no DNS option (`ADDRESS`, `NETMASK`, `SERVER_ADDRESS`, `NEXT_SERVER`
   only). So the guest's routing table holds only the on-link `10.0.2.0/24`.
   - **Observed:** probes to 1.1.1.1, 8.8.8.8, deb.debian.org's address and the
     host's LAN address failed in the guest's own stack (`Network is unreachable`),
     before any packet reached QEMU.
   - **Observed:** probes to the SLIRP addresses did reach QEMU, and `restrict=on`
     refused them: TCP to `10.0.2.2` on both host-forward ports and to `10.0.2.3:53`
     got `Connection refused`, and UDP DNS to 10.0.2.3 got no reply.
   - **Inference:** from the unprivileged `agent` account, egress is blocked. But a
     guest root could add a default route via 10.0.2.2. Whether `restrict=on` then
     still drops off-link traffic outside the guest is **not shown here**. F-03.3.2
     must test it with a route in place, as root, in a disposable guest.
3. **P6 literal check: `/tmp/.X11-unix` exists.** The contract's P6 inspect lists
   "the absence of … `/tmp/.X11-unix`". In this guest it is an empty directory
   (`total 0`, no socket), created at boot by the guest's own
   `/usr/lib/tmpfiles.d/x11.conf` (`D! /tmp/.X11-unix 1777 root root 10d`). It holds
   no host X11 socket, which is what P6 protects against (inference). `inspect` keeps
   the contract wording and reports FAIL. Whether the wording should read "no socket
   in `/tmp/.X11-unix`" is for F-03.3.1 and the contract owner; it is not changed
   here.
4. **Guest kernel warning under `-cpu max` with WHPX.** Each boot logs:
   ```
   [    0.771086] x86/fpu: misordered xstate at 1408
   [    0.772756] WARNING: CPU: 0 PID: 0 at arch/x86/kernel/fpu/xstate.c:254 fpu__init_system_xstate+0x300/0xbe0
   ...
   [    0.827084] ---[ end trace 0000000000000000 ]---
   [    0.827496] x86/fpu: Supporting XSAVE feature 0x001: 'x87 floating point registers'
   ...
   [    0.841764] x86/fpu: Supporting XSAVE feature 0x800: 'Control-flow User registers'
   ```
   The kernel continued and enabled x87, SSE, AVX, AVX-512 and CET user state, and
   the guest ran normally. **Inference:** WHPX reports, for the `max` model, an XSAVE
   layout that Linux 6.12 considers out of order. A named CPU model might avoid it;
   that is a profile decision for the Overseer or Architect, not taken here.
5. **QMP connections linger in `CloseWait`.** After a QMP client disconnects, QEMU
   keeps its side of the socket in `CloseWait`: two such rows at inspect time, and

   **Inference:** QEMU's Windows socket chardev notices the hang-up late. It is
   harmless here; worth watching in long-lived `shared` instances.
