- **`--ephemeral`:** no. C-3 chose decision 0016's shared lifetime (section 2.4: "between those it may
  be reused for successive jobs (`shared` mode) with a non-ephemeral runner that is deleted at
  destroy"). An ephemeral runner would be deleted by Gitea after one task and could not take the
  session's next job without a new registration, which needs a new registration token, a reset and,
  under the live gate, a new negative probe: that is the per-validation design C-3 did not choose.
  The recreation conditions keep the persistent runner's exposure bounded: the guest (and with it the
  runner, deleted at destroy, and its token, revoked by the deletion) is recreated at every policy or
  pin revision, after any failed containment probe, when the runner is deleted, at each unit
  boundary, and (C-3) at every session's end and whenever it is compromised or unverified. The
  checker ties the variant's register call to the choice: `--ephemeral` exactly when the chosen mode
  is per-validation.

## 3. The findings that stop the variant

### Finding A: ruling (1)'s condition is not met by the pinned source (the dispatch's STOP condition)

Ruling (1): the exchange mount moves to `container.volumes` read-only "only if the pinned source
confirms `:ro` is kept and workflows still cannot add mounts (`valid_volumes` stays empty);
otherwise STOP and report".

- **`:ro` is kept: yes.** Each `container.volumes` spec is appended verbatim to the job's binds on a
  target the job leaves unclaimed (`run_context.go` 303-313), so `/home/agent/exchange:/aieh/exchange:ro`
  reaches Docker with its `:ro`; the specs are validated at load (`config.go` 328-332); the upstream
  test asserts the read-only spec in the job's binds (`act/runner/run_context_test.go` 281-313, line 309).
- **`valid_volumes` stays empty: yes.** The sources "need no valid_volumes entry"
  (`config.example.yaml` 274-277).
- **Workflows cannot add mounts: no.** `validVolumes()` appends every `container.volumes` source to the
  list a workflow's own volumes and `container.options` binds are checked against, with `:ro` kept
  (`run_context.go` 284, 290-301: "lets workflows mount the container.volumes sources with no more
  access than they give"; `act/container/docker_run.go` 1311-1331, a `:ro` rule admits read-only mounts
  only; the upstream test line 311-312: "a workflow must not mount a read-only source writable"). A
  workflow may therefore add a **read-only mount of the exchange source at any other target**, and a
  workflow volume on `/aieh/exchange` takes the runner's place (`config.example.yaml` 275-276).
  Services and Docker-action containers get the volume too (line 274).

What this exposes, as data for the decision (no choice made here): the only host path a job could
mount stays the exchange, read-only; nothing writable and no other path. The governance workflow's
checked rules (no `container:`, `services:` or `uses:`) leave the one workflow that runs unable to
declare any volume, and Actions is disabled wherever proposals land. The runner configuration alone
no longer forbids every workflow mount, as `valid_volumes: []` did with the mount in `options`.
**Alternatives at 6.0.0:** (a) accept the read-only reuse, disclosed, and check `container.volumes` to
be exactly the declared read-only exchange; (b) `valid_volumes: ["/home/agent/exchange:ro"]` with the
bind in `options`: the same reuse, and `valid_volumes` no longer empty; (c) no bind at all: a
different delivery of the bundle into the job (a design question). The declared `options` list
still names the exchange `--volume`, which 6.0.0 drops: the policy's `options.notes` now says so. The
Overseer decides.

### Finding B: the provision lock needs the job image's layer list

A CI variant has a `provisioning` block (the policy places its `config.yaml` at
`provisioning.ci_runner.config`), so `check_profile` requires `provider.provision_lock`
(`check_provisioning`), and both `check_profile` (`provision_lock_problems`) and
`tools/guest.py provision-fetch` (`provision_image`) require `image.layers` with every layer's digest
and size, besides the index, manifest and config digests. The layer list is in the linux/amd64
manifest (`sha256:97dc788c...`), which the C-3 builder read but no record holds (the C-3 record has
only the total: 7 layers, 411,937,983 bytes). Getting it needs one anonymous read at
`registry-1.docker.io` (with `auth.docker.io`), which this dispatch does not allow; any scratch copy the
earlier builder kept lies outside the paths this dispatch named, and none was looked for. Without it
`check_profile --strict` cannot pass on any variant, so the variant, the seed and the lock were not
written. The manifest's own sha256 authenticates whatever copy is used.

### Finding C: the label's digest reference and an image loaded offline (unverified)

The label is required as `aieh-validation:docker://<image>@sha256:<64 hex>` (`check_ci_policy`
`LABEL`; the policy's `image_rule`). Before a job the runner inspects the image by that reference and
pulls it when absent (`act/container/docker_images.go` 19-42; `docker_pull.go` 33-47 and 77-85); with
no network a pull fails the job. Decision 0016 has the image "loaded by digest at provisioning and
never pulled", the decision 0006 pattern the agent-server image follows: `docker load`, the image id
checked against the locked config digest, a local tag kept. **Expected, not verified here** (the
Moby source is not a read this dispatch allowed): Moby 26.1.5's classic image store records no repo
digest for a loaded image, and resolves a `name@sha256:<digest>` reference only through its reference
store, so the label's reference would not find the loaded image; a bare `sha256:<image id>` is
resolved by image id. Options for the Overseer or the Architect: the label names the image id
(`docker://sha256:<config digest>`, which the LABEL rule does not admit today: a policy change);
Moby's containerd image store (a daemon change, unverified); or a local tag (a mutable name, refused
by the decided rule). Finding C does not depend on finding A or B and should be settled before the
variant's config is written; Q-02.2.2 would observe it.

## 5. The job's Python tools set without network (ruling (6)): design, no implementation

The job image carries CPython 3.12 and pip but not the tools set (PyYAML, Dulwich, urllib3, keyring
and its closure) that `task test` needs, and the job has no network.

| Option | How | For | Against |
|---|---|---|---|
| **A. Staged wheels, job-local venv** | The host stages the linux x86_64 cp312 wheels of `composition/lock/python/tools-requirements.txt` (the lock already carries the `sys_platform == 'linux'` part, hash-locked) into the CI guest at provisioning, by the 0006 pattern (provision-fetch, sha256 per wheel, copy-then-verify); a root-owned directory mounted read-only into each job; a first step `python -m venv <job tmp> && <venv>/bin/pip install --no-index --find-links <mount> --require-hashes --only-binary=:all: --no-cache-dir -r tools-requirements.txt` from the bundle's own lock | The upstream image stays the pinned one; pip and the lock already exist (adoption first); the venv dies with the container (no cross-job state); `--require-hashes` fails closed when a proposal changes the lock, which is a pin revision and so a guest recreation (decision 0016 section 2.4) | A second read-only mount (so it shares finding A's question) or a place in the exchange; a few seconds of install per job; a new upload role for `provision-fetch` and the root step |
| B. Derived image | Build `FROM python@sha256:...` with the wheels installed, at provisioning (`docker build` in the CI guest, `--no-index`) or on a builder | No per-job install | A build, not an adoption; its digest is not known before the build, so it cannot be pinned in advance, and "loaded by digest, never built" no longer holds; more owned surface |
| C. Venv built once per guest | The root step builds the venv in a one-off container of the job image from the staged wheels into a root-owned directory mounted read-only | No per-job install, no build | State shared by every job of the session (read-only, but outside the per-job lifetime); an absolute venv path baked into the mount; the same mount question |

**Recommendation: A.** It keeps the pinned upstream image unchanged and the per-job lifetime of
everything a job runs, and reuses the existing lock, pip and the provision-fetch pattern. The
declaration it needs (a wheel-set entry in the variant's provision lock, its guest directory and its
read-only mount) belongs to the variant and waits on findings A to C; nothing was added to the
checker for it. Two details for the workflow (Q-01.x): `HOME` must point at a writable job directory
for the numeric `--user` (the image has no such user), and the job runs the suites with the venv's
interpreter, since `tools_install.py --python` looks in a managed data root the job does not have.
