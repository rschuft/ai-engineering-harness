## 1. The qualification launcher (`inference_qualification.py broker`)

**Choice:** a sibling module, `integrations/inference/inference_qualification.py`, holding both qualification-only
commands, so that the broker's module names no qualification at all.

```
<synthetic key> | <tools python> -I -B integrations/inference/inference_qualification.py broker --provider ID
```

It reads `components.inference_broker` once, checks it, reads the key, and then calls the broker's own command
line, `inference_broker.main(['serve'], context)`, with a `Context` copied from the managed one (or a test's)
whose `component` returns the checked snapshot, whose `provider` returns the launcher's in-memory provider and
whose `stdin` is gone. The broker is not duplicated: `serve`, its listeners, journal, audit and I7 scan run
unchanged. The broker's receipts and audit lines go where `serve` writes them; the key is written nowhere.

| Constraint (ruling section 5) | How it is enforced | The test that proves it |
|---|---|---|
| (1) every declared family's upstream is plain `http` to a loopback IP literal | `check_upstreams`: every configured family with an upstream must have `scheme == 'http'` and `Origin.loopback` (an IP literal that is loopback; `localhost` and other names are not) or the launch is refused, `QUALIFICATION_UPSTREAM_REFUSED`; at least one such family must name `--provider` (`QUALIFICATION_NO_FAMILY`). The broker's own loader refuses plain `http` to anything but a loopback IP literal first (`CONFIG_ORIGIN_INVALID`). The configuration is read once and the broker serves that deep-copied snapshot, so it cannot change between the check and the start | `TestLauncherRefusals.test_every_configured_upstream_is_plain_http_to_a_loopback_ip_literal` (an `https` family beside a loopback one, `https` to `127.0.0.1`, `localhost`, a public address, no keyed family, none at all, a secret-shaped key: each exit 2 with its code, standard input unread, nothing opened); `test_check_upstreams_accepts_loopback_literals_only` (`127.0.0.1`, `127.0.0.2`, `[::1]`); `TestLaunch` (the component read exactly once, a second read would have returned an `https` upstream) |
| (2) the key from standard input only, a terminal refused, a mandatory synthetic prefix sent verbatim | `read_synthetic_key`: the broker's `read_key` (a terminal refused, `KEY_STDIN_TTY`; one printable word, `KEY_INVALID`), then the shape `aieh-qualification-synthetic-` + 16 to 128 of `[A-Za-z0-9_-]` (`KEY_NOT_SYNTHETIC`). The key is never stripped: the broker forwards it whole, prefix included. There is no other key path (no argument, variable or file) | `test_the_key_is_a_synthetic_key_from_standard_input_only` (a terminal; a provider-style key without the prefix; the prefix not at the start; 15 and 129 characters; a `.`; a space; empty: each refused, no message repeats what was read); `TestLaunch` (the fake upstream received the credential whose fingerprint is the synthetic key's, so it went verbatim) |
| (3) the start receipt records the key's fingerprint with source `stdin-qualification`, never the key | The broker's `ProviderKey` now carries `source`, the name of the credential provider the key was read from (`credentials.describe(provider)['provider']`); the start receipt (`aieh-inference-broker-start/1`) and the status record it beside the fingerprint. The launcher's provider is named `stdin-qualification`. Under `serve` on Windows it is `windows-credential-manager` (an added field, the format unchanged) | `TestLaunch.test_the_synthetic_key_is_substituted_and_only_its_fingerprint_recorded`: the receipt's `provider_key` is `{entry, provider, fingerprint, source: stdin-qualification}`; the key appears nowhere in the store dump, the audit, the reports or the fake upstream's records; `test_serve` and `test_broker_http` updated for the field |
| (4) a separately named command, never a flag or variable on `serve`; `select_provider` never returns an in-memory provider | `serve` keeps its parser without arguments; `inference_broker.py` names no qualification and reads no environment; `SyntheticKeyProvider` is constructed only in `launch`; `credentials.select_provider` is unchanged (Credential Manager on Windows, a keyring backend on Linux and macOS, else `NO_CREDENTIAL_PROVIDER`); the provider writes nothing (`set` and `delete` refuse, `KEY_NEVER_WRITTEN`) | `TestSeparateCommand.test_serve_takes_no_flag_and_names_no_qualification` (`serve --provider`, `serve --synthetic-key`, `serve stdin`, `serve-qualification`, `broker` all exit 2 at argparse; the `serve` subparser is an unbound expression in the syntax tree; no `environ`/`getenv`; no qualification name in the source); `test_the_credential_factory_never_returns_the_launchers_provider` (the factory on Windows with a fake store, on Linux and macOS with fake keyring modules, and an unknown system; the factory's source names nothing of the launcher; `managed_context`'s provider is `credentials.select_provider` in the syntax tree; the launcher's module never names `select_provider`); `test_its_provider_holds_the_key_in_memory_and_writes_nothing` |

The launcher prints the key's fingerprint, its source and the keyed families on standard error with the label
"substitution shown with a synthetic key", the label the ruling asks the evidence to carry.

**Prefix choice.** `aieh-qualification-synthetic-`: lower case, the project's own name and the word synthetic;
no provider's key format begins so (OpenAI-style `sk-`, Anthropic-style `sk-ant-`, Google-style `AIza`, and
the other common `<vendor>_`/`<vendor>-` prefixes). A key pasted from a provider fails the prefix check; one
with the prefix added is not valid at its provider as sent.

**Reading made:** "writes nothing" (the ruling) is read as "persists no key": the launcher's provider stores
nothing and the key is in memory only; the broker it runs writes its ordinary receipts and audit lines (with
the fingerprint) to the managed integration store and logs, which constraint (3) requires.

## 2. The token issue command (`inference_control.py issue`)

```
<tools python> -I -B integrations/inference/inference_control.py issue --conversation-id UUID --family ID \
    --model NAME [--model NAME ...] --requests N --tokens N --ttl-s SECONDS [--attempt-id UUID] \
  | python -I -B tools/guest.py job-access-probe ... --attempt-token-stdin
```

- `ControlClient.issue(conversation_id, attempt_id, family, models, requests, tokens, ttl_s)` posts
  `/v1/grants` with exactly the control API's fields and checks the answer: one token of the broker's shape,
  whose fingerprint is the answer's and whose attempt is the one asked (`CONTROL_ANSWER_INVALID` otherwise,
  never repeating the token). The broker's refusals pass on by code (`MODEL_NOT_ALLOWLISTED`,
  `ATTEMPT_HAS_GRANT`, ...). The control port comes from `components.inference_broker` through
  `dispatcher_ports`, as `guest.py` reads it; there is no port option.
- Standard output receives the token and one newline, nothing else; standard error receives one line,
  `inference-control: issued: {"attempt_id": ..., "token_fingerprint": ...}` ("the grant's id" read as the
  attempt id: one grant per attempt, its receipt keyed by it). `--attempt-id` defaults to a new random UUID.
- **Guard (choice): standard output must be a pipe**, checked before the configuration is read or the broker
  asked: a terminal is refused (`TOKEN_STDOUT_TERMINAL`), so the token is not shown, and anything that is not a
  pipe (a file, a device such as `NUL`) is refused too (`TOKEN_STDOUT_NOT_PIPE`), so the token is not kept on
  disk. This is stricter than the dispatch's terminal check; it matches "for a pipe into ...". Limit: a terminal
  window that is itself a pipe (mintty, Git Bash's default window) looks like a pipe and cannot be told apart.
- Tests (`test_control.py`, against an in-process broker): `test_issue_returns_one_checked_grant`,
  `test_the_issue_command_writes_the_token_to_a_pipe_only` (a real `os.pipe()`: the token alone, flushed once,
  usable on the inference listener; standard error exactly the attempt id and fingerprint),
  `test_the_issue_command_refuses_a_terminal_a_file_and_a_broker_refusal` (no grant issued on any refusal, the
  configuration not read for the output refusals, nothing written to the pipe),
  `test_the_issue_command_requires_every_grant_field`.

## 3. The fake upstream (`inference_qualification.py fake-upstream`)

```
<tools python> -I -B integrations/inference/inference_qualification.py fake-upstream --family ID --port PORT [--address ADDR]
```

- One declared family (`families.json`), on a loopback IPv4 literal (`127.0.0.1` by default; `0.0.0.0`, a
  public address, `localhost`, `::1` and anything not exactly an IPv4 loopback literal refused,
  `FAKE_ADDRESS_REFUSED`), a port from 1024 to 65535 (`FAKE_PORT_INVALID`), all checked before anything binds;
  bound without address reuse (`SO_EXCLUSIVEADDRUSE` on Windows), no name lookup.
- A request on a declared route of the family gets one fixed answer, not a model's: the family's JSON shape
  with the text `aieh fake upstream: a fixed answer, not a model` and usage 1 and 1, which the broker's
  extractor reads (`test_each_answer_is_well_formed_and_read_by_the_usage_extractor`, all three families).
  Another route, method or a query answers 404; a chunked body or an invalid length 411 with `Connection:
  close`; a body is read and discarded, never kept.
- Records (`aieh-inference-fake-upstream/1`, one JSON line per request on standard output, flushed, before the
  answer): `method`, `path` (a declared route only, else `null`), `header_names`, `credential_fingerprints` (the
  fingerprint of each value of the family's auth header, its scheme word removed), `status`; `start` and `stop`
  lines frame them; a handler error is a `handler-error` line with the error's type.
- The substitution is shown by comparison: the record's credential fingerprint equals the start receipt's
  provider-key fingerprint and differs from the token's (`TestLaunch`).
- Tests: `TestFakeUpstream` (refusals before any bind; the answers; records with names and fingerprints and no
  header value, body, model name or query; exclusive port, freed at stop; bodies drained on a kept-alive
  connection; a handler error recorded).

## 6. Defect found: a race in slice 1's streaming fixture (fixed forward in `3498199`)

The first baseline of the mutation harness (four workers in parallel) failed once in
`test_broker_http.TestPassThrough.test_a_stream_is_passed_on_as_it_arrives`: the fake upstream set `first_sent`
after writing and flushing the first event, so the broker could relay those bytes and the test read them before
the event was set. **Classification: unrelated-but-detected** (slice 1's fixture, not this slice's code; detected
under the mutation run's load). The fixture now sets the event before the write; the inference suite and every
later baseline passed.

## 9. Not verified, limits and findings

- **Not verified (each part of act A2 or later):** the launcher against the managed root and a fake upstream
  outside a test process; the fake upstream as a process; `issue` piped into `guest.py job-access-probe
  --attempt-token-stdin` through a real PowerShell or Git Bash pipe (the pipe check was observed with an
  `os.pipe()` only); the comparison of the fake upstream's credential fingerprint with the start receipt in a
  qualification run; Linux and macOS (`SO_EXCLUSIVEADDRUSE` is Windows-only; the pipe check uses `S_ISFIFO`).
- **Limits:** a terminal that is a pipe (mintty) passes the `issue` guard; the fake upstream serves IPv4 only
  (the broker also admits `http://[::1]`, which the launcher accepts, but the fake upstream cannot serve there);
  the launcher's keyed-family rule needs one family named with `--provider` (a keyless loopback family alone is
  refused, since it would show no substitution).
- **Found, not changed:** the `inference-broker` role's realization note (section 4); the plan step 7 wording
  in slice 3's record ("no harness command issues it") is history and stays.
