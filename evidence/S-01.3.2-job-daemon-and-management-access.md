## 3. Hardening applied, with each option's upstream mechanism
1. **The Agent Server's own configuration** (decision 0006 channel, the seeded
   `config.json`): `enable_browser: false`. Conversation containers get
   `OH_ENABLE_BROWSER=0` by this setting rather than only because the local tag is not the
   stock image's. The guest's `config.json` held it (`inspect` A and B). The caps and image
   were already explicit. The server offers nothing else for its containers, so everything
   else the job profile requires is **declared and verified**, not configured: the hard-coded
   flags (cap-drop ALL, `no-new-privileges`, exactly three binds, no socket mount, the
   loopback port) and the Moby defaults of section 2.
2. **Moby daemon defaults:** none added. The two the job profile relies on were already in
   `daemon.json`: `no-new-privileges: true` (the daemon-wide default behind the server's own
   flag) and `icc: false` (S-01.3.1). `provisioning.moby.required_security_options` now names
   the daemon defaults the jobs rely on (`name=no-new-privileges`, `name=apparmor`,
   `name=seccomp,profile=builtin`, `name=cgroupns`), which `inspect`'s Moby daemon check
   requires (a strengthening). Considered and not applied:
   - `host-gateway-ip` would retarget `host.docker.internal`, not remove it;
   - `ip-forward: false` would cut the NAT path, which belongs to S-01.4's deny-by-default
     matrix;
   - `userns-remap`, another runtime or rootless Moby are structural (STOP condition; not
     needed by any observation here, recorded for S-02.1 in `fd-container-shares-service-uid`);
   - `default-ipc-mode` and `default-cgroupns-mode` are already `private`; the per-container
     check catches a change.
3. **`host.docker.internal`:** not removable cleanly (no Config option; the flag is
   unconditional). Carried (section 10); every port there is refused by the container guard.
4. **The declared job profile**, `provisioning.agent_server.jobs` (data, as S-01.3.1 added
   `admission`):
   - `host_config`: exact `HostConfig` values and the AppArmor profile (section 2);
   - `environment`: the conversation's two keys are the only credential-like names allowed;
   - `process`: the in-container capability, `no_new_privs`, seccomp and AppArmor rule;
   - `engine_sockets` (10 paths), `engine_tcp_ports` (2375, 2376), `host_alias` (10.0.2.2
     with the instance's SSH and QMP ports and the host Gitea's 13300; 10.0.2.3);
   - `credential_files`, the token rule, the deviations, the fail-closed statement and the
     CI constraints.

   `check_profile` validates it (`check_jobs`: exact values, no unconfined, disabled or
   privileged option, Moby's `no-new-privileges` and required options, no engine variable in

   `inspect`'s `conversation containers` check and every container check of
   `conversation-smoke` and `admission-probe` now apply the declared values to every

## 10. Findings
1. **The conversation image ships engine clients and setuid-root helpers** (exposed by this
   leaf; upstream image content). `docker`, `ctr`, `containerd`, `runc`, setuid-root `sudo`,
   `su`, `mount` and others; the image's own `openhands` user (uid 10001) is in group `sudo`.
   Inert in a job (no endpoint, `no_new_privs`, no capability, uid 999 unnamed), but a job
   that gained an engine endpoint would find the client installed. New limit
   `fd-job-image-engine-clients`, carried to S-02.1 and E-01.2.2.
2. **`host.docker.internal` cannot be removed by configuration** (exposed; upstream). Carried
   in `fd-container-network-deviations` (S-01.4, E-01.2.2, S-02.1) with the NAT path out:
   from a job, SLIRP's aliases refuse and off-guest addresses are unreachable; the
   deny-by-default matrix stays S-01.4's.
3. **`fd-container-shares-service-uid` narrowed** (open-risk, carried to S-02.1): the job
