## 1. The qualification create (slice 2)

`integrations/dispatch/acp_qualification.py` with two pinned data files under `integrations/dispatch/qualification/`
(README section "The ACP qualification create (S-03.3, slice 2)"):

- **The fixture** (`acp-claude-code-create.json`, sha256 pinned in the module): the Docker runtime, `/workspace`,
  `agent_settings` `{agent_kind: acp, acp_server: claude-code, acp_command: ["claude-agent-acp"], acp_args: [],
  acp_model: <approved>, acp_session_mode: null, acp_isolate_data_dir: true, mcp_config: {}}`, `secrets`
  `ANTHROPIC_API_KEY` (the attempt token) and `ANTHROPIC_BASE_URL` (the guest endpoint), both `StaticSecret`,
  `secrets_encrypted` false, no browser, `autotitle` false, the tag `s-03.3-disposable`. Four placeholders, each
  filled and checked: the reserved conversation id, the model, the token, the endpoint. `acp_session_mode` null
  leaves the registry's `bypassPermissions`, which is documented as conferring no authority and as no isolation
  control (recommendation R2; the Owner's OA-12 words).
- **The registry extract** (`acp-registry-claude-code-1.60.1.json`, sha256 pinned): the registry facts the fixture
  relies on, each with its source line in the locked wheels, whose sha256 it names (equal to the lock, checked by a
  test). The fixture's command and secret names are checked against it at every load.
- **Admission** (`check_create`; `build_create` fills and checks): exactly the fixture with its four values;
  every other shape refused with a stable code. Per the dispatch: `StaticSecret` only, a `LookupSecret` or any other
  source refused (`SECRET_KIND_FORBIDDEN`, F-2); exactly `["claude-agent-acp"]`, the empty or absent command (the
  `npx` fallback), the `npx` form, a path, a shell, an `env` prefix, another adapter and any `acp_args` refused
  (`ACP_COMMAND_NOT_PINNED`); `agent_profile_id` and other profile references refused
  (`AGENT_PROFILE_FORBIDDEN`); MCP fields and a non-empty `mcp_config` refused (`MCP_FORBIDDEN`); tools, skills,
  plugins, hooks, client tools, agent definitions, launch additions and an `agent_context` refused
  (`TOOLS_FORBIDDEN`); the base URL must be the profile's one `network.endpoints` entry of class `inference`
  (`http://172.17.0.1:8090` for `strong-windows-qemu-whpx`) and no other URL may appear anywhere
  (`DESTINATION_NOT_ENDPOINT`). Also: the secret names exactly the registry's two (no `OH_*` name, no OAuth token);
  `ANTHROPIC_API_KEY` exactly one broker-issued token (the broker's own `TOKEN_SHAPE`), never a provider-key shape,
  and the token, its body or any other token nowhere else; the model one name of the family's configured
  allowlist (the broker's `MODEL_NAME`; an empty allowlist approves nothing); the conversation id the reserved one.
- **A real stage refuses it.** The dispatcher's own body check against the checked-in profile's template and
  admission policy refuses the create (`BODY_FIELD_UNKNOWN` on `secrets`; without the secrets, `BODY_NOT_TEMPLATE`
  on `agent_settings`) while it admits the template itself, and its artifact reader reads only
  `profiles/<id>/...`, so neither qualification file can be pinned by a profile (`PROFILE_ARTIFACT_MISSING`). The
  qualification check refuses the stage template in turn (`TOOLS_FORBIDDEN`, then `ACP_SERVER_NOT_PINNED`). No
  change to the typed create of E-01.3.1 was needed, so the STOP condition on its accepted contract did not arise.

## 2. The refused-request audit (slice 3, part one; D-4)

`inference_broker.py` `Broker.observed_request`, written into the audit line of every refused request (README
"Audit"): `path`, `query_names` (sorted, at most 16) and, for a request that presented a grant's token, the
`model` of its JSON body (the body the refusal drains anyway, at most 1 MiB, when the refusal came before the body
was read). Each is recorded only in a bounded grammar: a path segment or a name of at most 32 characters of
`[A-Za-z0-9._~-]` (at most 16 segments), a model in the broker's `MODEL_NAME` (at most 128 characters); none
holding the token prefix; each passed through the broker's I7 guard (the provider key, every issued token, 40-hex
runs) on its own. Anything else is counted under `unrecorded` (`path`, `query_names`, `model`), never written.
Never a query value, a header, any other body field, the token or the key. An admitted request's line is as before
(its declared route and admitted model); the two new keys are `null` there. A request without a grant's token gets
its path and names recorded and its body is not parsed.

Disclosed: a secret the broker does not hold (for example another credential of the guest) that a client places
deliberately in a path segment, a parameter name or the `model` within those grammars is not recognized; the
32-character bound keeps out every credential shape in play (the attempt token 52 characters, provider keys over
100, the conversation keys of 43 each, `secrets.token_urlsafe(32)` in `agent_server/docker_runtime/provisioning.py` 161-162), and the guard keeps out what it holds.

## 3. F-3: can the create remove or blank the conversation keys from the adapter's environment?

**No, not without changing OpenHands' code.** Read in the locked wheels (`openhands_sdk-1.60.1`, sha256
`f6efa8f8…45eb6b`; `openhands_agent_server-1.60.1`, `df80a622…be76f6`); each line is also in the registry extract:

| Candidate | What it does at the pin | Source |
|---|---|---|
| `env_conflicts` | A field of the provider's registry entry (`ACPProviderInfo`, `compare=False`), not of `ACPAgentSettings` or the create. Applied by `ACPAgent._strip_conflicting_env` only when the entry's `dominant` variable is in the environment; Claude Code's one entry strips `ANTHROPIC_API_KEY` and `ANTHROPIC_BASE_URL` when `CLAUDE_CODE_OAUTH_TOKEN` is present. It never names an `OH_*` variable, and an unknown server takes the union of all entries, none of which does | `sdk/settings/acp_providers.py` 301, 404-409; `sdk/agent/acp_agent.py` 2811-2834 |
| `acp_env` | Does not exist at 1.60.1 (no occurrence in the SDK, agent-server or tools wheels). `ACPAgentSettings` declares no environment field (its fields: `agent_kind`, `acp_server`, `acp_command`, `acp_args`, `acp_model`, `acp_session_mode`, `acp_prompt_timeout`, `acp_startup_timeout`, `mcp_config`, `acp_isolate_data_dir`, `acp_file_secrets`, `agent_context`, `verification`, and the base's `schema_version`), and it sets no `model_config`, so an unknown key is ignored by pydantic's default rather than applied | `sdk/settings/model.py` 564-565, 1786-2012 |
| A settings-level or secrets override | The subprocess environment is `default_environment()`, then the inner server's `os.environ`, then the **non-empty** values of the whole secret registry, then the data dir, file secrets, `CLAUDECODE` removed and `env_conflicts`. An empty, whitespace-only or redacted `StaticSecret` value validates to `None`, and `get_all_secrets_as_env_vars` skips it, so a secret named `OH_SECRET_KEY` or `OH_SESSION_API_KEYS_0` can neither remove nor blank the inherited value. Only a non-empty value replaces it: a placeholder, which is neither removal nor blanking, is not the ruling's mechanism, would add secret names beyond the registry's two (which the admission refuses), and leaves the real values in the inner server's own `/proc/<pid>/environ`, readable by the same user | `sdk/agent/acp_agent.py` 3076-3101; `sdk/utils/pydantic_secrets.py` 133-135; `sdk/conversation/secret_registry.py` 250-284 (281) |
| `acp_command` (a wrapper or `env -u`) | A non-empty command is used verbatim, so `["env", "-u", "OH_SECRET_KEY", ..., "claude-agent-acp"]` would unset them, but it is an arbitrary ACP command: the Owner's constraints and the ruling require exactly `["claude-agent-acp"]`. The image's wrapper (`/usr/local/bin/claude-agent-acp`, `PATH="/acp-node/bin:$PATH" exec "/acp-node/bin/claude-agent-acp" "$@"`, image check) unsets nothing | `sdk/settings/model.py` 2047-2073; [image check](S-03.3-image-adapter-check.md) |

Also from the sources: the native terminal's environment strips both (`sanitized_env`, `sdk/utils/command.py`
17-30, 62-68); the ACP subprocess's does not; and the Docker runtime passes both into the conversation container
(`agent_server/docker_runtime/registry.py` 615-665). **F-3 is therefore recorded as disclosed, the existing
exposure class** (S-01.3.1 and S-01.3.2: both keys readable by the container's user through `/proc/1/environ`),
with a new path (the adapter and every process it starts inherit them). Nothing was changed for it: no field is
sent for it, and slice 1's observation was not changed (it reads no environment by design; a check that the
adapter's environment lacks the keys would fail at the pin, by the reading above). The admission refuses any
`OH_*` secret name, so a create cannot add a second path either.

- its verdict: `tools/guest.py` `job_env_verdict` (7141-7144), the job probe's specification (10283-10305,

amendment first.
