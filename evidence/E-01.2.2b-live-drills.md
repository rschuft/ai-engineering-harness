## 4. Proof item (2): the stored state

### 4.1 Method (`e0122b-d`, `794ff96`, 10:12:48Z to 11:42:55Z, 5407.4 s)

One disposable conversation (the fixture with id `e0122b00-…-d001`) was created (201), its
runtime stopped, and its directory, `/srv/scratch/openhands/conversations/<hex>`, read and
snapshotted root-only: `base_state.json` (2,681 bytes), `meta.json` (1,030 bytes), both
`999:989` `600`, and `.owner_lease.lock` (0 bytes). This is the job's own conversation-store
bind (S-02.1, S-02.2: uid 999 writes it from inside the job).

**The alterations: 136.** Every field of the two stored files, one at a time: 37 in
`meta.json` and 95 in `base_state.json` (a field is a scalar, an empty object or a list without
objects; objects and lists of objects are walked). Each gets one altered value, aimed at
steering where the field's name suggests it: a path or a working directory becomes a new path
under the outer server's writable home, `/srv/scratch/openhands/home/aieh-drill-<n>` (which no
container mount reaches, so its appearance on the guest is steering); `execution_status`
becomes `running`; a runtime `local`; an image `busybox:latest`; an id a foreign UUID; a
timestamp another year; a boolean its negation; a number +7 or +1000; other text gets a suffix.
Then the targeted additions: `meta.json` `container` `{"memory": "8g", "cpus": 4.0}` and
`conversation_runtime` `local`, a planted `owner_lease.json` (a foreign owner, far expiry), and
one combination, the start-up pair: `execution_status` `running` with `meta.json`
`workspace.working_dir` pointed at a new path.

Each alteration was written by the drill helper while the runtime was stopped, keeping the
files' owner and mode: files the job's uid can write (S-02.1). Section 4.4 shows which of the
steering values survive when the job writes them itself.

**One cycle per alteration:** restart the Agent Server (its start-up path); observe its
processes, the journal of that start (its own invocation only) and the altered path; read the
outer view (`/server_info` runtime, an unauthenticated `GET` of the conversation, the
authenticated `GET` and `…/runtime`); reopen (`POST …/runtime/reprovision`); read the root
conversation facts and compare the container with the baseline cycle: `.Image`,
`Config.Image`, `User`, `WorkingDir`, `Entrypoint`, `Cmd`, environment names, AppArmor profile,
owner label, the effective mounts and 33 `HostConfig` keys (binds, caps `Memory`/`MemorySwap`/
`NanoCpus`/`PidsLimit`, `CapAdd`/`CapDrop`, `SecurityOpt`, `Privileged`, network, PID/IPC/user
namespaces, `Runtime`, devices, port bindings, …), and the container's two key fingerprints;
then stop the runtime, roll the directory back to the snapshot, restart the server (dropping
whatever it loaded), roll back again and read the directory, which must equal the snapshot.

## 5. Proof item (3): the guest-root P5 scan

`drill --kind root-scan --canaries <the set create planted> --raw`, with one disposable
conversation running so that its container and keys are in the scan. As root, in the guest:
every regular file of every disk-backed and tmpfs mount (no mount crossed, no link followed),
every `/proc/<pid>/environ` and `cmdline`, and with `--raw` the raw block devices. Searched for:
- the canary set's 32-hex cores, by sha256 only (the values never enter the guest; 12 cores for
  the 13 needles of each set; the 13th, the AWS access key id, has no core and is covered by the
  cloud-token pattern; every core of both sets was bounded, so the guest's matcher could see it);
- the guest's own secrets, by value, in the guest: the server's `OH_SECRET_KEY` and session key
  (from `secrets.env` and `session.key`) and the running container's own two keys;
- private-key blocks (body sha256, compared with the instance's private key on the host);
- the Owner-class patterns of `profiles` P5 plus the Windows profile-path shape;
- a positive control planted root-only outside every store (a canary-shaped value, a secret-shaped
  value and a private-key block) and removed afterwards.

A guest secret is allowed only in its declared store: the server's in `secrets.env`, the
agent-readable `session.key` (P5, amended 2026-11-07) and the server's process environment
(`provisioning.agent_server.secrets.delivery`); a conversation's own keys in Moby's store of
