## Residuals (accepted)

- The SDK retries a `-32603` failure up to 3 more times per turn (appendix R8), so a token the provider refuses may
  be sent up to four times within the attempt before the refusal surfaces (upstream behaviour).
- The conversation's events are persisted in a directory mounted into the agent's container: a forged or erased
  event can turn an authentication refusal or an unclassified end into an interruption; it can never turn a security
  stop into anything else (the security stops are the dispatcher's own records; the end record holds only values of
  closed sets). The engineering manager can escalate any end to a security stop.
- The producers of the dispatcher's stop records (E-05.10's tunnel census, E-05.9's outbound token search, S-03.3's
  containment observation) are wired to the end at E-05.5 (carried); here they are validated inputs.
- Carried to E-05.4: the result path refuses an attempt that has an end record; whether a rework follows a finished
  attempt.
- The cause commands are bound to no principal (the engineering manager's by convention; decision 0010 point 1's
  same-account limit).

### 2. How a provider refusal, a cut stream and a lost path surface

The chain: the CLI turns an API failure into a synthetic assistant message with a text (prefix `API Error`,
`claude @252036377`) and an error kind (`_u`, `claude @259429512`; `ley`, `@252017922`; `Tpo` adds `apiErrorStatus`,
`@252017713`). The adapter keeps the last top-level assistant message's `error` (`acp-agent.js:2615`) and, when the
turn's result `is_error`, fails the prompt with `RequestError.internalError` (`-32603`) whose message is the result
text and whose data is `{"errorKind": <kind>}` (`:2316-2365`, `errorKindData` `:4528`); a `Please run /login` text or
a synthetic login message fails it with `RequestError.authRequired` (`-32000`, `:2307-2310`, `:2668-2669`). The SDK
(after R8's retries) emits an agent `MessageEvent` `ACP error: <detail>` and a `ConversationErrorEvent` with `code`
from `_classify_acp_turn_error` (`ACPAuthRequired` for `-32000` or a `-32603` whose text has `401`/`403` or an auth
marker; `UsagePolicyRefusal`; otherwise `ACPPromptError`) and `detail` = `[<code>] <message>: <data>` (secret-masked,
at most 500 characters), and sets `execution_status` `error` (`sdk/agent/acp_agent.py:1143-1160`, `:1212-1238`,
`:1277-1291`, `:4029-4073`). A failure at start-up surfaces the same way from `init_state` (`ACPAuthRequired`,
`ACPStartupTimeout`, `ACPSpawnError`, `ACPInitError`; `:1241-1275`, `:2416-2450`). The run loop adds no second event
when the agent emitted one (`sdk/conversation/impl/local_conversation.py:135-165`, `:2249-2268`). The event's
`classification` is the SDK's `classify_error`, which classifies `ACPPromptError` as `config` before reading the
detail, so a rate limit there is `config` (`sdk/event/error_classification.py:65-81`): the dispatcher records it and
does not use it. The Agent Server serves the conversation's `execution_status` (`GET /api/conversations/{id}`) and its

### 4. Limits of reading the conversation (after the independent review)

- **The events are not the dispatcher's.** The Docker runtime bind-mounts the conversation's host directory into the
  agent's container (`as/docker_runtime/registry.py:669-673`), and the conversation's events are persisted there; a
  process of the attempt can forge or erase them. A forged or erased event can turn an authentication refusal or an
  unclassified end into an interruption; it can never turn a security stop into anything else (the security stops are
  the dispatcher's own records). The end therefore records only values of closed sets, and the engineering manager can
  always escalate an end to a security stop (`record-end-cause security-stop`).
- **The 500-character cut.** The SDK caps the detail at 500 characters after masking (`acp_agent.py:1212-1238`). A
  detail cut there loses the adapter's trailing `{"errorKind": ...}` data, and its end may be the message's decoy;
  the dispatcher reads no error kind from a detail of 500 characters or more (fails closed, unclassified).
- **Decoys.** The CLI's message (the part before the data) can quote the provider's response; the error kind is read
  only from the trailing data, and a detail naming more than one distinct error kind classifies nothing.
- **Order.** Only the last `ConversationErrorEvent` decides, and only when no later agent or user `MessageEvent` or
  `ActionEvent` shows the conversation went on (the SDK writes its `ACP error:` message before the error event,
  `acp_agent.py:4029-4073`, so a genuine terminal error is last; a hook- or environment-sourced event does not count).
- **Unverified, live:** the event search's paging (`next_page_id` as the next `page_id`, `as/event_router.py:68-141`,
  `as/event_service.py` `search_events`) is read, never run against a live server.
