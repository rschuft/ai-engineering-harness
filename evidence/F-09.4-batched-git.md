## 2. What was built (Part B)

| Change | Commit | What |
|---|---|---|
| Batch reader | `cc5bca7` | `planning_adapter.BatchReader`: one `git cat-file --batch` process (git's own batch protocol). One request line per object name; `<oid> <type> <size>`, contents and a newline back, or `<name> missing` / `<name> ambiguous` (the echoed name must equal the request). Standard output and error are drained by two daemon threads; each request waits on a condition with the `TOOL_TIMEOUT_S` deadline (read at call time). `close()` closes standard input, waits for git (kills it past the ceiling) and joins the threads. |
| Read sessions and memos | `cc5bca7` | `Git.session()` (re-entrant context manager): one reader, started on the first object read, closed when the block ends. Memos for the session only: objects by an immutable name (`<full id>` or `<full id>:<path>`), revisions (each resolved once, a snapshot), file lists by (full commit id, directory). Outside a session each call opens and closes its own. `commit`, `object_type`, `blob` and the new `object_kind` read through it; the work-tree check (`rev-parse --show-toplevel`), `ls-tree` and `archive` stay single commands with the same argv. | Benchmark | `fea80e7` | `integrations/lineage/tests/test_traversal_git.py` `OneTraversal` (category `performance`): one traversal of the two-task example per registry; its result is the launch count. |

## 6. Dulwich: **not adopted** in this leaf

- **Documented capability** (blueprint `#integration-contracts`, "Repository ↔
  integration": "Dulwich ... Our Python adapters require no Git executable"; decision card
  SHIP-02 "ADOPT Dulwich within Python adapters", with the verification "validate supported
  clone/commit/ref/push/auth operations on target OS and Gitea for pinned Dulwich"; SHIP-03:
  Dulwich is dual Apache-2.0/GPL). Dulwich reads git objects, refs and trees in Python, so
  it could serve these reads with no process at all. It is not installed here, not pinned in
  `composition/`, and the dispatch forbids a new dependency; it was not run or measured.
- **Measurement of the batched git path:** one traversal 808 → 55 ms with 4 processes, of
  which three are single commands (about 35 ms at 11.6 ms each); a batch request costs 0.30
  ms. The most Dulwich could remove from a traversal is those launches, about 35 to 40 ms;
  across the suites the remaining product git launches (542 `cat-file`/`rev-parse` plus 165
  `ls-tree`, about 8 s at 11.6 ms each, an upper bound) are the most it could remove from the
  serial run.
- **Outcome: not adopted, because** the leaf's purpose is met by git's own batch protocol
  for nearly all of the measured cost, while adoption is a new hash-locked dependency (a
  non-goal of this dispatch), needs proof that Dulwich answers as git does for the revision
  grammar, the work-tree check, `ls-tree` and `archive`, and carries the release licence gate
  (dual Apache-2.0/GPL). No adoption is proposed, so no gate C consultation was needed.
- **Recorded for the Overseer:** this does not settle the blueprint's own target. SHIP-02 and
  `#integration-contracts` say our Python adapters need no Git executable;
  `lineage_schema.json` already records that the design resolver, like P-02.1, runs git. That
  deviation stays open and is unchanged by this leaf.

## 11. Findings

Classified per the fix-forward rule.

- **Introduced by this leaf, fixed before commit:** a shell heredoc turned `\0` and `\n`
  escapes in the `test_verify_seed` edit into a NUL byte and a line break (rewritten
  bytewise, checked); a first `read_readiness` edit took a shortcut and was reverted for a
  clean split; the first mutation set showed the batch reader's echo check untested (test
  added); the new tests' first timeouts (0.5 s) and one-reader-per-call equivalence loops were
  made cheaper (0.2 s, one session). A copy of `test_verify_seed.py` was briefly written to
  `%TEMP%\tvs_keep.py` (Git Bash `/tmp`) during a negative control, outside the authorized
  scratch directory, and removed.
- **Exposed by this leaf, not fixed (decisions for the Overseer):**
  - **Serial `task test` is 154.2 s, not at most 150 s** (section 7); the ranked remaining
    costs are in section 7. Every one needs a ruling the dispatch reserves or a change of
    test design outside these leaves.
  - **Product `cat-file` + `rev-parse` launches fell 88.2%, not 90%, across the three
    suites** (section 4): per traversal −97%, lineage suite −92.0%. The rest is one work-tree
    check and one reader per independent read, which only sharing across reads (excluded by
    the memo constraint) would remove.
  - **"At most 10 processes"** holds with Backlog.md answered in the test process (4); with
    the fake Backlog.md launched it is 13, the 9 being Backlog.md reads outside the git
    adapter (section 3).
  - **Whitespace in a repository path is now refused**: an OpenSpec change directory whose
    name holds a space (`openspec/changes/<a b>/.openspec.yaml`) makes the objective resolver
    answer `authority-unavailable` `GIT_FAILED` (`OBJECT_NAME_INVALID`) instead of reading it.
    This follows the dispatch's input-safety rule (no whitespace reaches the batch protocol);
    OpenSpec change ids are kebab-case, so a conforming repository has none. No test covered
    the old behaviour.
  - **A TEMP of about 124 characters or more breaks the publication-gate tests' fixture push**
    (section 1.2; 20 errors at 131, all pass at 123): the fixture's git has no
    `core.longpaths`. Not fixed: it is the gate's test fixture, and the F-09.3 criterion (a
    TEMP of at least 100 characters) is met.
  - The blueprint's Dulwich target (section 6) stays open.
- **Unrelated but detected:**
  - `integrations/paths/tools_install.py`'s docstring still describes the dev set as "the
    pytest and pytest-xdist set" (F-09.3 recorded it; unchanged).
