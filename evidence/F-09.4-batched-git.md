## 2. What was built (Part B)

| Change | Commit | What |
|---|---|---|
| Batch reader | `cc5bca7` | `planning_adapter.BatchReader`: one `git cat-file --batch` process (git's own batch protocol). One request line per object name; `<oid> <type> <size>`, contents and a newline back, or `<name> missing` / `<name> ambiguous` (the echoed name must equal the request). Standard output and error are drained by two daemon threads; each request waits on a condition with the `TOOL_TIMEOUT_S` deadline (read at call time). `close()` closes standard input, waits for git (kills it past the ceiling) and joins the threads. |
| Read sessions and memos | `cc5bca7` | `Git.session()` (re-entrant context manager): one reader, started on the first object read, closed when the block ends. Memos for the session only: objects by an immutable name (`<full id>` or `<full id>:<path>`), revisions (each resolved once, a snapshot), file lists by (full commit id, directory). Outside a session each call opens and closes its own. `commit`, `object_type`, `blob` and the new `object_kind` read through it; the work-tree check (`rev-parse --show-toplevel`), `ls-tree` and `archive` stay single commands with the same argv. ## 6. Dulwich: **not adopted** in this leaf

*Round 2 (section R.5) replaces this outcome and its reasons, the licence point included; the
measured facts stand.*

- **Documented capability** (blueprint `#integration-contracts`, "Repository ↔
  integration": "Dulwich ... Our Python adapters require no Git executable"; decision card
  SHIP-02 "ADOPT Dulwich within Python adapters", with the verification "validate supported
  clone/commit/ref/push/auth operations on target OS and Gitea for pinned Dulwich"; SHIP-03:
  Dulwich is dual Apache-2.0/GPL). Dulwich reads git objects, refs and trees in Python, so
  it could serve these reads with no process at all. It is not installed here, not pinned in
  `composition/`, and the dispatch forbids a new dependency; it was not run or measured.
- **Measurement of the batched git path:** one traversal 808 → 55 ms with 4 processes, of
  which three are single commands (about 35 ms at 11.6 ms each); a batch request costs 0.30
  ms. The most Dulwich could remove from a traversal is those launches, about 35 to 40 ms;
  across the suites the remaining product git launches (542 `cat-file`/`rev-parse` plus 165
  `ls-tree`, about 8 s at 11.6 ms each, an upper bound) are the most it could remove from the
  serial run.
- **Outcome: not adopted, because** the leaf's purpose is met by git's own batch protocol
  for nearly all of the measured cost, while adoption is a new hash-locked dependency (a
  non-goal of this dispatch), needs proof that Dulwich answers as git does for the revision
  grammar, the work-tree check, `ls-tree` and `archive`, and carries the release licence gate
  (dual Apache-2.0/GPL). No adoption is proposed, so no gate C consultation was needed.
- **Recorded for the Overseer:** this does not settle the blueprint's own target. SHIP-02 and
  `#integration-contracts` say our Python adapters need no Git executable;
  `lineage_schema.json` already records that the design resolver, like P-02.1, runs git. That
  deviation stays open and is unchanged by this leaf.

### R.1 R1: spaces in object names (`417c904`)

- The reader's argv is `git -C <project> cat-file --batch`, with no format and so no
  `%(rest)`: git takes the whole request line as the object name. Checked in the code
  (`Git.batch_argv`) and by the tests below.
- An object name (`<rev>:<path>`) may again hold a space or other whitespace that is not a
  control character. Refused before the process (`OBJECT_NAME_INVALID`): the C0 controls (line
  feed, carriage return, NUL and the others, **tab** among them) and DEL, a leading `-`, a
  name that is not text. Revisions keep refusing any whitespace (`REVISION_INVALID`), as at
  `352920a`.
- A `<name> missing` or `<name> ambiguous` answer is now matched against the whole request
  line; round 1 split the line on spaces, which would have failed closed on a missing name
  with a space.

  `352920a` read it. No conforming OpenSpec id contains one.

### R.2 R3: one operation, its proofs and the two launch criteria (`417c904`)

`planning_adapter.operation()` (a context variable around an `ExitStack`) is one top-level
operation:

- one lineage traversal (`Traversal.run`);
- one readiness evaluation (`planning_readiness.read_readiness`), and so one dispatch read
  (`PlanningWorkSource.read`, which lists the tasks and then evaluates);
- one resolution from the command line (`planning_adapter.py resolve` / `pointer`) or from a
  lineage resolver entry point (`DesignResolver.resolve/current`, `ObjectiveResolver`,
  `WorkResolver.resolve/current`, `CommitResolver.resolve`).

Within an operation:

- `project_git(project)` gives one `Git` per project (one work-tree check) with its read
  session open (one batch reader);
- Backlog.md's reads are a snapshot: the same `task list` or `task view` in the same directory
  with the same command runs once (a failure too); a `task create` ends that snapshot.

Inside an operation, a nested one is the same operation. When it ends, normally or by an
exception, every session is closed and the snapshot dropped. There is no module-level cache
and no cross-operation state. `lineage_resolve`'s own scope from round 1 is replaced by it.

The proofs extended to the new scopes:

| Operation git sharing and lifecycle | `test_git_batch.OperationScope`: one `Git` and one reader per operation, a new one for the next (one work-tree check each); an unreadable project is answered once; an exception ends the reader; a timeout fails closed and ends the reader; a readiness evaluation runs `task list` once and each `task view` once, with one reader |

### U.2 The G2 mechanism: one process tree per git process

**Chosen: a process tree** (`planning_adapter.ProcessTree`; `run_tree` for the one-shot
commands).

- **Windows.** The process is created suspended (`CREATE_SUSPENDED` through
  `subprocess.Popen`'s `creationflags`). It joins a new job object with
  `JOB_OBJECT_LIMIT_KILL_ON_JOB_CLOSE`, then resumes. So the launcher cannot start the real
  git before it is in the job, and every process it starts is in the job too. `kill`
  terminates the job, then waits for each member process (handles opened before the
  termination, checked with `IsProcessInJob`), and loops until the job is empty or the
  ceiling passes. `close` kills what is left and closes the job handle; kill-on-close also
  ends the tree if the Python process dies first. If the process cannot join its job, it is
  killed and the start raises `OSError`: it is never left running outside the job.
- **Resume.** `ntdll`'s `NtResumeProcess`, as psutil resumes a process. It is not in the
  Win32 documentation, so the documented path is the fallback: a Toolhelp walk of the
  system's threads with `OpenThread` and `ResumeThread`. A test forces the fallback.
- **POSIX.** The process leads a new session (`start_new_session=True`), and `kill` sends
  `SIGKILL` to its process group. Liveness uses `waitid(WNOHANG | WNOWAIT)`, so the leader is
  not reaped and the group id cannot be reused before the kill. **Not verified:** no POSIX
  run was possible here (WSL is protected).
- **The reader (G1).** Before each request is written, `BatchReader.read` checks that its
  process still runs. One that has exited marks the reader broken: the tree is killed, and
  `GIT_FAILED` "exited N" is raised before anything is written. Every later read raises
  `GIT_FAILED` at the existing `_broken` check. A timeout, a protocol error and a write or
  read at the end of the output still mark the reader broken as before; each now kills the
  whole tree.
- **The one-shot commands.** The work-tree check, `ls-tree` and `archive` go through
  `run_tree` (`Git._run`). `subprocess.run` with a timeout kills only the launcher, then waits
  in `communicate()` for the pipes to close, which the orphaned real git holds open. `run_tree`
  kills the tree and waits for each process, then reads what is left. Backlog.md and OpenSpec
  calls are not git calls and are unchanged.

**Evidence** (scripts and outputs in `…\c8\`):

| Probe | Result |
|---|---|
| job limits read back (`probe_job.py`) | `LimitFlags` 0x2000; structure sizes 64, 144 and 28 bytes, as on Win64 |
| kill-on-close alone | a sleeping child in the job ended at once when only the handle was closed |
| real launcher (`test_git_batch.RealLauncher`) | the launcher has exactly one `git.exe` child; after an external kill of the launcher that child still runs (the defect), and the reader's next read ends it |
| resume cost (`bench_resume.py`, 4,802 threads on the host) | Toolhelp walk 20.72 ms per process; `NtResumeProcess` 0.02 ms |
| per-launch cost, `git --version` (`bench_launch.py`, 40 each) | `subprocess.run` 18.7 and 19.1 ms median, `run_tree` 16.9 and 18.5 ms: no added cost with `NtResumeProcess` (41 ms with the Toolhelp walk alone) |
| launcher against real binary (`bench_resume.py`) | `cmd\git.exe --version` 16.2 ms, `mingw64\libexec\git-core\git.exe --version` 9.2 ms median |

**Rejected:**
- **Resolving the real git once** (`git --exec-path`, then `<exec-path>\git.exe`). It would
  save about 7 ms per git launch, but:
  - it works only where the launcher is recognized, and a fallback to the PATH git (an
    unknown launcher or shim) would still orphan;
  - it changes the binary and the environment the adapter runs: the launcher prepends
    `mingw64\bin` and `usr\bin` to PATH and sets `MSYSTEM`, and `archive` can run filters
    through `sh` (G3);
  - it is an optimization, a non-goal here.

  It remains available for a ruling, with the measured saving.
- **Assigning the job after a normal start.** The launcher can start the real git before the
  assignment; a scheduler delay makes that a race, not a proof.
- **Closing the pipes so that the orphan sees EOF or a broken pipe.** A git that hangs (the
  timeout case) is not reading or writing, so it never exits; the pump threads would also
  wait on the orphan's handles. The `kill_only_launcher` mutation below shows the cost: the
  module took 393 s, against 8 to 11 s.
- **Only the Toolhelp resume.** It added 21 to 24 ms to every git launch on this host.

the profiler counts a failed attempt as a launch (its documented rule), so the paths suite
counts 10 launches whichever shells PATH holds. Coverage is unchanged: the round trip runs
wherever the shell exists, and still skips, with the same message, where it does not.

- **Why not budgets at the larger figure:** the PowerShell bound would be one launch looser
  than that shell's exact count, `propose` of one profile would no longer give the committed
  budgets, and `CommittedBudgetTests` (budgets equal the baseline's counters) would need an
  exception. The test-side change keeps every counter an exact bound in every shell.
- **Why not a change to the profiler:** it cannot know what a skipped test would have
  launched; round 4's `4c5f5e9` set the precedent of making a test's launches the same in
  both shells.
- With no `sh` and no `pwsh` on PATH (child PATH `System32;Windows`), both round trips skip
