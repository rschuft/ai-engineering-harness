## What changed

- `integrations/planning/planning_adapter.py`: `Git` is a facade over
  `integrations/repository/repository_access.py`, loaded by path. Making a `Git` is the work-tree
  check (`check_work_tree`: the module's `open_repository`, then closed); each read session opens
  one repository on its first read and closes it at its end; the F-09.4 memos (immutable names,
  the revision snapshot, file lists by full commit id) are kept; `check_revision` and
  `check_object_name` (the module's grammar) refuse before anything is opened; the module's
  `RepositoryError` becomes a `PlanningError` with the same code, message and details, and its
  `CannotRun` (`NOT_A_WORK_TREE`, `REPOSITORY_NEEDS_DULWICH`) the adapter's `CannotRun`.
  `export_tree` replaces `archive`. Every repository is opened under the `repository` policy
  (`CONFIG_POLICY`); `Git.config_sources` lists the files read (the repository's own `config`).
  Deleted: `BatchReader`, `_Session`'s reader, `batch_line`, `Git._run`, `Git.batch_argv`, the git
  one-shots and the tar round trip. Kept: `ProcessTree` and `run_tree` (now with `cwd`, and closing
  the pipes when `communicate` raised), and `Backlog.run` and `openspec_apply_state` run on
  `run_tree`.
- `integrations/lineage/lineage_resolve.py`: `WorkResolver` reads a pinned reference from
  `export_tree(commit, '.', tmp)`; the tar handling is gone. Docstrings in `lineage_resolve.py`,
  `lineage_trace.py` and `planning_readiness.py`.
- Tests: `test_git_batch.py` retargeted (every F-09.4 id kept); `test_traversal_git.py` retargeted,
  with the git-oracle measurement in `OneTraversal`; `test_trace.ReadOnly`, `test_planning_adapter.BacklogRunnerSeam`
  and `test_work_source_operation` (dispatch) retargeted where they named `subprocess.run` or
  `BatchReader`; `two_task_fixture.py` gains `require_repository_access`, `damage_object`,
  `loose_object` and `loose_objects`; the lineage fixtures call `require_repository_access` first;
  `lineage_example.py` refuses (exit 2) to print or record an example without Dulwich.
- Documentation: the planning and lineage READMEs, `lineage_schema.json`'s notes on git,
  `docs/development.md`, and two stale statements of `integrations/repository/README.md`.

## Ratios

Method: `OneTraversal.check_against_the_git_oracle`. The module's requests of one traversal of
the example are recorded through the facade (3 `commit`, 7 `read`, 2 `files`). The git oracle
makes them as the adapter did before this leaf, each process one tree (`run_tree`,
`ProcessTree`): the work-tree check, one `cat-file --batch` for every revision and read, one
`ls-tree` per file list; the module side is the work-tree check and one opened repository. Their
answers are compared (equal), then 15 interleaved rounds of each; the one-shot is `rev-parse
--verify --quiet HEAD^{commit}` against open and `commit('HEAD')`, 30 interleaved rounds.

| Run | Traversal git / module (ms) | Ratio | One-shot git / module (ms) | Ratio |
|---|---|---|---|---|
| Git Bash, the suite | 47.8 / 21.2 | 2.3 | 11.2 / 1.23 | 9.1 |
| PowerShell, the suite | 76.2 / 21.6 | 3.5 | 18.2 / 1.26 | 14.4 |
| Git Bash, `test:all` (8 workers) | 56.3 / 24.8 | 2.3 | 12.3 / 1.37 | 9.0 |

The probe's 76.5 ms for git is reproduced (76.2 ms in PowerShell). Its 10.6 ms Dulwich figure is
not: on the same requests, raw Dulwich (the probe's method, `Repo.discover`, object lookups and
two tree walks) takes **8.7 ms** (git/Dulwich 5.6x in Git Bash), the module **21.1 ms**. The
module makes 180 Dulwich object reads for the 12 requests where raw Dulwich makes 76: each parsed
object is read twice (`_object` verifies the raw bytes, then reads the object again through the
object store to parse it), trees walked by several requests are read again (no per-repository
object cache), and Dulwich 1.2.21 looks in the packs first, listing `objects/pack` on every miss
(180 directory listings per access in a loose repository; about 5 ms of the 21). See finding F-1.

| Shell | Runs (s) | Median |
|---|---|---|

The Overseer's hypothesis, that PowerShell is slower because its `git` is the `cmd\git.exe`
launcher, was measured rather than assumed. One git launch made as the adapter makes one (a job
object), 60 interleaved rounds, the same from either shell: `git --version` 16.8 ms through the
launcher against 10.0 ms for the real git, `git -C <checkout> rev-parse HEAD` 18.0 against 11.1
ms; **+6.7 to +7.0 ms per launch**, and the launcher's job holds **2 processes** per launch
against 1. The suites make 1,055 git launches per run; at that cost the launcher predicts 7.1 to
7.3 s of the 7.9 s between the shells, and the suite gaps follow the git counts (repository: 203
launches, predicted 1.4 s, observed 1.5 s). The hypothesis holds: the residual gap is git
launches by name, now almost all in test fixtures, oracles and the retained rows (the gate,
`guest.py`, `verify_seed`).

## Findings

- **F-1 (exposed-by F-10.3; in the module of F-10.2, `622bd75`/`f585e87`): the module's read
  path is 2.4x raw Dulwich.** 180 object reads where 76 suffice, for the reasons under
  [Ratios](#ratios). It is not a correctness defect, and per the dispatch it was not tuned. With
  it the traversal criterion fails in both shells; raw Dulwich would pass it (5.6x in Git Bash).
  Decision needed: a performance repair of the module, or a different criterion or shell.
- **F-2 (exposed-by F-10.3): the required measurement and the `performance` wall budget.** The
  oracle's rounds take about 1.5 s of git in Git Bash; the category's budget is 0.6 s (limit
  1.10 s). Decision needed: a wall budget for the measurement, or fewer rounds.
- **F-3 (exposed-by F-10.3; `Taskfile.yml`, not in this leaf's paths): the product command-line
  targets run under the plain interpreter.** `planning:create`, `planning:resolve`,
  `planning:readiness`, `lineage:resolve`, `lineage:trace` and `lineage:example` use `PYTHON`;
  without Dulwich the planning commands and the example exit 2 with `REPOSITORY_NEEDS_DULWICH`
  (observed), and the lineage resolvers answer `PROJECT_UNAVAILABLE` naming it (decision 0014
  section 3). `docs/development.md` now says to pass `PYTHON=<tools python>`; the targets should
  resolve the tools interpreter as `planning:test` does.
- **F-4 (introduced-by this change, repaired in it): `lineage:example -- --record` without
  Dulwich** would have rewritten `examples/` with unavailable projections; `lineage_example.py`
  now refuses with exit 2 (observed).
- **F-5 (introduced-by this change's tests, repaired in it): `run_tree` left the pipes open when
  `communicate` raised** (a `ResourceWarning` in the exception test); it now closes them.
- **F-6 (unrelated-but-detected): decision 0014 named "Proposed"** in
  `integrations/repository/README.md` and `docs/development.md` though it is Accepted; corrected
  there. `integrations/repository/README.md` also said "No caller uses it yet"; corrected.
- **F-7 (unrelated-but-detected): 0014's documentation list** also names `AGENTS.md`'s command list
  and the README's component status; both are outside this leaf's paths and unchanged.
- **Scope note:** `integrations/dispatch/tests/test_work_source_operation.py` changed beyond an
  import path: its `Recorded` subclassed the deleted `BatchReader`; it now records read sessions.
  Ids and outcomes unchanged; no dispatch behaviour changed.
