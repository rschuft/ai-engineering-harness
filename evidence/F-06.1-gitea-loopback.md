## 4. The managed environment

`task gitea:up` starts `python -I -B integrations/gitea/gitea_host.py supervise` detached, as the
Owner's account. The supervisor creates a Job Object, sets `JOB_OBJECT_LIMIT_KILL_ON_JOB_CLOSE`
(read back: limit flags `0x2000`, no breakaway flag), assigns itself to it, and only then starts
`gitea web`, which is born inside the job. The job handle is not inheritable and is held only by
the supervisor. `IsProcessInJob(gitea, job)` is recorded as true at start. `down` calls Gitea's own
`gitea manager shutdown` and waits on both process handles.

## 7. The two identities

`task gitea:identities` (Gitea running) created, with Gitea's own CLI:

```
gitea admin user create --username aieh-site-admin --email aieh-site-admin@localhost.invalid
      --random-password --random-password-length 24 --must-change-password=true --admin
gitea admin user create --username aieh-owner --email aieh-owner@localhost.invalid
      --random-password --random-password-length 24 --must-change-password=true
```

(each with `--work-path`, `--custom-path` and `--config` as above). Gitea 28.3.0's help states that
`--must-change-password` defaults to false for the first user, hence the explicit `=true`.

```json
{"created": ["aieh-site-admin", "aieh-owner"], "admin": {"aieh-site-admin": true, "aieh-owner": false},
 "credential_targets": ["AIEH Gitea site-admin (temporary)", "AIEH Gitea owner (temporary)"]}
```

**How nothing leaked.** Gitea generates each temporary password (`--random-password`), so no
password is ever an argument: the command lines above are complete. The CLI prints the password on
its standard output, which the tool captures through a pipe into its own memory, never writes or
echoes, and parses with one pattern; on any failure only the exit code and the count of matches are
reported. Each password goes, as UTF-16LE bytes, by `CredWriteW` into one generic Credential Manager
entry (`CRED_PERSIST_LOCAL_MACHINE`, user name the Gitea account); the ctypes buffer is zeroed after
the call. It is not in an environment variable, file, log or tool output. The Credential Manager
code was first exercised once on the target `AIEH Gitea site-admin (temporary)` with a non-secret
dummy value (write, read back, delete), before any account existed.

After creation (`post_identities` check, no secret printed): both accounts have
`must_change_password` set (read from Gitea's database, read-only); both entries exist with the
account names as user names; a search of every file below `%LOCALAPPDATA%\AIEH` (UTF-8 and UTF-16)
and of the checkout's 467 tracked and untracked, not ignored files finds neither temporary password.
`verify` passes with the accounts in place.

**Disposable-instance qualification of the whole flow** (a root in scratch, an in-memory credential
store instead of Credential Manager, the browser steps driven over HTTP):
`finish-first-login` before the sign-in refuses with `FIRST_LOGIN_PENDING`; a second `identities`
refuses with `ACCOUNT_EXISTS`; signing in with each temporary password and submitting the forced
password change (login 303, change page 200, change 303) clears `must_change_password`; afterwards
each temporary password no longer authenticates and each new one does; `finish-first-login` then
finds no temporary password in the root or the checkout, deletes both entries and reports none
remaining; the Owner account gets 403 from `/api/v1/admin/users`. A first attempt refused with
`TEMPORARY_PASSWORD_FOUND` because LevelDB's `queues/common/LOCK`, held open by Gitea, could not be
read; it is empty, so the search now skips only unreadable files of size 0 and still counts any other
unreadable file as a hit.

## 8. The Owner's first sign-in (no commands)

1. Open `http://127.0.0.1:13300/`.
2. Read each temporary password in Control Panel → Credential Manager → Windows Credentials:
   `AIEH Gitea site-admin (temporary)` (user `aieh-site-admin`) and `AIEH Gitea owner (temporary)`
   (user `aieh-owner`); Windows asks for the Owner's own sign-in to show it.
3. Sign in as `aieh-site-admin`; Gitea forces a new password. Sign out, then do the same as
   `aieh-owner`.

Then an agent runs `task gitea:finish-first-login`, which verifies (no `must_change_password`; each
temporary password no longer signs in and occurs in no file of the managed root or the checkout),
deletes the two entries and reports. **Not run:** the Owner has not signed in yet.

## 9. What stays reachable during bootstrap

During bootstrap every process of the Owner's Windows account, host agent sessions included, can
read `app.ini` and the SQLite database (`fd-bootstrap-shared-identity`). The secrets in `app.ini`
reach Gitea's private API (`INTERNAL_TOKEN`) and, with write access to the database, any account,
its administrator flag or its password hash can be changed: such a process can forge or take over
sessions and identities. Until `finish-first-login`, the two temporary passwords are also readable
from Credential Manager by the same account. The final passwords exist only as Gitea's password
hashes. Directory placement is not a security boundary (decision 0009, point 11).

The supervisor runs the tool from the source checkout: no installed harness distribution exists yet.
