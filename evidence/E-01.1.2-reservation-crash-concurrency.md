## 1. Method

- **Crash mechanism.** The new worker command `store_worker.py scripted` opens the store and
  runs real library calls: `reserve_attempt`, then `transition` to each named state. The crash
  is applied at one SQL statement boundary of one call. For the target call, the worker wraps
  the store's `sqlite3` connection in a test-side `CrashingConnection`. It delegates every call
  and stops the process once, before or after the first statement with a given prefix:
  - `exit`: `os._exit(9)`, with no rollback, no close and no checkpoint;
  - `hold`: the worker prints its position and blocks, and the test kills it with
    `Popen.kill`.

  The library has no fault-injection seam, and none was added. The wrapper lives only in the
  worker. Every crash prints `crashed_at` with the exact point before it fires. The test
  requires that line and the matching exit code, so no row can pass without its crash having
  happened.
- **Waiting.** The parent waits on each worker's own output lines and exit, never on a fixed
  sleep (`WAIT_CEILING_S = 60` only bounds a hang).
- **Verification after every crash:**
  - `PRAGMA integrity_check` = `ok`;
  - `PRAGMA foreign_key_check` empty;
  - `storecore.check_current`;
  - the store kind's own invariants (`KIND.verify`: each event history matches its state;
    `attempt_id` and `conversation_id` equal the uuid5 of the key; `live` matches the state; no
    `attempt/` key lacks an identity);
  - no triple with more than one live row.

In every row:
- the row counts are exactly 1/1/n for `attempt`, `attempt_identity`, `attempt_event`, or
  0/0/0 when nothing persisted;
- `state_seq` = the number of events minus 1;
- the re-request returns the derived `operation_key`, `attempt_id`
  (`uuid5(ATTEMPT_NAMESPACE, key)`), `conversation_id` (`uuid5(CONVERSATION_NAMESPACE, key)`)
  and the same `design_revision` and identity fields, with `created=False` whenever a row
  existed;
- every verification in section 1 passes, both after the reopen and after the re-request and
  next-ordinal step.

`test_killed_writer_releases_the_lock`: a writer killed inside the reservation transaction leaves
nothing, and the next writer reserves at once under a 2 s busy timeout.

**Restart semantics (`RestartTests`):**
- One process reserves and dispatches, then exits without closing (the WAL is not
  checkpointed and is non-empty).
- A new process's `attempts()` and identity lookup (`attempts`, `get`), and two later reopens
  in the test process, return the same reservation and identity: the same UUIDs and
  `design_revision`, and the same canonical dump bytes. After the clean close the WAL is
  checkpointed away.
- After a restart in each lifecycle state (reserved, dispatched, unknown, confirmed via
  unknown, failed), an identical request is `existing` with the same identity and state.

## 3. Concurrent admission

`ConcurrencyTests`: 8 processes each. Each opens the store, reports ready, and is released by a
`go` line once all are ready. The store's own policy applies: `BEGIN IMMEDIATE` and a 10 s busy
timeout. The test asserts outcome classes, never timing, and fails on any raw `sqlite3` error
(the worker reports one as `raw:<type>`).

Observed outcome multisets over 20 in-process repetitions of the class (scratch `tally.py`, which
wraps `race()` to record outcomes):

| Race | Required semantics | Observed (20 runs) |
|---|---|---|
| 8 identical requests | one `created`, 7 `existing`, one key, one live row, one conversation UUID | 20 × {created, 7 × existing} |
| ordinals 1 to 8 on one fresh triple | ordinal 1 `created`; every other `LiveClaim` or `OrdinalOutOfSequence`; one live row | 20 × created plus 7 refusals, in 8 different `LiveClaim`/`OrdinalOutOfSequence` mixes (from 7 × LiveClaim to 7 × OrdinalOutOfSequence) |
| ordinals 1 to 8 after ordinal 1 `failed` | 1 `existing`, ordinal 2 `created`, the rest `LiveClaim` or `OrdinalOutOfSequence` | 20 × that, in 6 different mixes |
| one key, 8 different intents (workspaces) | one `created`, 7 `ConflictingReservation` | 20 × that |
| 8 different triples (4 works × implement/review) | all `created`, 8 live rows | 20 × that |
| 7 reservers of ordinal 2 race the transition that confirms ordinal 1 | the transition always succeeds; at most one reserver `created`, later ones `existing`, earlier ones `LiveClaim`; if none created, all `LiveClaim` and a later request is admitted | 16 × {created, 6 × existing}, 1 × {4 LiveClaim, created, 2 existing}, 1 × {3 LiveClaim, created, 3 existing}, 1 × {6 LiveClaim, created}, 1 × {7 LiveClaim} |
| 8 competing transitions of one dispatched attempt (confirmed/unknown/failed, `expected_from='dispatched'`) | exactly one `transitioned`, 7 `IllegalTransition`; 3 events; `live` matches the winner | 20 × that |

**SQLITE_BUSY.** No `SQLITE_BUSY` or other raw `sqlite3` error escaped the library in any run:
- 20 tally repetitions;
- 25 + 25 stability iterations;
- every suite run.

Every writer takes the write lock with `BEGIN IMMEDIATE` before it reads, and waits under the
busy timeout. The mutation check shows that this is load-bearing (section 5).

The reserve-versus-transition race first started the transition worker first, and 20 of 20 runs
then took the transition-first branch. The test now releases the reservers first, and both
branches occur (above).

## 6. E-01.1 parent proof: clause table (for the Overseer)

Parent E-01.1 proof: "Concurrent identical dispatch requests resolve to one reserved key; a
restart finds the same UUID and revision."

| Clause | Evidence | Observed |
|---|---|---|
| Concurrent identical dispatch requests resolve to one reserved key | `ConcurrencyTests.test_identical_requests_resolve_to_one_reserved_key` (8 processes: 1 `created`, 7 `existing`, all with the same key, `attempt_id` and `conversation_id`; one row, one live claim), 20/20 tally runs and 50/50 stability iterations; also E-01.1.1 `AcceptanceTests` (one process, two processes, 8 concurrent) | **yes** |
| … and no second claim of the same work, design revision and stage is admitted concurrently (dispatch step 02) | competing ordinals (two variants), different intents, reserve-versus-transition: never more than one live row; refusals are typed only | **yes** |
| A restart finds the same UUID | `RestartTests` (a new process after an exit with the WAL not checkpointed, then two reopens) and every crash-matrix row: the same `conversation_id` and `attempt_id` | **yes** |
| … and the same revision | the same `design_revision` and full identity in every case above | **yes** |
| A crash mid-reservation leaves no partial reservation, and the request can be repeated | crash matrix rows 1 to 7 (exit and kill, inside the transaction and after COMMIT) | **yes** |
| A lost reply does not create a second attempt | rows 7 and 12: a crash after COMMIT, or after `dispatched`, is answered by the identical request as `existing` with the same `conversation_id`; the next ordinal is refused while the attempt is live | **yes** (store level; the Agent Server side is E-01.4.x) |

Inference, not observation: the store side of the parent proof is satisfied. Whether the
dispatcher actually re-sends the same `conversation_id` to the Agent Server after a restart is
E-01.3.x and E-01.4.x.
