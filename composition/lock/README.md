# Component lock (F-01.2)

The lock pins the upstream composition selected in F-01.1
(`composition/candidates.json`) on the version line fixed by
[decision 0001](../../decisions/0001-agent-server-dispatch-precondition-and-version-line.md).
`components.lock.json` is the entry point. It names every pinned artifact and
points to the hash-locked Python and npm files.

## Resolver command

```
<tools python> -I -B composition/resolve.py --work <empty-or-absent directory outside the checkout>
```

`<tools python>` is the Python tools interpreter (`task tools:install`; `python -I -B
integrations/paths/tools_install.py --python` prints it): the resolver reads the source tags with
the shared [repository-access module](../../integrations/repository/README.md) over Dulwich
(plan leaf F-10.6, decision 0014, R11). Under an interpreter without Dulwich it stops with
`REPOSITORY_NEEDS_DULWICH` (exit 2), naming `task tools:install`; there is no git fallback.

The resolver does five things:

1. It lists each pinned source tag over HTTPS (`ls_remote` of the repository-access module: anonymous, no git, no credential helper) and checks the tag → commit mapping: an annotated tag's object id and its peeled commit, or a lightweight tag's commit.
2. It downloads every locked Python wheel for each locked target and checks its sha256. It builds the one reviewed sdist (see [Reviewed sdist exception](#reviewed-sdist-exception-decision-0002)). It installs the host target's set with
   `pip install --target <work>/python/site --only-binary :all: --require-hashes --no-deps --no-index`
   and reads the installed versions back with `pip inspect --path`. It re-hashes every installed file against its RECORD.
3. It runs `npm ci --ignore-scripts` from `npm/package-lock.json` with an isolated cache and empty npm config, so npm itself verifies each tarball's integrity. It then compares npm's hidden lockfile and `npm ls --all --json` with the lock. Every locked tarball that npm skips on this host (other OS or CPU optionals, such as `backlog.md-linux-x64` and `-arm64`) is downloaded and integrity-checked separately.
4. It fetches each OCI index and its linux/amd64 and linux/arm64 manifests (linux/amd64 only for the CI job image) from the registry by digest and recomputes their sha256. This is a manifest-digest check. No image is pulled and nothing is run.
5. It checks the release assets (GitHub releases, and the gitea-runner release on gitea.com) against the upstream checksum files, which it downloads and verifies by sha256. Where upstream publishes no checksum file, it uses the GitHub asset digest.

It writes `<work>/report.json`. The main fields are:

| Field | Meaning |
|---|---|
| `resolution` | Every verified digest. It is deterministic for a given lock and host. |
| `resolution_digest` | sha256 of the canonical JSON of `resolution`. |
| `installed` | The versions the installers report. For Python, each package also carries `record_sha256`: the sha256 of its sorted RECORD rows (path, hash, size), taken after every listed file has been re-hashed on disk and matched. Console-script launchers are generated by pip at install time, and on Windows they embed the install timestamp. They are still checked against RECORD, but only their path and size enter the digest. For npm, it is the version per installed path; npm ci has already checked each tarball's integrity. |
| `installed_digest` | sha256 of the canonical JSON of `installed`. It depends on installed contents and versions, never on wheel archive bytes. |
| `conversation_image` | The verified conversation image digest. |
| `checks` | Each check with a pass or fail status. |
| `observations` | Tag → digest lookups and the sha256 of the rebuilt reviewed-sdist wheel. These are informational and are not included in any digest. |
| `run` | Timestamps and tool versions. |

Two clean runs are equivalent when their `resolution_digest` and `installed_digest` values are equal.

Exit codes:

| Code | Meaning |
|---|---|
| 0 | All artifacts verified and every locked set fully installed. This is the current expected result. |
| 1 | Any mismatch or failure, including a refused reviewed-sdist build. |
| 2 | Usage or prerequisite error. |
| 3 | All artifacts verified, but a `known_gaps` entry with severity `blocking` leaves an installed set incomplete. `known_gaps` is currently empty. |

**Host prerequisites** (the resolver checks each one):

- CPython 3.12 with pip ≥ 23.1, as the Python tools interpreter (which provides Dulwich)
- Node.js ≥ 24 with npm ≥ 11
- HTTPS access to:
  - pypi.org and files.pythonhosted.org
  - registry.npmjs.org
  - github.com and api.github.com (unauthenticated, 2 API calls)
  - ghcr.io
  - registry-1.docker.io and auth.docker.io
  - gitea.com (the gitea-runner source tag and release checksum file, Q-02.2.1; its release downloads redirect to gitea.com's attachment storage on Cloudflare R2, `*.r2.cloudflarestorage.com`)

Registry tokens are anonymous, held in memory and never printed. No credentials are used. The resolver never imports or executes installed package code.

`ghcr.io/openhands/agent-server@sha256:b43ee580c2177280c81cb807c9a559d7a14aa13b48dba5040132a6a637bb6d55`.
This is the 1.60.1-python multi-arch index. These references are **non-conforming**:

- `…:e99e5c7-python`, a different index
- Any `latest-*` or other tag reference

This lock does not configure any server. F-04.1 sets `conversation_image` to the locked reference, and F-04.2 and E-01.5 observe it (decision 0001 §4).

## Reviewed sdist exception (decision 0002)

`openhands-tools` 1.60.1 requires `func-timeout>=4.3.5`. PyPI publishes every func-timeout release (3.0.0 through 4.3.5) as an sdist only. [Decision 0002](../../decisions/0002-reviewed-sdist-exception-for-resolution.md) allows exactly one reviewed sdist. The lock records it in `python.reviewed_sdists`:

| Field | Value |
|---|---|
| Package | `func-timeout` 4.3.5 |
| sdist sha256 | `74cd3c428ec94f4edfba81f9b2f14904846d5ffccc27c92433b8b5939b5575dd` |
| `setup.py` sha256 (in archive) | `79b14e79da31bcf9ac21bdc350615c438868604b1f6a92f3cb12597f5cd4798b` |
| `setup.cfg` sha256 (in archive) | `1c473cbaee8da5fc46e7f0158794af5cea4414c34a3cf3f180c2001f5e38bd3e` |
| Archive shape | 41 members (35 files), no links |
| Reviewer | Overseer, 2026-11-06 |
| Licence | LGPL-3.0: the shipped `LICENSE` text and the module headers say so, while `PKG-INFO` and the `setup.py` header say LGPLv2/2.1. The shipped text governs ([audit](../inventory/PUBLICATION-AUDIT.md) C8). This is an open distribution item (see `../inventory/LEDGER.md`). |

The resolver builds it only when every check passes:

1. The downloaded sdist's sha256 equals the lock and PyPI.
2. The archive matches the review: same member count, no links or unsafe paths, the reviewed build-file hashes match, and there is no unreviewed `pyproject.toml`, `setup.py` or `setup.cfg`.
3. The backend (`python/build-requirements.txt`) installs from hash-verified wheels into `<work>/python/build-backend`. That is never the install target, and no build dependency is fetched unpinned.
4. The build runs with `python -I -S` and the setuptools legacy backend. It uses an environment built from scratch, so no inherited variables or credentials reach it. HOME and TMP point into the work directory, and `SOURCE_DATE_EPOCH=1566250327` is set (the sdist's upload time).
5. The build yields exactly one wheel. It must be tagged py3 (or py2.py3)-none-any, have `Root-Is-Purelib: true` and contain no compiled member.

Any failure refuses the build and the resolver exits 1. The wheel's sha256 is recorded in `observations`. Reproducibility is judged on installed contents (RECORD) and versions. Every other package stays wheels-only. If upstream ever publishes a func-timeout wheel, prefer it and retire the exception.

## Regenerating the lock

Regenerate only under the revisit rule, using the tools pinned in `components.lock.json` (`tools`). Verify each tool's sha256 before running it.

```
# Python (repeat for each target, and its output file):
#   x86_64-pc-windows-msvc  -> windows-x86_64.txt
#   x86_64-manylinux_2_28   -> linux-x86_64.txt
#   aarch64-manylinux_2_28  -> linux-aarch64.txt
UV_NO_CONFIG=1 UV_PYTHON_DOWNLOADS=never UV_CACHE_DIR=<empty dir> \
  uv pip compile python/requirements.in --excludes python/excludes.txt --python-version 3.12 \
    --python-platform <target> --no-build --generate-hashes --no-header --no-annotate -o python/<file>

# npm (from composition/lock/npm, with empty config files and an empty cache):
npm install --package-lock-only --ignore-scripts --no-audit --no-fund \
  --registry https://registry.npmjs.org/ --cache <empty dir> --userconfig <empty file> --globalconfig <empty file>
```

The build backend is regenerated the same way, with `--universal` in place of `--python-platform`:

```
uv pip compile python/build-requirements.in --python-version 3.12 --universal --no-build --generate-hashes --no-header --no-annotate -o python/build-requirements.txt
```

So are the tools lock and the dev tools lock:

```
uv pip compile python/tools-requirements.in --python-version 3.12 --universal --no-build --generate-hashes --no-header --no-annotate -o python/tools-requirements.txt
uv pip compile python/dev-requirements.in --python-version 3.12 --universal --no-build --generate-hashes --no-header --no-annotate -o python/dev-requirements.txt
```

After regenerating, update `components.lock.json`, which records pin and entry counts and the direct integrities, and run the resolver.
